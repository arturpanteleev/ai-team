## [Unreleased]

### Security

- **Выкладка через TeamCity: второй раунд усиления (BL-32).** Запуск сборки
  несёт уникальный `env.AI_TEAM_DEPLOY_ID`; если ответ на запуск потерян,
  повтор этапа находит сборку по нему и продолжает, только если она одна, из
  настроенной build configuration и на той же ревизии — иначе по-прежнему
  нужен оператор. Явным отказом TeamCity считаются только HTTP 400, 401, 403,
  404, 405 и 415. `webUrl` и редиректы сравниваются по имени хоста без учёта
  регистра и порту (443 по умолчанию). Ревизия в ошибках и событиях
  обрезается. Изолированный `git` создаётся без шаблона каталога, скачивание
  обрывается при зависании, каждая проверка мержа ограничена по времени,
  `gh` запускается в пустом временном каталоге. Ограничения squash/rebase и
  то, что человеческий гейт перед выкладкой обеспечивает защита ветки в
  GitHub, задокументированы.

### Added

- **Рекомендательные гейты, технические повторы и админский обход (S06).**
  `mode: advisory` в ссылке на гейт теперь допустим для автоматических гейтов
  (кодовых и LLM; для `human_approval` и grill `agent_review` отклоняется):
  `fail` или техническая ошибка такого гейта не блокирует переход и не прячется
  — попытка хранит свой `execution` и `verdict`, событие попытки несёт
  `mode: advisory` и `advisory_warning`, `check_passed` — список `warnings`
  (severity `warning`), отчёт проверки помечает правило `advisory_failed` /
  `advisory_error`; в группе можно смешивать обязательные и рекомендательные
  гейты. Технический сбой (`error`/`timeout`) обязательного гейта теперь
  предлагает действие `retry_gate`: гейт запускается снова на **той же**
  версии результата (новая попытка, прежняя остаётся; успешные гейты группы не
  повторяются; запись `gate_retry_requested` переживает падение;
  повторный сбой поднимает новое решение): `POST
  /api/runs/{run}/stages/{stage}/gates/{gate}/retry` и `POST
  /api/runs/{run}/gate-attempts/{attempt}/retry`. Обход проваленного
  обязательного гейта — только **системное право администратора** (роль
  `admin`, permission `gate:override`), отдельное от `product_owner`: другим
  участникам `403`, без причины — ошибка валидации, а `POST
  /api/runs/{run}/approvals/{id}/decisions` больше не обходит это право.
  Обход пишется как неизменяемое `check_overridden` (автор, `authority`,
  время, причина, хеш результата, посещение, проваленные гейты и ID попыток) и
  не меняет исход гейта: `fail` остаётся `fail` в попытках, событиях, API и UI;
  обход действует только на ту версию результата, для которой сделан.
  `GET /api/runs/{run}/gates` (и MCP `get_task_gates`) отдаёт реальные гейты
  каждой версии, их попытки, обходы, предупреждения и агрегированное
  разрешение перехода с причинами. Схема 17: создатель команды (и в миграции —
  владелец существующей команды) получает `admin` вместе с `product_owner`,
  остальные PO — нет; последнего администратора снять нельзя; в локальном
  режиме локальный владелец получает право явно. UI: красное предупреждение
  об обходе провала и янтарное о рекомендации в карточке задачи, маршруте и
  истории; форма обхода видна только администратору.
- **Трекер: входящие изменения через контроллер (S15).** Блок
  `tracker.inbound` (`poll_interval`, `rules[]` с `status`, `action:
  advance|return`, необязательными `stage` и `to_stage`) превращает смену
  статуса в трекере в запрос, а не в команду: опрос с durable-курсором и ручной
  `POST /api/tracker/sync`; идемпотентность по ID внешнего изменения; собственные
  переходы ai-team (`origin: ai-team`) не вызывают входящих запросов. Автоматически
  выполняется только продолжение готового этапа (`run-agent`); подтверждения,
  решения по проваленным гейтам и возвраты остаются ожидающим запросом или
  конфликтом с причиной и допустимыми действиями (преждевременный «Done»
  ничего не обходит), неоднозначный статус графа не двигает. Сбой трекера
  оставляет курсор на месте и виден; повтор восстанавливает без дублей. REST:
  `GET /api/tracker/sync`, `GET /api/tracker/inbound`, `POST
  /api/tracker/sync`, `POST /api/runs/{runID}/tracker/inbound/{id}/dismiss`;
  MCP: `get_tracker_status`, `get_tracker_sync`, `list_tracker_inbound`,
  `list_tracker_link_conflicts`, `list_tracker_deliveries`, `get_task_tracker`.
  Схема SQLite v18 (`tracker_inbound_changes`, `tracker_sync_state`).
- **Встроенные кодовые гейты на общем контракте (S04).** `required_sections`,
  `verdict_marker`, `pr_exists`, `pr_open`, `pr_base_branch`, `project_checks`,
  `pr_checks_green` исполняются только планировщиком гейтов (попытка с
  `execution` и `verdict`); удалён неиспользуемый обходной `runHardChecks`.
  Нечитаемый md-результат у `required_sections`/`verdict_marker` теперь `error`
  (технический сбой), а не `fail`. Добавлен гейт `required_phrases@1`: явные
  `case`, `scope` (весь результат или раздел по заголовку), `match`
  (`all|any|at_least`), `unit` (подстрока или слово) и опциональный
  `regex: true` (только RE2, до 50 фраз по 200 байт, компиляция при валидации);
  скриптов нет. Неверный параметр — ошибка конфигурации до запуска. Тесты
  pass/fail/error на каждый гейт, приёмка «спека без Критериев приёмки
  блокируется до LLM и человека». Инъекция `WithPullRequestRunner` для `gh pr view`.

- **LLM- и человеческий гейты в общей цепочке (S05).** Библиотека получила
  `agent_review@2` и `human_approval@2` (версии 1 не изменены, закреплённые
  шаблоны продолжают работать). LLM-гейт вызывает проверяющего с фиксированным
  входом и обязан ответить по `verdict_schema` (`verdict_marker` или строгий
  `json` с `verdict/reason/findings`); ответ вне схемы и отказ рантайма —
  `execution: error`, а не `pass`; `max_attempts` (1..5) повторяют только такие
  сбои, все вызовы видны в причине попытки (`pkg/llmgate`, не зависит от
  `grill`). Человеческий гейт пишет ожидание и каждое решение (одобрение, отказ,
  возврат) в ту же историю попыток гейтов с автором, ролью и комментарием, в том
  числе когда решение принято, пока процесс остановлен; `on_reject: stay`
  оставляет задачу на этапе после отказа (причина обязательна, новая версия
  повторяет всю цепочку, счётчик посещений не расходуется). Решение о переходе
  принимает единый сервис `pkg/humandecision` (действие, точный хеш предмета,
  роль, запрет самоподтверждения, аудит `human_gate_decided`, повтор доставки
  — `human_gate_decision_replayed`), через который идут и `POST .../confirm`, и
  `POST .../approvals/{id}/decisions`; `confirm` принимает необязательный
  `subject_hash`, фронтенд его отправляет (путь без хеша объявлен устаревшим:
ответ с заголовками `Deprecation`/`Warning`, для MCP хеш обязателен).
Исправлено по ревью: отказы `on_reject: stay` не расходуют лимит посещений и
после перезапуска run'а (resume по решению из Web/REST); повтор доставки
учитывает роль, а один человек в нескольких ролях голосует по разу на роль;
два параллельных одинаковых запроса пишут один `human_gate_decided`. Ограничения: `human_approval` по-прежнему
  только в последней группе, а LLM-гейты группы вызываются по одному.

- **Docker-исполнитель этапа code review (S10).** Адаптер `executor_adapters`
  получил блок `docker` (образ по digest, сеть `none` по умолчанию, лимиты
  CPU/памяти/процессов): этап, например `code_review`, исполняет внешний
  контейнерный агент по тому же JSON-контракту, а подключение другого агента не
  меняет граф. Входы этапа монтируются только на чтение в `/stage/in`, результат
  пишется в приватный каталог `/stage/out`, пути хоста в запрос не попадают,
  в контейнер идёт только allowlist `env_allow`. Ошибка контейнера, невалидный
  или неоднозначный ответ — техническая ошибка, а не вердикт; контейнер
  удаляется при отмене, осиротевшие помечены `ai-team.stage-attempt`. В
  Файлы результата записываются в объявленные пути только после проверки
  контракта всего ответа, расхождение вердикта удаляет выходы попытки;
  `/stage/out` внутри приватного каталога, размер ограничен `output_mb`
  (по умолчанию 64 МБ, контейнер останавливается при превышении). В
  `executor_info` записываются `container.image` (digest), сеть, лимиты,
  mounts и исключения. Добавлен воспроизводимый агент
  `e2etest/container-review-agent` и интеграционные тесты с реальным Docker;
  в `docs/reference/config.md` описано подключение другого агента и что нужно
  от CoreKit (вывод результата в JSON-файл).
- **Гейт внешней программы с JSON-контрактом (S07).** В библиотеке появился
  `external_program@1`: доверенная команда из конфига репозитория (argv без
  shell, `timeout_seconds`, `cwd`, `env_allow`, `max_output_bytes`) получает
  JSON-контекст `ai-team.gate/v1` и возвращает один JSON-вердикт
  `pass|fail|not_applicable`. Раннер `pkg/gaterun` отличает валидный `fail`
  (`succeeded`) от падения, неверного JSON, превышения лимита вывода и потери
  процесса (`error`), таймаута (`timeout`) и отмены (`canceled`) — они никогда не
  становятся `pass`. Группа процессов убивается целиком; секреты вычищаются из
  логов, причины и записи запуска, файл-доказательство с секретом не
  сохраняется; запуск идемпотентен по ID попытки, способ запуска вынесен в
  интерфейс `Launcher` (для Docker-адаптера). Программа не получает каталог
  попытки (её `evidence_dir` — отдельный временный каталог), запись попытки
  подписывается HMAC и принимается при повторе только с верной подписью;
  JSON с повторяющимися ключами или ключами в другом регистре — `error`;
  фоновые потомки убиваются после выхода лидера; значения всех `env_allow`
  маскируются в логах; относительный путь программы не выходит за репозиторий. Планировщик гейтов пока не
  подключён. Справочник — `docs/reference/gate-protocol.md`, демо —
  `pkg/gaterun/testdata/demo-gate.sh`.

- **Внешний исполнитель этапа (S09).** Этап `executor: agent` можно отдать
  именованному внешнему адаптеру (`executor_adapters` + `adapter` на этапе):
  доверенный argv без shell получает JSON-запрос (входы, объявленные выходы,
  контекст задачи) и возвращает один JSON-ответ (статус, выходы или файлы,
  метаданные, заявленный verdict) с лимитами времени и вывода, allowlist
  окружения и redaction лога. Появился интерфейс `StageExecutor`
  (`pkg/stageexec`) с реализациями для внутреннего агента и внешнего адаптера;
  исполнитель не зависит от gate runner. Ошибка программы, таймаут,
  невалидный ответ или отсутствие выхода не выглядят завершённым этапом, а
  выходы, mutation scope и verdict проверяются тем же путём, что у внутреннего
  агента. Фактический исполнитель попытки (`executor_info`) записан в манифест
  и в `attempt_finished` (`executor_kind`, `executor_name`).

- **Сетевой MCP для Claude и Codex (S12).** `POST /mcp` на `ai-team web`:
  stateless Streamable HTTP по спецификации MCP 2026-07-28 (клиенты 2025-11-25
  подключаются через `initialize`), официальный Go SDK. Авторизация только
  Bearer-токеном: персональные долгоживущие токены `aitm_…` (SHA-256 в SQLite,
  срок, отзыв, журнал; выпуск только для себя через `/api/mcp/tokens` и страницу
  «Доступ MCP») либо токен, принимаемый веб-сервером; роли берутся из реестра
  команды на каждый вызов. Инструменты и ресурсы чтения над теми же обработчиками
  и RBAC, что REST: проекты, backlog, задачи, события, логи, артефакты, шаблоны,
  каталог гейтов, метрики, команда. Большие ответы режутся и пагинируются.
  Проверка `Origin` и `--mcp-allowed-origins`. Схема БД 15. См.
  `docs/reference/mcp.md`. OAuth и действия — следующие шаги.

- **Трекер задач: явная связь 1:1 и исходящая синхронизация (S14).** Вместо
  поиска ключа в `external_links` задача связывается с карточкой явным полем
  (`tracker` + `issue_key`, `PUT/DELETE /api/runs/{runID}/tracker/link`) с
  проверкой формата, доступности и уникальности; задача — максимум одна
  карточка, карточка — максимум одна задача, исправление только явное.
  Интеграция стала абстрактной: интерфейс `Tracker` с реестром адаптеров
  (`jira` на REST API v2/v3 и детерминированный `fake` для тестов и демо),
  методом чтения изменений с курсором под будущую входящую синхронизацию.
  Конфиг: `tracker.on_enter` / `tracker.on_pass` (старый
  `jira.stage_statuses` читается как `on_pass`), `tracker.adapter`,
  `jira.api_version`. Вход в этап и успешное завершение вызывают только
  настроенные переходы; провал, пропуск, отклонение и обход комментируются
  честным исходом и не выдаются за успех. Комментарии идемпотентны по ID
  события, исходы доставок хранятся в durable-таблице и видны в API
  (`/api/tracker`, `/api/runs/{runID}/tracker`) вместе с ручным повтором;
  ошибка трекера не откатывает прогон. Существующие корректные ссылки
  переносятся один раз, неоднозначные показываются как конфликт. Схема БД v16,
  право `tracker:link`. **Поведение изменилось:** ссылка на карточку в
  `external_links` у НОВЫХ задач больше не связывает карточку автоматически —
  связь создаётся только явным `PUT /api/runs/{runID}/tracker/link`.
  Идемпотентность комментария в Jira проверяется по всем страницам комментариев,
  а не по 50 последним; устаревший повтор `on_enter` пропускается (`superseded`),
  неудавшиеся доставки снятой связи помечаются `abandoned` и не считаются
  ошибками; при сбое сохранения доставки опрос идёт с экспоненциальной паузой.
  Jira `Changes` использует `/search/jql` (запасной `/search` для Data Center),
  относительное окно JQL и определяет автора по `/myself`.

- **Контракт гейтов и версионированная библиотека (S02).** Введены типы
  определения гейта, ссылки этапа (`ID@версия`, параметры, `required|advisory`),
  групп (`exit_gate_groups`: группы последовательны, гейты внутри независимы) и
  попытки с раздельными `execution` (`pending/running/succeeded/error/timeout/canceled`)
  и `verdict` (`pass/fail/not_applicable`). Реестр именованных гейтов в Go
  (`pkg/gatelib`: `required_sections`, `verdict_marker`, `pr_*`, `project_checks`,
  `pr_checks_green`, `agent_review`, `human_approval`) читается через
  `GET /api/gates/catalog`; редактировать его из UI/API нельзя. Схема конфига
  **v6** заменяет `required_sections`/`check`/`confirm` одним `exit_gate_groups`;
  v5 продолжает загружаться и даёт тот же путь и вердикты, `init` создаёт v6.
  Неизвестный ID, версия или параметр отклоняются до запуска с путём вида
  `stages[1] (product_spec): exit_gate_groups[0][0]`; шаблон закрепляет точные
  версии определений, поэтому новая версия библиотеки не меняет идущие задачи.
  Исполнение групп планировщиком — отдельная задача.
- **Проекты: папки для задач и обязательная привязка (S01).** Проект — ID,
  имя, описание и архивный признак; репозитория, шаблона и прав у проекта нет.
  Каждая задача и идея бэклога принадлежит ровно одному проекту: `POST
  /api/runs` и `POST /api/backlog` без `project_id` отклоняются (`400
  project_required`), архивный проект не принимает новые задачи (`409
  project_archived`), история читается. REST: `GET/POST /api/projects`,
  `GET/PATCH /api/projects/{id}`, `POST .../archive` и `.../unarchive`
  (физического удаления нет); создавать и архивировать могут Product Owner и
  Architect (`project:manage`). Миграция схемы 14 создаёт проект «Основной» для
  старых задач и идей, чистая установка получает его же. `GET /api/runs` и
  `GET /api/backlog` принимают `project_id`; автоподбор и восстановление
  admission сохраняют проект. В Web UI: страница «Проекты», обязательный выбор
  проекта в формах новой задачи, фильтр проекта на доске и в списках, понятная
  пустая страница нового проекта. **Несовместимое изменение API:** клиентам,
  создающим задачи, нужно передавать `project_id`.
- **Планировщик групп гейтов (S03, `pkg/gatesched`).** Группы
  `exit_gate_groups` исполняются последовательно, гейты внутри группы —
  параллельно с пределом `gate_concurrency` (верхний уровень конфига, 1..64,
  по умолчанию 4). После отказа обязательного гейта следующие группы не
  стартуют, а уже запущенные гейты доводятся до исхода. Волна
  привязана к хешу результата, он сверяется до неё, после каждого гейта и в
  конце (правка обнаруживается и отменяет волну, физического запрета записи
  нет); успех для старого хеша не
  засчитывается новому — новая версия исполняет все группы заново. Каждая
  попытка пишется в `events.jsonl` (`gate_attempt_started/waiting/finished` с
  временем, `execution` и `verdict`), при старте задачи записываются
  закреплённые определения (`gate_pins_recorded`), после рестарта завершённые
  гейты не повторяются, прерванные закрываются как `canceled`. Допустимы
  произвольные цепочки из кодовых и LLM-гейтов (в том числе разных видов в
  одной группе и несколько `agent_review` на этапе); `human_approval` — в
  последней группе. Временный мост S02
  (`projectGates` и его ограничения) удалён.

- **Уведомления из `ai-team run` и `scheduler-worker` (B-81).** Каналы из
  раздела `notifications` теперь получают события не только от `ai-team web`:
  локальный `ai-team run` и `ai-team scheduler-worker` отправляют их тем же
  диспетчером из той же базы `.ai-team/web.db`, каждый по своему курсору.
  Пара «канал — событие» атомарно захватывается в общем журнале
  `notification_deliveries` до отправки, поэтому web и run на одной базе и
  повторный run дублей не шлют. Сбой канала по-прежнему пишется как
  `integration_error` и на исход run не влияет; без `notifications` поведение
  не меняется.

- **Вход через SSO (OIDC) и постоянные сессии дашборда (B-83).** В облачном
  режиме `ai-team web --oidc-issuer … --oidc-client-id … --oidc-redirect-url …`
  включает вход через OpenID Connect: authorization code + PKCE, проверка
  `state`, `nonce`, подписи `id_token` по JWKS, issuer, audience и срока.
  Client secret — только из переменной окружения. Функции пользователя
  берутся из назначений участника команды. Сессии браузера хранятся в базе
  дашборда (схема v10; бинарники со старой схемой такую базу не открывают),
  переживают перезапуск, продлеваются при активности и отзываются кнопкой
  «Выйти». Локальный режим с токеном работает как раньше.
- **`delivery_timeout`** — бюджет всей post-terminal доставки (`git commit`,
  `git push`, `gh pr view/create`) вынесен в конфигурацию проекта, значение по
  умолчанию — `10m`. Прежде доставка исполнялась с `context.Background()`:
  зависший `git` или `gh` держал контроллер бесконечно и не прерывался ни
  SIGINT, ни SIGTERM. Бюджет доставки намеренно отвязан от
  `budget.max_wall_time` run'а (доставка уже одобрена человеком), но привязан
  к контексту процесса — `Ctrl-C` её прерывает. Внешние команды доставки
  исполняются неинтерактивно (`GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`,
  askpass-хуки не наследуются) (QS-06).
- **Новый сайт документации.** Документация перестроена по схеме «знакомство →
  учебник → руководства → справочник»: страница «Как это выглядит» со
  скриншотами настоящего прогона, сравнение с 13 альтернативами, учебник на
  агентах-заглушках без ключей и модели, руководства по CI-gate, проверкам
  проекта, остановкам, evidence и дашборду. Справочный материал переехал из
  README в `docs/reference/`, README стал короткой витриной. Генератор сайта
  получил врезки (синтаксис GitHub alerts), подписи к картинкам, оглавление
  страницы, поиск, тёмную тему и навигацию «назад / дальше». Скриншоты
  пересобираются скриптом `docs/demo/screenshots.sh`.
- **`preflight_timeout`** — бюджет одной внешней команды preflight (опрос
  версии CLI-рантайма, `git`, `gh`) вынесен в конфигурацию проекта. Прежде это
  была константа в 5 секунд, что на холодном старте рантайма по умолчанию
  оставляло около двух секунд запаса и делало работоспособный рантайм
  неотличимым от отсутствующего. Значение по умолчанию — `60s` (PDD-01).
- **Точки внедрения в `pkg/preflight`** (`WithCommandRunner`, `WithLookPath`,
  `WithTimeout`): классификацию исходов теперь можно проверять извне пакета без
  порождения настоящих процессов.
- **Подписи релизных артефактов (cosign keyless).** Каждый архив релиза и
  `sha256sums.txt` подписываются через Sigstore в keyless-режиме по OIDC-токену
  GitHub Actions; рядом публикуется `<asset>.cosign.bundle` (подпись +
  сертификат + Rekor-proof). Ключ не хранится и не ротируется, сертификат
  привязан к `release.yaml@refs/tags/<tag>`. Перед публикацией подписи
  проверяются дважды: в job сборки и повторно в job публикации уже над
  скачанными артефактами, с проверкой того, что bundle есть у каждого ассета.
  Команда проверки — в README («Готовые бинарники и проверка подписи»), нужен
  cosign ≥ v2.4.2. `id-token: write` выдан только job сборки, `contents: write`
  — только job публикации (#101).

### Changed

- **Конфиг v5/v6 после ревью S02.** Ошибки перевода v5 помечены «(из
  required_sections/check v5)». Валидация v5 не строже прежней: пробелы по краям
  названий разделов нормализуются, повторы после обрезки схлопываются, а
  применимость правила к типу результата для v5 не проверяется. Поведение
  идущих этапов: `required_sections` теперь исполняется контроллером как гейт
  для любого этапа, который его объявил (раньше — только при `check: hard` и
  при ручной сдаче); события `check_*` несут `artifact_sha256`, а проверка,
  записанная для другого хеша результата, игнорируется. Добавлен тест
  конкурентного использования реестра `gatelib`.
- **Resume после остановки по бюджету больше не выдаёт бюджет неявно (B-86).**
  Обычный resume задачи, остановленной по бюджету задачи, новый бюджет не
  даёт — задача снова встаёт на паузу перед вызовом модели. Ещё один бюджет
  того же размера выдаётся только явным решением человека с причиной:
  `POST /api/runs/{runID}/resume` с `{"grant_budget_allowance": true,
  "reason": "..."}`, кнопка «Выдать бюджет и продолжить» или
  `ai-team run --resume <id> --grant-budget-allowance "<причина>"`. Выдача
  пишется в evidence (`budget_allowance_granted`) и в `run_resume_requested`
  (`budget_allowance_granted: true`, `reason`). Дневной бюджет не выдаётся и
  не сбрасывается никогда.

- **Релизный гейт равен CI.** `.github/workflows/release.yaml` больше не
  повторяет урезанный набор проверок (`go build`/`go vet`/`go test`), а
  вызывает `ci.yaml` как reusable workflow против точного коммита тега — то
  есть gofmt, `go mod verify`, coverage-гейт с per-package floors, `-race`,
  e2e, фронтенд (build + сверка встроенного `web/dist` + lint + test + audit),
  govulncheck и строгую OpenSpec-валидацию. Заодно `go build` в CI расширен с
  `./cmd/ai-team` до `./...`. Текст release notes приведён в соответствие с
  тем, что действительно прогоняется (#102).

### Fixed

- **Jira и уведомления: доработки после ревью (BL-28, BL-29, BL-34).**
  Если курсор интеграции в SQLite не читается или не записывается, Jira и
  уведомления в этом запуске не включаются, вместо повторной рассылки всей
  истории. Комментарий Jira несёт маркер попытки и не публикуется повторно
  после сбоя; ошибки транспорта Jira пишутся в `integration_error` только
  классом, без URL и заголовков. Ссылка `/browse/app-12` и порт `:443`
  нормализуются. Для `smtp://` к не-loopback хосту STARTTLS обязателен.
  Редирект webhook на другой порт или на `http` отклоняется. Захват доставки
  принадлежит владельцу (токен), `integration_error` о сбое канала пишется
  один раз на пару «канал — событие», старые записи журнала доставок
  удаляются через 30 дней. Второй Ctrl-C прерывает досылку уведомлений в
  `scheduler-worker`.

- **Run без секции `budget` больше не безграничен по времени.** Заявленный
  канонический дефолт `24h` существовал только как строка для диагностики:
  `EffectiveMaxWallTime` возвращала нулевую длительность, а пайплайн вооружал
  таймер лишь при положительном значении — то есть конфиг без `budget` давал
  run без верхней границы вообще, удерживающий workspace lock и
  candidate-worktree сколь угодно долго. Теперь дефолт разбирается в
  длительность, таймер вооружается всегда, а непарсящееся значение даёт
  дефолт, а не отсутствие лимита (#143).
- **`stage_timeout` получил дефолт на уровне кода (`30m`).** Прежде значение
  писал только `ai-team init`; конфиг, написанный руками, шёл и без бюджета
  стадии, и без бюджета run'а. Неположительный `timeout` теперь отвергается,
  а не трактуется как «без таймаута» (#143).
- **Журнал событий привязан к своему прогону (QS-13).** Корень hash-chain
  событий больше не общая константа, а значение, выведенное из `run_id`
  прогона. Прежде цепочка доказывала только внутреннюю целостность лога, а
  принадлежность лога своему прогону держалась на одном сравнении полей: целый
  валидный `events.jsonl` другого прогона, перештампованный под чужой `run_id`
  и пересобранный от общего корня, проходил проверку целостности и принимался
  `ai-team run --resume` как собственная история прогона. Теперь принадлежность
  — часть самой цепочки (#163).
- `docs/demo/run-demo.sh` снова проходит все три сценария: JUnit-отчёт
  первого сценария больше не остаётся неотслеживаемым файлом и не блокирует
  второй.
- Нестабильность `make verify`: preflight-тест зависел от реального времени
  запуска процесса и падал под нагрузкой (PDD-01).
- **Три fail-open в сканере секретов** — механизме, который обязан быть
  fail-closed (QS-08, #159, #150). Правило `secret assignment` было
  регистрозависимым: `password=` ловился, `PASSWORD=`, `API_KEY=`, `Token:` —
  нет, то есть доминирующая форма в env-файлах, shell-export'ах и CI-логах
  проходила блокер насквозь. JSON крупнее 4 MiB не сканировался структурно
  вовсе, а вложенность глубже 16 обрывала разбор **всего** документа, из-за
  чего терялись и секреты, стоявшие после глубокого поддерева. Теперь ключи
  сопоставляются без учёта регистра, лимит на размер документа снят (обход
  стал линейным), а слишком глубокое поддерево пропускается точечно.
- **Непросканированное больше не исчезает.** Всё, что сканер не разобрал
  (глубокое поддерево, оборванная JSON-структура), попадает в отчёт как
  «не просканировано» — с причиной, строкой и путём файла; при включённом
  блокере такой участок останавливает экспорт наравне с находкой. Пустой
  список находок означает «секретов нет» только тогда, когда пуст и список
  непросканированного (QS-08).

### Breaking

- **Evidence schema 6 → 7.** Корень hash-chain событий выводится из `run_id`
  (QS-13), поэтому evidence, записанная бинарником до этого изменения, не
  проверяется новым. Это уже действующий контракт: `run.json`, attempt
  manifests и каждое событие сверяются со schema version на строгое равенство,
  миграции между версиями evidence в продукте нет и раньше не было — смена
  версии лишь делает отказ явным (`identity/schema mismatch`) вместо
  диагностики о сломанной цепочке. Незавершённые прогоны, начатые старым
  бинарником, после обновления не возобновляются: их нужно завершить старой
  версией либо начать заново. Уже проверенные bundle'ы остаются проверяемыми
  бинарником той версии, которой они были выпущены.

- **Откат после появления `stage_entered_at` невозможен без миграции.**
  Lifecycle state-файлы `.ai-team/state/runs/<run_id>.json` теперь хранят
  `stage_entered_at` (момент входа в текущий этап), и контроллер сравнивает
  его при каждом сохранении checkpoint'а. Бинарник предыдущей версии читает
  state-файлы строго, без неизвестных полей, поэтому после обновления не
  загрузит ни один прогон, затронутый новой версией. Откатиться на старую
  версию можно только после того, как все такие прогоны завершены, либо
  удалив поле `stage_entered_at` из их state-файлов вручную.

*Дата версии vs дата публикации:* строка выше — **version date** (дата
release-коммита тега `v0.1.0`, 2026-08-24). Сама **публикация** на GitHub
Releases произошла позже (в конце августа 2026 г.), поэтому при сравнении с
метаданными GitHub учитывайте, что «дата релиза» в Changelog относится к
содержимому версии (коммиту тега), а не к моменту публикации Release-страницы.

### Added

- Строгий workflow-контроллер AI-агентов: план → детерминированные проверки →
  enforcement вердиктов → delivery, контролируемая человеком доставка через
  SHA-256 approval канонического плана (`--approve-plan`).
- Graph schema v4: доменные state/outcome типы и чистые переходы в `pkg/workflow`.

- Scheduler для оркестрации задач разработки (dev-task-workflow) в ручном
  и автоматическом режиме.
- CLI: `ai-team version`, exit-коды run (OK/FAILED/BLOCKED/USER_STOPPED),
  E2E-тесты на mock-opencode.
