1. Резюме: что это и зачем

ai-team — локальный control plane (Go CLI + веб-дашборд) для решения IT-задач цепочкой AI-агентов. LLM-агенты создают содержательные артефакты — proposal, design, код, тесты, ревью — и предлагают вердикты. Но переходы между этапами, проверки, mutation scopes, evidence (неизменяемые доказательства) и итоговую доставку в git исполняет детерминированный Go-контроллер, а не LLM.

Ключевая идея одной фразой: модель думает — код решает. Ни один вердикт LLM не является фактом: фактами (какой diff, какие тесты реально запускались, какой exit code, какие байты закоммичены) владеет только контроллер.

Статус позиционирования (честная самооценка проекта)

  • Подходит сейчас: доверенный локальный репозиторий одного разработчика/маленькой команды; агент и проверки работают с правами вашего OS-пользователя.
  • Не подходит (пока): недоверенный/сторонний код, секреты рядом с агентом, production delivery без человека. Это не hermetic sandbox — OS-level изоляции нет (открытый риск C-01 из аудита).
  • Typed test-адаптер реализован только для Go; delivery для Rust/Python/Node заблокирован до появления адаптеров.

2. Проблема и ценность

Какую проблему решает

Обычный «AI-кодинг» сегодня — это агент с терминалом, который сам себе хозяин: сам пишет, сам «проверяет», сам коммитит. Проблемы этого подхода:

  • False green: агент заявляет «тесты прошли», хотя ничего не исполнялось или исполнилось не то.
  • Нет ответственности за границы этапов: непонятно, кто одобрил переход от дизайна к коду.
  • Недоверие к доставке: агенту страшно давать права на git push.
  • Нулевая наблюдаемость: что происходило в прогоне, сколько это стоило, где застряло — неизвестно.

ai-team отвечает на это архитектурно: контроллер владеет переходами, гейтами, проверками и side effects, а каждое человеческое решение фиксируется как типизированный approval по точному SHA-256 предмета.

Ценность по ролям пользователя

3.2 Веб-версия (dashboard)

3.3 MCP — статус: план, не реализовано

идея Read-only MCP-сервер — план plans/mcp-server.md (№14 в приоритете). Замысел: внешний агент (Claude Desktop, другая сессия кодинг-агента, любой MCP-клиент) узнаёт состояние ai-team — раны, этапы, ожидающие решения, результаты проверок. Управляющих операций нет вообще — инвариант «конвейер управляет только человеком через web/CLI» сохраняется на уровне контракта.

Черновик инструментов: list_runs, get_run, get_timeline, list_pending_approvals, get_artifact/get_report (bounded, без секретов). Транспорт: stdio первым. Данные переиспользуют read-API слоя web — «другой транспорт к тем же данным, не новая логика». Сегодня единственный способ дать внешнему агенту контекст — файлы .ai-team/runs/<id>/ на свой страх и риск.

4. Конвейер и роли агентов

4.1 Конвейер по умолчанию

analyst → architect → coder → reviewer → tester → verifier → deployer

Это не жёсткий порядок в коде, а дефолтный граф в конфиге schema v4: вершины объявляются в pipeline:, маршрут и approval-политики — в workflow.edges. Реально AI-driven ролей — шесть; deployer никогда не вызывает LLM.

Tester только пишет тесты; фактический typed execution делает контроллер. Артефакты между агентами заворачиваются как untrusted data в промптах (защита от prompt injection, PR #22).

4.3 Человеческие роли (RBAC)

Approvals привязаны не к стадиям, а к рёбрам графа и требуют роль: product_owner, architect, developer, reviewer, qa, security, release_manager. Политика quorum: any|all — достаточно одной роли или нужны все. В вебе: Product Owner и Architect могут создавать runs; Product Owner и Release Manager — отменять; approval принимается только ролью, которая есть и у principal, и в policy ребра.

5. Фичи: подробный разбор

Формат каждой фичи: что это → как работает → как настроить → бизнес-ценность. Статус-теги: готово в master, частично, открытые вопросы, план.

F1. Инициализация проекта — ai-team init готово

  • Как работает: создаёт строгий config schema v4, каталоги artifacts/reports/logs. Исключает .ai-team/ через .git/info/exclude — первый запуск гарантированно не ломается на baseline-guard «чистого workspace» (историческая находка Н-1 исправлена).
  • Настройка: --target dir, --write-gitignore, --profile fast|standard|regulated (см. F15). Детектирует go.mod и сразу прописывает required check go-test-json. Для стеков без адаптера — warning, delivery запрещён до ручной настройки check.
  • Ценность: time-to-first-run близок к нулю; идемпотентен (повторный init не перезаписывает config).

F2. Оркестрация конвейера агентов готово

  • Как работает: RunEngine исполняет граф: на каждом этапе вызывает opencode с промптом агента и typed inputs предыдущих артефактов; парсит verdict; запускает deterministic checks; проверяет mutation scope; пишет evidence; вычисляет исход (outcome) и идёт по соответствующему ребру графа.
  • Loopback (петля review→revise): негативный вердикт reviewer создаёт ребро назад к coder. Работает и в non-TTY: run переходит в waiting_for_approval с действиями return_to_coder / override_approve / reject — после решения человека --resume продолжает тот же run. Каждое обратное ребро создаёт новые attempt IDs и инвалидирует downstream-ветку. Ограничение — max_visits.
  • Настройка: весь маршрут — в workflow: конфига; дефолт — 7 ролей, профили — см. F15.
  • Ценность: автоматический цикл «код → ревью → доработка» без потери контроля: петлю санкционирует человек, а не модель.

F3. Workflow graph v4 готово

  • Как работает: schema v4 разделяет определения узлов (pipeline) и маршрут (workflow): entry, уникальные рёбра (from, outcome), terminal targets, edge approval policies, max_visits. Компилятор до первого LLM-вызова проверяет references, достижимость, terminal path и циклы (каждый узел цикла обязан иметь положительный max_visits). Выбранное ребро пишется событием transition_selected в evidence и WebSocket projection; resolved workflow.json — immutable snapshot фактически исполненного графа.
  • Fail-closed валидация: unknown/duplicate поля YAML, несколько документов, неоднозначные edges, недостижимые узлы, неограниченные циклы — отклоняются до запуска. Поддерживается только schema v4; v1–v3 отклоняются с подсказкой о миграции.
  • Ценность: процесс — данные, а не код: кастомный pipeline собирается YAML-ом без форка движка; невалидный процесс невозможно запустить.

F4. Human approvals + RBAC готово

  • Как работает: каждое non-terminal ребро графа требует typed approval: subject = SHA-256 конкретного предмета (план перехода, design, candidate, delivery plan). Решение — отдельная сущность в .ai-team/state/approvals/<run_id>/<approval_id>.json: actor, role, action, comment, timestamp. Non-TTY запуск переводит run в waiting_for_approval (никогда — неявное согласие). Stale/conflicting решение отклоняется: если предмет изменился, старый hash не подходит. Конкурентные CLI/web-решения сериализуются in-process mutex + flock на каталоге run.
  • Настройка: на каждом ребре — roles, quorum: any|all, actions (action→target map, включая $stop). --approve-gates — совместимый transport для скриптов: на каждой достигнутой точке создаёт те же exact request/decision, не обходя модель.
  • Ценность: аудируемое «кто, в какой роли и по какому именно предмету разрешил»; защита от одобрения устаревшего материала; одинаково работает через терминал, веб и API.

F5. Delivery: canonical delivery plan + двухфазное подтверждение готово

  • Как работает: deployer — не исполнитель команд LLM. Контроллер строит строгий JSON-план только из файлов, изменённых в рамках текущего run, затем проверяет 7 условий: (1) review APPROVED, (2) test-report PASS, (3) verifier APPROVED, (4) успешный required typed test check, (5) approval точного SHA-256 плана ролью release_manager, (6) пустой staged index, (7) защита базовой ветки. Только потом — exact-file commit, push, PR через gh. До commit повторно сверяются staged paths/blob SHA/modes, после — parent/tree/blobs/modes. Crash-safe recovery: если процесс убит между commit и push, retry принимает существующий commit только после полной пересверки — дублей не будет.
  • Как использовать: первый прогон доходит до deployer и останавливается (exit 3), печатая план + SHA-256; второй запуск — --resume <run_id> --approve-plan <sha256> (или решение из веба, потом просто resume). Изменился план — старый SHA не подходит ни одним путём.
  • Ценность: главный страх «доверить агенту push» снят архитектурно: подтверждение одноразовое, привязано к конкретному набору байт; всё доставленное = ровно то, что прошло review/tests/verifier.

F6. Candidate worktree (изоляция кандидата) готово

  • Как работает: для Git-проекта контроллер создаёт отдельный detached worktree от exact baseline commit. Все AI-этапы, checks, review и delivery работают внутри candidate; ветка, HEAD и live checkout не меняются. Metadata с base commit/tree и workspace hash хранится и проверяется при resume. Human approval содержит exact candidate hash — после любой мутации решение становится stale.
  • Ценность: live workspace никогда не повреждается экспериментами агента; «проверено то, что доставлено» становится доказуемым; retry/resume опираются на неизменяемую идентичность.

F7. Deterministic checks готово Go-only адаптер

  • Как работает: required/optional проверки запускаются argv-массивом без shell, с confined working dir, timeout, process-group kill, bounded stdout/stderr, tool path/version fingerprint, exit code, timestamps. Падение required check переопределяет любой позитивный LLM verdict. Отсутствующий optional tool виден как skipped/warning и не маскируется под pass. Typed adapter go-test-json парсит JSON Go-тестов и доказывает discovered/passed cases; zero-tests = failure.
  • Настройка: checks задаются в def.yaml агента и per-stage в конфиге; policy: required/optional; классы unit/integration.
  • Ценность: «тесты зелёные» означает «контроллер реально исполнил тесты и распарсил результат», а не «LLM так сказал».

F8. Mutation scopes + baseline guard готово

  • Как работает: каждый агент объявляет разрешение на изменение файлов (glob с */?/**, запрет выхода за workspace, нельзя трогать .git/.ai-team). Baseline фиксируется перед попыткой; изменения вне scope проваливают guard. Read-only этап с любой source mutation падает; require_diff без фактической delta падает. Delivery получает только нормализованные разрешённые пути.
  • Ценность: tester физически не может «подправить продовый код», analyst — код вообще; guard детективный, но связка с candidate worktree делает последствия откатываемыми.

F9. Verdict-контракт + BLOCKED готово

  • Как работает: reviewer/tester/verifier обязаны записать ровно один канонический маркер (**Verdict:** APPROVED / CHANGES_REQUESTED / REJECTED, **Result:** PASS/FAIL) в свой отчёт. Missing/unknown/duplicate маркер — ошибка контроллера, fail-closed (парсер line-anchored; покрыт contract-тестом, связывающим инструкцию в промпте с парсером). Любой этап может сигнализировать BLOCKED через status-файл с обязательной причиной — pipeline останавливается с exit 2.
  • Ценность: вердикт — машиночитаемый сигнал, а не свободный текст; модель не может «рекомендательно» пройти этап.

F10. Evidence, tamper-evident журнал, ai-team verify готово внешний якорь — план

  • Как работает: живые артефакты в .ai-team/artifacts/{feature}/, доказательство — immutable layout .ai-team/runs/{run_id}/: run.json (schema v6: snapshots config/workflow, SHA-256 бинарника контроллера, Go/VCS identity), events.jsonl (append-only hash chain, проверяется перед каждым append — splice/reorder чужой цепочки обнаруживается), attempts/{id}/manifest.json (execution/decision/outcome, blocker, SHA-256/provenance артефактов, checks, mutations, delivery result), logs, reports. Публикация attempt атомарна. Mutable execution checkpoint отдельно в state/runs; resume сохраняет исходный run_id, добавляет run_resumed.
  • Новое (PR #43): при terminal-завершении создаётся anchor.json — отпечаток всего журнала (кол-во событий, хеш последнего события, дайджест манифестов). ai-team verify <run_id> проигрывает журнал, пересчитывает и сверяет с якорем. Ловит: случайную порчу, усечение, подмену события, полную пересборку цепочки с новыми хешами (без обновления якоря).
  • Ценность: спор «агент этого не делал» решается командой, а не разбором файлов на глаз; фундамент для внешних якорей/подписей (план event-log-anchoring: вопрос «владелец файлов может подделать оба файла» остаётся открытым — см. раздел открытых вопросов).

F11. Метрики прогона: usage envelope + ai-team usage готово токены unknown

  • Как работает: каждый run автоматически собирает usage.json: длительность всего прогона и каждого этапа, попытки по агентам, количество loopbacks, итоговый исход. ai-team usage <run_id> печатает таблицу. Токены пока TokensUnknown — CLI-хосты не отдают их в интерфейсе (ждёт adapters-layer).
  • Ценность: видно, какой этап самый дорогой, растут ли переделки, сколько живёт типовая фича. Фундамент для model-routing, evals-регрессий и бюджетных лимитов.

F12. Retention и уборка: ai-team gc готово дефолты обсуждаются

  • Как работает: чистит candidate worktrees завершённых ранов (и сироты), mutable state старых ранов; immutable runs — только с явным --prune-runs, только terminal и старше срока, последние N всегда остаются. Активный run не трогает (workspace lock). --dry-run показывает план в байтах. Дефолты: --older-than 720h, --keep-last 20.
  • Ценность: предсказуемый диск при постоянной работе; безопасность по умолчанию (без флагов удаляется только заведомо лишнее).

F13. Workflow profiles: fast / standard / regulated готово решения по дизайну

  • Как работает: ai-team init --profile .... fast — 5 этапов вместо 7: отдельного verifier нет, reviewer совмещает ревью+верификацию (для чего init кладёт project-local override reviewer'а в .ai-team/agents/). standard — прежние 7 этапов. regulated — те же 7, ключевые переходы требуют согласия всех ролей (quorum all), повторные попытки ограничены 2.
  • Ключевой дизайн: профиль — способ сгенерировать явный конфиг, а не скрытый механизм рантайма; после init на диске обычный schema v4, читаемый и версонируемый.
  • Ценность: дефолт требовал ~6 человеческих решений на мелкую задачу — люди бросали инструмент или выключали гарантии целиком. Один флаг: личные задачи → fast, команда → standard, критичные изменения → regulated.

F14. Evals (advisory LLM-оценка артефактов) готово нет калиброванного корпуса

  • Как работает: ai-team eval гоняет независимые LLM-оценки артефакта в изолированном временном каталоге, сохраняет samples/median/mean/stddev в .ai-team/evals/. Явно advisory: нормативные гарантии дают только deterministic checks. Hard suite failures возвращают error.
  • Ценность: сигнал качества промптов/артефактов; полноценным benchmark станет после golden corpus и human-labelled калибровки (план evals-harness).

F15…F16. Веб-дашборд и облачный режим готово

Разобраны в разделе 3 (поверхности). Дополнительно про cloud/self-hosted режим:

  • Auth: два режима. Zero-config loopback (по умолчанию; случайная HttpOnly SameSite session-cookie + X-CSRF-Token поверх fixed Host/Origin policy) и cloud mode: общий secret ≥32 байт (AI_TEAM_AUTH_SECRET), auth-token выпускает versioned HMAC token с immutable actor ID, ролями и bounded expiry; token обменивается на персональную browser-session и нигде не хранится. RBAC policies на start/cancel/approve. TLS — снаружи на ingress/reverse proxy.
  • Worker isolation: --worker-command — HTTP-процесс перестаёт исполнять runs сам и сериализует strict job schema v1 через stdin subprocess-у того же бинарника (reference launcher; в production — disposable container/job с mount и лимитами инфраструктуры).
  • Scheduler (несколько workers): --scheduler-db превращает control plane в постановщик очереди: persistent SQLite queue, idempotent active identity, bounded lease с heartbeat, global/per-target concurrency, cancel через queue. После execution immutable run tree архивируется в SHA-256 CAS (content-addressed store) с проверяемым restore. SQLite/CAS — reference backends, заменяемые managed queue/object storage по тем же контрактам.
  • Preflight: перед созданием run dashboard показывает runtime preflight (OpenCode/version, model/provider, credential allow-list без значений, Git; для delivery — origin remote, gh, gh auth status). Тот же gate повторно применяется при Start — fail-closed.

F17. Layered agent registry (кастомизация агентов) готово

  • Как работает: резолюция слоями: project .ai-team/agents/ → каталоги из AI_TEAM_AGENT_PATH → user config → built-in. Невалидный override НЕ маскируется fallback-слоем — registry возвращает ошибку (осознанно: тихий fallback означал бы запуск не того кода). list показывает победивший источник и load failures.
  • Ценность: безопасная кастомизация под проект/команду без форка; предсказуемость «какой именно промпт исполнился».

F18. Безопасностные механизмы (сквозные) готово OS-sandbox нет

МеханизмЧто даёт

F19. Analyst question tool готово (interactive TTY)

  • Как работает: def.yaml агента может объявить ask_questions — тогда в интерактивном TTY аналитику разрешён инструмент question (уточняющие вопросы пользователю вместо немедленного BLOCKED). Non-TTY — fail-closed deny (иначе вопрос завис бы до таймаута).
  • Ценность: снял внутреннее противоречие «промпт требует задавать вопросы, runtime денял инструмент» — качество требований растёт там, где есть человек у терминала.

F20. Отчёты и уведомления (периферия) базово упрощение запланировано

  • HTML-отчёты по завершённым run (pkg/report), консольный UI с цветом/прогрессом (pkg/ui), notifier chain (pkg/notifier). По scope-review это дублирующие поверхности (~1670 строк), запланированы к срезке после того, как фронт научится рисовать чеки; notifiers как подписка Slack/email — отдельный план №13.

  entry: analyst
  max_visits: {coder: 3, reviewer: 3, tester: 3, verifier: 3}

effort: medium
stage_timeout: 30m

7. Сценарии использования

Сценарий A. Быстрый старт (личная задача, fast-профиль)

cd /my-project
ai-team init --profile fast

  --approve-gates                 # фаза 1: до deployer, exit 3, печать plan + SHA256
ai-team run --resume <run_id> \
  --approve-gates --approve-plan <sha256>   # фаза 2: commit/push/PR

Сценарий B. Командный процесс (standard, решения из веба)

ai-team web                       # дашборд на 127.0.0.1:8080
# создать run из UI; на каждом переходе — карточка approval:
# посмотреть diff/план → решить (return_to_coder / approve / reject)
# CLI-альтернатива решения: ai-team decision --run ... --approval ... --role ... --subject ...
ai-team run --resume <run_id>     # после записи решения

Сценарий C. Cloud/self-hosted с несколькими воркерами

export AI_TEAM_AUTH_SECRET='<случайный секрет ≥32 байт>'
ai-team auth-token --actor architect-1 --roles architect,reviewer --ttl 1h
ai-team web --host 0.0.0.0 --worker-command /opt/ai-team/bin/ai-team \
  --scheduler-db .ai-team/scheduler.db
ai-team scheduler-worker --scheduler-db .ai-team/scheduler.db \
  --artifact-store .ai-team/cloud-artifacts --worker-command /opt/ai-team/bin/ai-team

TLS завершать на внешнем ingress/reverse proxy. Reference backends (SQLite queue + local CAS) заменяются managed-инфраструктурой по тем же контрактам.

Сценарий D. Наблюдаемость и гигиена

ai-team list                      # какие агенты и откуда
ai-team usage <run_id>            # время/попытки по этапам
ai-team verify <run_id>           # целостность evidence
ai-team gc --dry-run              # что можно почистить
ai-team gc                        # убрать worktrees и устаревший state

8. Разработка самого ai-team

  • Spec-first через OpenSpec: любая поведенческая фича проходит цикл explore → propose → design → specs → tasks → apply → archive с gate-rule («следующий артефакт — только после явного ок»). make specs — строгая валидация всех капабилити (62 шт.).
  • Make-таргеты: build, test, test-coverage (gate 60% агрегатно + per-package полы 50–75% с правилом «только повышать» — PR #38), test-e2e (subprocess-level сценарии на mock-opencode), verify (specs + mod verify + vet + govulncheck + race + frontend audit/lint/test/build + сверка встроенного dist с исходниками).
  • CI (8 jobs): build, specs, lint (gofmt+vet), unit-tests, race-tests, e2e-tests, frontend, security. После PR #38: actions запинены по commit SHA, least-privilege permissions.
  • E2E: e2etest/mock-opencode.sh — mock LLM-runtime для прогонов без платных вызовов; доказывается вплоть до реального subprocess environment.
  • Процесс самого автора: CLAUDE.md + .opencode/commands (opsx-цикл), dev-task-* skills для работы с задачами.

12. Ограничения и подводные камни

  • Trusted-local only: нет OS-sandbox. Недоверенный код — только во внешнем container/VM.
  • Go-only delivery: другие стеки не доходят до delivery (нет typed адаптеров). Init честно предупреждает.
  • Токены не меряются: usage.json содержит TokensUnknown до появления adapters-layer.
  • README на master отстаёт от кода: новые команды usage/verify/gc и init --profile описаны в PR-описаниях и планах, но ещё не попали в README (мастер = 2e48ecc). При написании документации это учесть.
  • MCP нет: только план; внешним агентам доступен лишь сырой .ai-team/runs/.
  • Windows/Plan9: кросс-компиляция есть, runtime CI только Linux; поведение не-Unix платформ формально не формализовано (план windows-support).
  • Branch protection: по аудиту от 07-23 правила на master не требовали ни проверок, ни ревью — стоит проверить актуальное состояние.
  • Спеки: 62 капабилити, часть с историческим мусором; pruning запланирован (30–31).
  • Стоимость человеческих решений: standard-профиль требует ~6 approvals на фичу — для одиночки выбирать fast.
  • Anchor и владелец файлов: verify ловит порчу/пересборку журнала, но не сговор владельца файлов (нужен внешний якорь).
