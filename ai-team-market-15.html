ЧАСТЬ A · Auto-Company: переходы, контроль «кто что сделал», что заимствовать

A.0 TL;DR по части A

Никаких «переходов между уровнями» в коде у Auto-Company нет. Всё управление — это: backup → run engine → validate skeleton → restore on fail. «Уровни» (brainstorm→validate→ship) существуют только как проза в PROMPT.md и держатся на послушности модели. Контроль «кто что сделал» реализован самым грубым способом — файлы в папках + один Markdown-файл consensus.md, без immutable evidence, без атрибуции к агенту, без крипто-якоря.

Вывод для нас: как реализован контроль — у Auto-Company хуже, чем у нас (это берётся обеими руками из ai-team). Но что именно оно оркестрирует (бизнес-цель, автономный 24/7 цикл, сопротивление «обсуждению ради обсуждения», персоны-мышление, мягкий ручной steering файлом) — это ценные примитивы, которых у нас нет. Ниже — честно по механизмам.

A.1 Как устроены «переходы» в auto-loop.sh

Единственный цикл — while true в scripts/core/auto-loop.sh (743 строки). Разберу жизненный цикл одного цикла (строки 630–743):

loop_count++
1. backup_consensus            # cp consensus.md consensus.md.bak
2. snapshot_gitignore          # cp .gitignore в mktemp
3. собрать FULL_PROMPT = PROMPT.md + guardrails + состояние consensus
4. run_engine_cycle "$FULL_PROMPT"  # claude -p ...  или  codex exec ...
5. echo OUTPUT > cycle-XXXX.log
6. cleanup_accidental_root_artifacts   # rm файлов '=*' и '口径说明*' (0 байт)
7. restore_gitignore_if_changed         # вернуть .gitignore, если мутировал
8. extract_cycle_metadata               # parse cost, type, type через jq
9. классификация: timed-out? exit!=0? validate_consensus?
   → OK / FAIL / SOFT_TIMEOUT
10. FAIL: restore_consensus (откат) + circuit breaker + usage-limit backoff
11. sleep LOOP_INTERVAL

Что это значит технически:

  • Состояние-батон: весь контекст между запусками — один файл memories/consensus.md. Новый процесс получает его через инъекцию в промпт («pre-loaded, do NOT re-read»). Фактически — это «память» агентессы, передаваемая строго файлом.
  • «Переход» между каким-то уровнями не является графом. Код не знает про brainstorm/validate/ship. Эти фазы — текст в PROMPT.md (Cycle 1/2/3+), и их соблюдение полностью на совести модели. Если модель «забудет» фазы — код этого не заметит. Это и есть слабое место: корректность процесса не кодифицирована, только подсказана.
  • Soft-timeout (умно!): если цикл убит по таймеру, но consensus.md успел измениться (cycle_soft_timeout=1), это НЕ считается ошибкой — прогресс сохранён. Хорошая идея.
  • Circuit breaker: 5 подряд ошибок → cooldown 300с; usage-limit → backoff 3600с. Это честные runtime-примитивы.

Чего тут НЕТ (и это важно сравнить с нами)

  • Нет никакого машинного подтверждения «сделано». Успех цикла = exit code 0 + валиден скелет consensus. Если модель пишет «я всё сделал» и ставит exit 0 — это успех. Никто не проверяет, что код исполняется/собран.
  • Нет атрибуции. Нет записи «какой агент создал этот diff/файл». Есть только папки docs/<role>/, куда агенты кладут свои «отчёты» — по договорённости в промпте, а не по контракту.
  • Нет неизменяемости/криптографии. consensus.md — обычный текст с .bak. Никакого hash-chain, якоря.
  • Валидация консенсуса — скелетная: только grep на # Auto Company Consensus, ## Next Action, ## Company State. Семантика не проверяется вообще.

A.2 Контроль «кто что сделал» — как это устроено и насколько честно

У Auto-Company НЕТ слоя, который бы связывал действие с агентом и проверял его. Есть три «механизма припоминания», все файловые:

МеханизмЧто хранитСилаСлабость
logs/cycle-XXXX.logсырой stdout каждого циклаполный выводтекст, нет структуры, ротируется (MAX_LOGS=200)
docs/<role>/«отчёты» ролей (по договорённости)читаемоне гарантировано кодом; роль может не писать
memories/consensus.mdитог/Next Actionбатон между цикламиодна точка, семантика не валидируется

Фактически: «кто что сделал» здесь не контролируется — только припоминается по логам. Если агент молча не записал отчёт, но записал код в projects/ — следов авторства нет. Это полный контраст с ai-team:

  • У нас каждый агент — отдельный процесс, который пишет в immutable run/attempt manifest.
  • События — append-only, хэш-цепочечные, с якорем (ai-team anchor) и проверкой (ai-team verify).
  • «Кто сделал» we фиксируем директорией agents/{role}/ и вердикт-контрактом с BLOCKED-протоколом. Спор «это он делал» закрывается проверяемо.
  • Переходы между стадиями (analyst→architect→coder→reviewer→tester→verifier→deployer) — граф в pkg/workflow с max_visits, loopback, enforcement вердиктов — то есть фазы реально существуют в коде, а не в прозе.
Вывод: по «кто что сделал» ai-team в разы сильнее. Auto-Company по-настоящему «не контролирует», а лишь «помнит в логге». Заимствовать тут нам — нечего (это скорее их бор).

A.3 Что РЕАЛЬНО заимствовать (технические примитивы, которых у нас нет)

Критично: берём именно механики, а не философию «модель сама решает». Вот честный список:

A.3.1 Soft-timeout с сохранением прогресса реально ценно

Идея: цикл/узел убит по таймеру, но если состояние продвинулось — это не ошибка (строки 690–707). У нас сейчас убийство по контексту — фатально (return error). Для длинных дорогих гейтов (analyst/architect/coder) это критично: модель может «успеть» записать план, но не «завершить». Стоит ввести «частичный успех, если есть неизменяемый след» — у нас есть evidence именно для этого.

A.3.2 Circuit breaker + usage-limit backoff заимствуемо

У Auto-Company: MAX_CONSECUTIVE_ERRORS=5 → cooldown; 429/billing/quota → длинный backoff. У нас есть kill по таймауту, но нет счётчика последовательных ошибок с остыванием и нет специальной обработки лимитов API/цены. Добавить: (а) падение на N подряд → пауза; (б) распознавание rate-limit/стоимости в ответе движка → backoff. Это дешёвое, но сильно повышает надёжность фоновых задач.

A.3.3 Gitignore/артефакт-гард полезно

Auto-Company делает снапшот .gitignore до цикла и восстанавливает его, если агент мутировал, плюс убирает случайные битые файлы (мальформированные redirect-артефакты). Это защита «метаданных репозитория» от агента. У нас есть scope-policy на пути мутаций, но защита именно мета-файлов (не связанных с задачей) — стоит усилить: снапшот до прогона, восстановление после.

A.3.4 «Обязан ship» / анти-бесконечное обсуждение перенос в граф

Авто-дисциплина из PROMPT.md: Cycle 3+ обязан выдать результат, а не рассуждать; повтор одного Next Action 2 цикла = «застрял». У нас в графе это частично есть — max_visits и rule «rejected → return_to_coder». Но нет бизнес-уровня «validate → GO/NO-GO → ship» и нет эвристики «то же самое действие 2 раза подряд = стоп». Можно добавить как edge-политику в workflow-граф: «N_identical_actions → escalate/fail».

A.3.5 Steering через файл (мягкий человеческий вход) спорно, но рассмотреть

У Auto-Company человек «рулит» правкой поля Next Action в consensus.md — без обязательных approval на каждом ребре. У нас жёсткий RBAC-approval на значимых переходах. Для профиля fast можно добавить «steer-файл»: оператор меняет поле, и контроллер учитывает его как необязательный вход, но при fast без подтверждения — при этом всё равно immutable evidence. Это снизит порог для соло-пользователя.

A.3.6 Персоны-мышление (ментальные модели) мягко заимствовать

У Auto-Company агенты — не «функциональные контракты», а «личности» (Munger-критик, Bezos-CEO). Плюс: качество решения растёт за счёт подражания мышлению роли. У нас роли сухие и функциональные. Но у нас роль = проверяемый контракт, это сильнее. Заимствовать точечно: добавить к reviewer «Reverse-Review по Munger» (список когнитивных ловушек) как опциональный чек-лист, не ломая контракт. Получим «роль + персона» без потери детерминизма.

ЧАСТЬ B · Рынок: категория, 15 инструментов, честный рейтинг

B.0 Как назвать класс — категория

Рынок называет это по-разному, консенсус (Delphi/Стэнфорд/вендоры) сейчас такой: общее — «agent orchestration» (координационный слой: декомпозиция, делегирование, роутинг, память, восстановление). Внутри выделяют подтипы, использующие «workflow/pipeline»:

  • Graph workflow — явный граф состояний (LangGraph, Google ADK).
  • Role-based teams (crew/company) — роли-личности, «команда» (CrewAI, MetaGPT, AutoGen).
  • Handoff-driven loop — лёгкий цикл «вызвал тул, решил дальше» (OpenAI Agents SDK, Smolagents).
  • Visual/low-code builder — визуальные воркфлоу (Dify, Langflow, n8n, Flowise).
  • Autonomous coding agent — агент «инженер», исполняющий доставку (OpenHands, Cline).

ai-team попадает сюда как… гибрид role-based + graph workflow с жёстким детерминированным контроллером и human-in-the-loop, ограниченный SDLC/доставкой кода. Ближайшие концептуальные кузены — MetaGPT (роли-«софт-компания», но без проверки/контроля) и Auto-Company (автономный цикл, но без контроля). Так и сформулируем нишу.

B.1 Метод оценки — критерии (честный набор)

Оцениваю не «кто лучше вообще», а по тому, что реально важно для инструмента типа «агентский orchestration для продуктивной/доверенной работы»:

  1. Популярность/экосистема — звёзды GitHub, downloads/mo, активность (сигнал доверия, но не качества).
  2. Модель оркестрации — граф / роли / handoff / low-code; выразительность и предсказуемость.
  3. Контроль исполнения (кто что сделал, verify) — насколько система реально проверяет действия агента.
  4. Human-in-the-loop — approvals, прерываемость, RTÉ-строгость.
  5. Состояние/память/durable execution — checkpointing, восстановление, наблюдаемость.
  6. Экосистема моделей/тулзов/MCP — провайдеры, интеграции.
  7. Кривая входа/документация — насколько быстро разобраться.
  8. Зрелость/риски/поддержка — статус (active/maintenance), лицензия, безопасность по умолчанию.

B.3 Индивидуальный разбор 15 инструментов

1. n8n · workflow automation с AI-нодами

⭐ ~190k · TypeScript · fair-code · низкий код, self-host/cloud, 400+ интеграций

Что умеет: визуальный конструктор пайплайнов: «когда X → вызов LLM → сделать Y + интеграции». Добавил нативные AI-ноды, агентские шаги, MCP-ноды. Огромная библиотека коннекторов (Slack, Gmail, БД, API).

Плюсы: минимальный порог входа; богатейшая интеграционная база; отличный self-host; визуальная отладка шагов.

Минусы: это не «контроль исполнения агента», а автоматизация шагов с LLM-нодами — предсказуемо, но не «агентно» в смысле сложных многоцикловых рассуждений; fair-code (есть закрытые Enterprise-части); нет детерминированной проверки результатов LLM.

2. AutoGPT · автономный general-агент

⭐ ~184k · Python · MIT · автономный цикл «цель→план→действие»

Что умеет: исторический пионер автономных агентов: сам ставит подзадачи, вызывает тулы, крутится до цели. Позже стал платформой/визуальными агентами.

Плюсы: знаковый бренд; большая база звёзд; сформировал жанр «autonomous». Отличный ориентир по UX-формату для «агентных» продуктов.

Минусы: звёзды на 90% исторические (основной всплеск 2023); реальная продуктизация не взлетела; качество «селф-планирования» слабое без интеграций; отсутствует проверка/доказательства действий; сейчас вторичен на фоне специализированных framework.

3. Langflow · визуальный builder агентов и RAG

⭐ ~145k · Python · (DataStax) · low-code визуальный граф

Что умеет: drag-and-drop построение агентных и RAG-пайплайнов, экспорт в API/MCP-сервер, много интеграций.

Плюсы: быстрое прототипирование без кода; RAG-first; DataStax-бэк; разворачивается self-host.

Минусы: визуально сложные воркфлоу загромождаются; меньше «контроля выполнения» чем у графа-кода; звёзды раздуты распространённостью UI-продуктов; enterprise-глубина хуже LangGraph.

4. Dify · low-code AI-платформа

⭐ ~144k · Python/TS · активен · workflow + RAG + агенты, cloud/VPC/self-host, SOC2 enterprise

Что умеет: визуальный оркестратор: LLM-apps, RAG-pipelines, агентный режим, инструменты, деплой.

Плюсы: самый тираж; enterprise-режим с SOC2; полный стек продуктовых приложений; команда-не-разработчики могут.

Минусы: это платформа «приложение поверх LLM», не низкоуровневый контроль агентов; гибкость ниже кодовых framework; нет детерминированной верификации действий; vendor-lock на платформу.

5. MetaGPT · «AI software company» (ролевые SOP)

⭐ ~70k · Python · MIT · роли: PM, архитектор, инженер, QA; лозунг Code = SOP(Team)

Что умеет: из одной строки требований генерирует PRD → архитектуру → дизайн данных/API → код → тесты. Роль-специфичные промпты; структурированный обмен сообщениями (SOP). Есть Data Interpreter.

Плюсы: наиболее близкий к ai-team по концепции (ролевая «софт-компания»); продуцирует документы-артефакты; исследовательская база (ICLR papers) хорошая.

Минусы: активность сошла на нет (last commit ~2025, no releases за ~17 мес); нет детерминированного контроля/верификации — код «доверяется»; качество генерируемого кода неровное; длина Python 3.9–3.11; это демо-research, не production-контроллер.

Как сравнивать с ai-team: у ai-team та же ролевая идея, но доведённая до контролируемого production: у нас фазы исполняются контроллером, а не «на веру»; у MetaGPT фаз нет enforcement — что и делает его уязвимым.

6. OpenHands (ex-OpenDevin) · автономный coding агент

⭐ ~85k · (TS+Python) · MIT · «AI software engineer»

Что умеет: агент сам исследует репо, пишет код, запускает команды, делает PR. Sandboxed execution (docker), интерфейс-IDE/CLI/SDK, плагины.

Плюсы: реальный автономный delivery; sandbox-изоляция исполнения (этого не хватает ai-team!); тесты/бенчмарки (SWE-bench); активное ядро.

Минусы: один агент верхнего уровня (нет богатой ролевой структуры как у нас/MetaGPT); контроль = «сделай PR» без жёстких immutable-evidence гейтов; надёжность зависит от модели; no детерминированных проверок паттернов.

Как сравнивать с ai-team: у него — то, чего у нас нет: sandboxed-исполнение кода и «агент-инженер» для реального внешнего мира. У нас — то, чего нет у него: детерминированные гейты, immutable evidence, approvals.

7. AutoGen / Microsoft Agent Framework

⭐ ~58k (AutoGen) · MIT/CC · AutoGen в maintenance → MAF 1.x

Что умеет: многоагентная conversation-оркестрация (дебаты, консенсус, GroupChat, инструменты). MAF 1.x = слияние AutoGen+Semantic Kernel, Python+.NET, durable execution, human-in-the-loop approvals на уровне инструментов.

Плюсы: концептуальный вклад (conversation-first); инструментальные approvals (human-in-the-loop); большой enterprise-путь.

Минусы: AutoGen официально в maintenance (новые проекты не стоит) — фрагментация (AG2 форк, MAF); исторические звёзды не отражают текущую силу; сложность/порог у MAF.

8. CrewAI · ролевые «команды»

⭐ ~52k · Python · MIT · 5.2M downloads/mo · активен 1.x

Что умеет: роли-агенты (role, goal, backstory), задачи, Flows (граф), компиляция команд. Быстрейший прототип «команды экспертов».

Плюсы: минимальный код до рабочего multi-agent; огромная популярность; Flows добавляют контроль над последовательностью.

Минусы: жалобы на зрелость (нет прозрачной observability, непонятно какие промпты идут в LLM, потеря контроля на абстракциях); CrewAI использует в ~3 раза больше токенов/латентности на простых задачах (бенчмарки); нет детерминированной проверки результатов; абстракции мешают переносить в production-графы.

9. LlamaIndex Workflows · event-driven агент-workflows

⭐ ~49k · Python · MIT · RAG-first + агентные in-process-schema workflows

Что умеет: легковесные event-driven workflow (шаги-функции, события, стейт), Agent-Workflows, глубокая интеграция с данными/RAG, наблюдаемость/эвалы.

Плюсы: отличный RAG/данные-first; Python-native, типизированные шаги; быстрее для RAG-центричных задач.

Минусы: не «полный оркестратор» для доставки кода/системных действий; фокус на данные, а не на human-in-the-loop/approvals; проигрывает по долгоживущему durable graph (LangGraph).

10. Agno (ex-Phidata) · агент-платформа

⭐ ~40k · Python · MIT · активен

Что умеет: лёгкий, model-agnostic; агенты, teams, memory, MCP-тулы; встроенный control plane для деплоя; агенты для ботов/knowledge-base.

Плюсы: быстрый старт; типобезопасность; хороший выбор для реальных ботов и знаний; активно развивается.

Минусы: меньше «тяжёлого» графа/durability чем LangGraph; фокус на разговорные/бот-сценарии, не на доставку/верификацию; экосистема меньше чем LangChain/CrewAI.

11. LangGraph · graph state machine (production default)

⭐ ~33k · Python/JS/TS · MIT · 34.5M downloads/mo · активен 1.x

Что умеет: явный directed graph, conditional edges, циклы/retries, state + checkpointing, time-travel отладка, durable execution, human-in-the-loop (interrupt), MCP-интеграции, LangSmith observability.

Плюсы: самый production-внедряемый фреймворк (Klarna, Replit, Elastic, Cisco, Uber, LinkedIn, BlackRock, JPMorgan); лучшая предсказуемость/транспарентность переходов; мощный HITL; огромное комьюнити.

Минусы: крутая кривая входа (низкоуровневый, много кода); «контроль» — это управление графом, но не детерминированная проверка того, что агент сделал (верификация делегируется LangSmith/эвалам, а не жёстким гейтам); требует Python/JS.

Как сравнивать с ai-team: LangGraph даёт гибкую graph-оркестрацию (шире нашего SDLC-графа), но не гарантирует, что результат доставлен проверяемо — это решение оставляется разработчику. Где ai-team реально сильнее — в обязательном, контроллер-подвластном исполнении и immutable evidence.

12. Semantic Kernel · enterprise agent SDK (.NET)

⭐ ~27k · C#/Python · MIT · активен

Что умеет: интеграция LLM в .NET-приложения; агенты, планирование, инструменты, human-in-the-loop на уровне вызовов тулов.

Плюсы: зрелая enterprise-интеграция для C#; строгие типы; подход «embedded agents» в корпоративных приложениях.

Минусы: Microsoft теперь направляет основной фокус на Agent Framework; niшa (C#); не «оркестратор-платформа», а SDK; меньше общего охвата multi-agent.

13. OpenAI Agents SDK (ex-Swarm)

⭐ ~26k · Python · 10.3M downloads/mo · 0.x

Что умеет: лёгкий agent loop, handoffs (передача управления между агентами), guardrails, встроенный tracing, MCP-тулы.

Плюсы: минимальный оверхед, максимальная гибкость; огромные downloads; простой API; отличные трассировки.

Минусы: легковесен: нет durable execution/состояния/восстановления как в LangGraph; меньше предсказуемость на масштабе; привязка к OpenAI-стеку (хотя provider-agnostic заявлен); «голый» цикл — тяжело поддерживать сложные уставы.

14. Haystack · production LLM-pipelines

⭐ ~25k · Python · Apache-2.0 · активен

Что умеет: компонентные пайплайны, конвейеры с тестируемостью, агенты, глубокая разработка поиска/RAG, контроль контекста.

Плюсы: максимальный контроль разработчика; production-ориентирован; хорошие пайплайны RAG/поиска; чистая архитектура.

Минусы: сложнее старт; фокус больше на поиск/RAG, чем на «swarm-оркестрацию» с HITL; меньше широкого multi-agent-хлус базового.

15. ai-team (наш проект) — критический разбор

⭐ 0 (без публичной активности) · Go · Apache-2.0 · v0.1.0 · соло-автор · 45 PR, 3 аудита, детерминированный контроллер

Что умеет: роль−+граф SDLC (analyst→architect→coder→reviewer→tester→verifier→deployer) с контроллером-владельцем исполнения. Детерминированные checks (Go-test adapter + command, без shell), immutable evidence (run/attempt manifests, hash-chain, anchor+verify), approvals с RBAC и точным SHA-256, scope-политика мутаций, safeio no-follow, process-group kill, crash-safe доставка (7 гейтов), web-дашборд (Go+SQLite+React+WebSocket), cloud/scheduler/worker, CAS-артефакты.

СИЛЬНОЕ (честно, где мы уникальны):

  • Контроллер-владеет исполнением: side effects (checks + доставка + evidence) у нас делает код, а не модель. В этом списке так не делает ни один инструмент.
  • Immutable доказательная база (hash-chain + anchor + verify): проблема «кто что сделал» решается проверяемо. Конкуренты её либо не решают (MetaGPT, Auto-Company, CrewAI), либо оставляют разработчику (LangGraph/Smith).
  • Детерминированная верификация, а не «самоотчёт модели»: verdict-контракт, BLOCKED-протокол, Go-test adapter.
  • Human-in-the-loop с точностью до байта: одобрение конкретного SHA-256 плана — сильнее, чем мягкие «approve tool» у MAF/CrewAI.

СЛАБОЕ (честно, где плохо):

  • Тотальный ноль экосистемы/доверия рынка: 0 звёзд, 0 пользователей, соло-автор. Для «позиции на рынке» это решающий минус на сегодня: любой популярный конкурент масштабнее и проверен чужими проектами.
  • Очень узкий скоуп: только локальный trusted-repo + Git/GitHub delivery, Go-only checks. Нет MCP (лишь план), нет мульти-провайдеров LLM, нет внешнего мира (деплой, маркетинг).
  • Тяжёлые гейты: ~6 approvals на фичу — дорого для соло/скорости; нет профиля «fast» с мягким steering (мы только обсуждаем).
  • Это не «фреймворк», а монолит-CLI/контроллер: не встраивается в чужие приложения как библиотека, нет package для сторонних.
  • Документация отстаёт от кода (README не описывает usage/verify/gc/profiles), спецификаций много, но «нашей» онбординг-истории снаружи нет.
  • Зависит от OpenCode CLI как движка (не абстрагирован по моделям); нет OS-sandbox (риск C-01) для недоверенного исполнения.

B.4 Честный итоговый рейтинг (позиции)

Сразу оговорка: «рейтинг» в этом классе неоднозначен — инструменты решают разные подзадачи. Дам два честных среза: (1) пригодность как production-оркестратора общего назначения и (2) сила именно в безопасной/доказательной доставке кода (наша компетенция). ai-team честно оценю в обоих.

Но в узкой нише «доказательная безопасная доставка кода с человеческим контролем» — пока объективно сильнейший в этой выборке. Это и есть реальное позиционирование: не «ещё один агентональный framework», а «контроллер доверия над агентами» — редкая и сложная ниша, где конкурентов почти нет, но и рынок/traction — нулевые.

B.6 Открытые решения

  1. Цель по продукту: остаться «контроллером доверия» (ниша, где мы #1, но рынок мал) или расширяться в «полноценный автономный агент-инженер с sandbox» (OpenHands-направление), сохраняя evidence? Тут нужны твоя бизнес-потребность и целевая аудитория.
  2. Приоритет тракции: снаружи ничего не видно (README, публичный репо, демо, релиз). Без этого «0 звёзд vs 190k» — и рынок просто не узнает про нашу уникальную нишу.
  3. «Платформize» vs «монолит»: делать ли из ai-team встраиваемую библиотеку/пакет, чтобы другие могли использовать наш контроллер внутри своих pipeline (как LangGraph), или оставить CLI-инструментом?

Данные по звёздам — оценка на август 2026 из открытых источников (Presenc/Citadel/relatedrepos и др.); числа дрейфуют. Качественные оценки — экспертные, честные, без предвзятости к любому инструменту.
