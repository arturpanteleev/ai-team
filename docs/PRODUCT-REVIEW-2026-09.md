## P0

<a id="pdd-01"></a>

### PDD-01 — `make verify` нестабилен из-за hardcoded wall-clock timeout

**ЧТО.** На чистом checkout `make verify` упал (exit 2): в
`go test -coverprofile ./...` свалился `TestRunPreflightClassifiesMissingDeliveryPrereqs`
с `cli: не удалось получить версию: timeout`. Изолированно тест стабилен
(5 прогонов, 1.8–2.1 с), в `-race`-прогоне той же сессии прошёл. Воспроизведение:
1 падение на 2 полных coverage-прогона — зависит от загрузки машины.

**ПОЧЕМУ важно.** Это не только флейк. `commandTimeout` — константа пакета,
не конфигурируемая и не инъецируемая. В проде холодный старт CLI-рантайма
(`opencode --version` на Node) дольше 5 с помечает **required** check `cli` как
failed, и контроллер блокирует run целиком. То есть медленная машина или
холодный кэш выглядят как «рантайм недоступен».

**ГДЕ.** `pkg/preflight/preflight.go:21` (`commandTimeout = 5 * time.Second`),
используется в `preflight.go:163`; тест — `cmd/ai-team/audit_machine_test.go:245`.

**КАК ПРОВЕРИТЬ.** Timeout вынесен в конфиг с дефолтом и инъекцией в тестах;
`go test -count=1 -coverprofile=cov.out ./...` зелёный 5 раз подряд под
параллельной нагрузкой; отдельный тест на классификацию таймаута как
`warning`, а не как блокирующий `failed`.

## P1

<a id="pdd-02"></a>

### PDD-02 — релизные бинарники не подписаны

**ЧТО.** `release.yaml` публикует `.tar.gz` + `sha256sums.txt`. Подписи нет:
ни cosign/Sigstore, ни SLSA provenance, ни DSSE тем механизмом, который проект
уже реализовал для bundle.

**ПОЧЕМУ важно.** Центральный тезис продукта — «integrity против authenticity»
(README, «Граница безопасности»): digest доказывает «не изменено», подпись —
«кто создал». Для evidence-bundle проект это различие реализовал, а для
собственных артефактов поставки — нет. Это самая заметная асимметрия между
обещанием и практикой, и её первым делом заметит security-ориентированный
адоптер.

**ГДЕ.** `.github/workflows/release.yaml:92-97`, `:120-137`.

**КАК ПРОВЕРИТЬ.** Релиз содержит подпись и attestation; в README описана
команда проверки скачанного бинарника.

<a id="pdd-03"></a>

### PDD-03 — release-гейт слабее CI, а комментарий утверждает обратное

**ЧТО.** Комментарий в `release.yaml` гласит: «Gate 3 … These mirror what CI
runs on master/PR». Фактически release прогоняет только `go build ./...`,
`go vet ./...`, `go test ./...`. CI дополнительно гоняет gofmt, coverage gate
с per-package floors, `-race`, e2e, frontend (build/lint/test/audit + сверку
встроенного `dist`), govulncheck и строгую OpenSpec-валидацию.

**ПОЧЕМУ важно.** Release notes печатают утверждение «Quality gates passed on
exact tag commit», создавая впечатление полного покрытия. Тег можно поставить
на коммит, не проходивший frontend/race/coverage-проверки.

**ГДЕ.** `.github/workflows/release.yaml:39-41, 70-76` против `.github/workflows/ci.yaml`.

**КАК ПРОВЕРИТЬ.** Release job вызывает `make verify` (или переиспользует CI
workflow через `workflow_call`); комментарий и текст release notes совпадают с
фактическим списком.

<a id="pdd-04"></a>

### PDD-04 — `cmd/ai-team` покрыт на 16.9% и не входит в safety-floors

**ЧТО.** Общее покрытие 67.4% при floor 60%. Но `cmd/ai-team` — 16.9%, при
этом `main.go` более 1400 строк и содержит разбор флагов, коды выхода и весь
пользовательский контракт CLI. В `scripts/coverage-floors.env` перечислены
`approval, checks, delivery, evidence, pipeline, safeio` — `cmd/` отсутствует.

**ПОЧЕМУ важно.** CLI — основная поверхность продукта. Ошибки разбора флагов и
кодов выхода (см. PDD-06) не ловятся ни одним гейтом.

**ГДЕ.** `scripts/coverage-floors.env`, `scripts/coverage-gate.sh:31`.

**КАК ПРОВЕРИТЬ.** Для `cmd/ai-team` заведён floor (стартово на текущем
значении, ratchet вверх) и добавлены тесты на разбор аргументов и exit codes
каждой команды.

<a id="pdd-05"></a>

### PDD-05 — чистый доменный пакет зависит от инфраструктурных

**ЧТО.** `pkg/workflow` документирован как «доменные state/outcome типы и
чистые переходы», но импортирует `pkg/checks` и `pkg/delivery` — исключительно
ради полей `StageResult.Checks []checks.Result` и `StageResult.Delivery
*delivery.Result`. `delivery.Result` содержит `CommitSHA` и `PRURL`.

**ПОЧЕМУ важно.** Инверсия зависимостей: доменный слой знает про git и про
исполнение проверок. Каждый результат стадии любого workflow — включая
не-софтверный — носит git-специфичные поля. Это первый барьер на пути
извлечения generic-движка (см. PDD-17, PDD-18).

**ГДЕ.** `pkg/workflow/result.go:6-8, 62, 65`.

**КАК ПРОВЕРИТЬ.** `go list -f '{{.Imports}}' ./pkg/workflow` не содержит
`pkg/checks` и `pkg/delivery`; эффекты представлены непрозрачным типом или
интерфейсом, git-поля живут в реализации эффекта.

<a id="pdd-06"></a>

### PDD-06 — `ai-team list` молча игнорирует аргументы

**ЧТО.** `cmdList` не создаёт `flag.FlagSet` и жёстко берёт `absoluteTarget(".")`.
Проверено: `ai-team list --target <dir>` печатает реестр текущего каталога,
`ai-team list --nonexistent-flag xyz` печатает вывод как ни в чём не бывало.
Все остальные команды используют `flag.ExitOnError`.

**ПОЧЕМУ важно.** Команда уверенно отвечает неправильно вместо того, чтобы
упасть. `--target` есть у всех соседних команд, поэтому пользователь ожидает
его и здесь.

**ГДЕ.** `cmd/ai-team/main.go:1259-1285`.

**КАК ПРОВЕРИТЬ.** `list` принимает `--target` и отвергает неизвестные флаги
ненулевым кодом; тест на оба случая.

<a id="pdd-07"></a>

### PDD-07 — неизвестные API-пути отдают SPA вместо 404

**ЧТО.** `srv.router.Get("/*", srv.handleFrontend)` ловит всё, включая
несуществующие `/api/...`. Проверено: `GET /api/definitely-not-a-route` →
`200 text/html`. (Аутентификация при этом работает корректно: `POST /api/runs`
без токена → 401, подмена `Host` → 403.)

**ПОЧЕМУ важно.** Любой автоматизированный клиент — включая внешний
оркестратор, ради которого затевался structured-output — получает 200 с HTML
вместо машиночитаемой ошибки.

**ГДЕ.** `pkg/web/server.go:163`.

**КАК ПРОВЕРИТЬ.** Неизвестный путь под `/api/` возвращает `404` с
`application/json`; SPA-fallback действует только вне `/api`.

<a id="pdd-08"></a>

### PDD-08 — нет статического анализа кроме `go vet` и `gofmt`

**ЧТО.** На 26 433 строк production-кода Go применяются только `gofmt -l` и
`go vet`. Ни staticcheck, ни errcheck, ни анализатора цикломатической
сложности.

**ПОЧЕМУ важно.** Именно такие линтеры ловят класс дефектов, которые в этом
проекте дороже всего: проглоченные ошибки в цепочках evidence/delivery и
разрастание функций (см. PDD-09).

**ГДЕ.** `.github/workflows/ci.yaml` job `lint`, `Makefile` target `verify`.

**КАК ПРОВЕРИТЬ.** `golangci-lint` с зафиксированной конфигурацией в CI и в
`make verify`, зелёный на текущем коде.

### PDD-09 — `pkg/pipeline` как hub-пакет

**ЧТО.** `pkg/pipeline` импортирует 22 из 42 внутренних пакетов, содержит 4692
строки production-кода. `Pipeline.RunWithResult` — 496 строк,

**ГДЕ.** `pkg/pipeline/pipeline.go:204`, `pkg/pipeline/stage.go:53`.

**КАК ПРОВЕРИТЬ.** Выделены отдельные единицы: подготовка run, исполнение
стадии, авторизация переходов, финализация; ни одна функция не превышает ~120
строк; импортов у пакета меньше.

## Стратегические — путь к универсальному конструктору

Эмпирическая база: на этой машине без единой строки Go запущен полностью
не-софтверный workflow (`researcher → writer → factchecker`, свои роли, свой
граф, свои артефакты, loopback-ребро). Он прошёл до `$complete`, произвёл
evidence, прошёл `ai-team verify`, `ai-team export` и автономную проверку
bundle, и отобразился в дашборде с полным снимком конфигурации. Движок уже
универсален для формы «LLM-стадия → файловый артефакт → вердикт →
гейтированный переход». Ниже — то, что отделяет его от конструктора общего
назначения.

<a id="pdd-17"></a>

### PDD-17 — граф является последовательным автоматом, а не DAG

**ЧТО.** `executeGraph` держит единственный `current string`;
`Graph.Edge(from, outcome)` возвращает ровно одно ребро; уникальность
`(from, outcome)` проверяется валидатором как инвариант. Ни fan-out, ни join,
ни параллельного исполнения ветвей не существует.

**ПОЧЕМУ важно.** Это главный архитектурный предел для заявленной цели.
Практически: нельзя запустить трёх независимых ревьюеров одновременно, нельзя
разложить задачу на параллельные подзадачи. Конкурент Bernstein строит своё
позиционирование именно на параллельном исполнении в изолированных worktree.

**ГДЕ.** `pkg/pipeline/execute.go:36-120`, `pkg/workflow/graph.go:55, 78-140`.

**ЦЕНА.** L. Затрагивает учёт `max_visits`, атрибуцию мутаций, схему evidence,
модель approval и UI. Делать после PDD-05 и PDD-09.

<a id="pdd-18"></a>

### PDD-18 — терминальный эффект жёстко привязан к git и `gh`

**ЧТО.** `kind: delivery` — единственный не-агентный вид узла, и он обязан
иметь `mutation: external`. `delivery.Controller.Execute` вызывает `git` и `gh`
напрямую (≈20 мест). Интерфейс `delivery.Service` существует и инъецируется
через `WithDeliveryService`, но его контракт (`Plan`, `Request`, `Result` с
`Branch`, `Remote`, `CommitSHA`, `PRURL`) полностью git-специфичен.

**ПОЧЕМУ важно.** Именно поэтому не-софтверный workflow из эксперимента выше
заканчивается на `$complete` и не может ничего «поставить»: опубликовать
статью, создать тикет, загрузить датасет. Интерфейс-шов уже есть — нужно
обобщить его тип данных.

**ГДЕ.** `pkg/delivery/executor.go:124-144, 203-482`;
`pkg/agent/registry.go:114-134`.

**ЦЕНА.** L. Предлагаемый шов: `kind: effect` + поле `effect: git-pr | http |
script`, каждый со своим canonical plan, его SHA-256 и subject для approval;
git становится одной из реализаций `EffectExecutor`. Механика
«approval точного хэша плана» сохраняется как есть — она уже доменно-нейтральна.

<a id="pdd-19"></a>

### PDD-19 — фиксированный словарь исходов, переходы без данных

**ЧТО.** Валидатор допускает ровно 7 значений outcome (`passed, failed,
rejected, blocked, canceled, skipped, warning`). Маршрут выбирается только по
outcome, который выводится из verdict-маркера и статуса проверок.
Маршрутизация по содержимому артефакта или по числовому порогу невозможна.

**ГДЕ.** `pkg/workflow/graph.go:96-100`, `pkg/workflow/state.go:30-38`.

**ЦЕНА.** M.

<a id="pdd-20"></a>

### PDD-20 — нет композиции, схемы и редактора

**ЧТО.** Граф нельзя вызвать из графа (нет sub-workflow). Для `config.yaml` не
опубликована JSON Schema, поэтому в редакторе нет автодополнения и валидации.
Дашборд показывает текущую позицию в графе, но не позволяет граф собирать.

**ПОЧЕМУ важно.** Для цели «DSL-сценарии» схема — обязательный

### PDD-21 — смешанный язык ограничивает adoption

### PDD-22 — позиционная коллизия с существующими проектами

**ЧТО.** На рынке уже есть два проекта с почти идентичным тезисом:

**ПОЧЕМУ важно.** Нужен явный выбор ниши и раздел сравнения в README.

# Второй проход: проверка исполнением

Первый проход оценивал устойчивость к сбоям, подпись и гейты по коду. Второй
проход проверил их прогоном. Ниже — протокол и четыре новые находки.

## Протокол проверок

| Сценарий | Результат |
|---|---|
| `make test-e2e` (mock-opencode, subprocess-уровень) | прошёл, 64.9 с |
| `kill -9` контроллера в середине стадии | checkpoint корректен: `phase: running`, `next_stage: writer` |
| `--resume` после обрыва | тот же `run_id`, оборванная попытка записана как `✗`, run завершён |
| `verify` после resume | anchor OK |
| Подмена одного поля в `events.jsonl`, resume на месте | отказ: `event_chain: event chain: event 2 hash mismatch` |
| Контрольный resume без подмены, тот же каталог | успешно (исключает ложную корреляцию) |
| `gate`: source + tests вместе | PASS, exit 0 |
| `gate`: source без тестов | FAIL, exit 1 |
| `gate`: working tree ≠ candidate | BLOCKED, exit 2, объяснение fail-closed |
| DSSE: подпись → verify своим ключом | подпись подтверждена |
| DSSE: verify чужим ключом | отказ: `dsse: подпись не совпадает` |
| DSSE: verify без ключа | integrity-only, честно помечено в выводе |
| Подмена подписанного bundle | отказ: `record "gate.json" повреждён (sha256 не совпадает)` |
| Согласованная перезапись неподписанного bundle | проходит integrity-only, `bundle_sha256` меняется |
| `redact verify` / `redact scan` | clean, 27 файлов, 0 находок |

**Вывод.** Устойчивость к сбоям и evidence-контур работают ровно так, как
описаны. Восстановление после обрыва не прячет оборванную попытку, а
записывает её. Подмена ловится на конкретном событии с указанием его номера.

**DSSE закрывает вопрос по PDD-11.** Функциональность реализована и работает
во всех четырёх режимах; расхождение чисто процессное — не отмечены задачи в
`openspec/changes/dsse-signed-bundle/tasks.md`. Это снижает техническую
серьёзность находки, но не процессную: реестр, по которому судят о состоянии
проекта, вводит в заблуждение.

**Подтверждение честности документации.** Согласованная перезапись
неподписанного bundle проходит integrity-only проверку — ровно так, как
README и описывает в разделе «integrity vs authenticity». Это не уязвимость, а
задокументированная граница; при этом печатаемый `bundle_sha256` меняется
(`908220be…` → `47b07942…`), так что сверка ранее записанного дайджеста
подделку обнаруживает. Формулировка README точна.

**Побочное подтверждение изоляции.** При попытке передать агенту переменную
окружения для управления моком она до подпроцесса не дошла: env allow-list
рантайма её отрезал. Заявленная изоляция окружения работает.

## Находки второго прохода

<a id="pdd-23"></a>

### PDD-23 — дочерний процесс агента переживает жёсткий обрыв контроллера

**ЧТО.** После `kill -9` процесса `ai-team` подпроцесс CLI-агента остаётся жив
и продолжает работать бессрочно. Проверено: через 2 секунды после обрыва
родителя `pgrep` находит процесс агента.

**ПОЧЕМУ важно.** SIGKILL перехватить нельзя, поэтому сам по себе факт
ожидаем. Значимо другое: осиротевший агент продолжает держать candidate
worktree и может писать в него уже после того, как контроллер перестал за ним
следить, — то есть вне контура, который проект гарантирует. `pkg/process`
реализует supervision группы процессов, и она корректно работает на штатных
путях (таймаут, отмена, SIGINT), но аварийный путь ничем не закрыт.

**ГДЕ.** `pkg/process/`, путь запуска агента в `pkg/runtime`.

**КАК ПРОВЕРИТЬ.** На следующем запуске контроллер обнаруживает и убивает
осиротевшие процессы предыдущего run'а того же workspace, либо запуск
отказывает fail-closed, пока они живы. На Linux дополнительно `PR_SET_PDEATHSIG`.

<a id="pdd-24"></a>

### PDD-24 — evidence привязан к абсолютному пути

**ЧТО.** Копия каталога проекта вместе с `.ai-team/` не резюмируется: `resume
run: target identity mismatch`. Контрольный прогон в исходном каталоге при тех
же данных проходит, то есть причина именно в смене пути, а не в содержимом.

**ПОЧЕМУ важно.** Практические следствия не описаны в документации: нельзя
перенести проект в другой каталог, нельзя продолжить run на другой машине или
в CI с иным путём checkout, нельзя разобрать инцидент на копии. Для
инструмента, который гордится переносимым bundle, это несимметрично: evidence
экспортируется куда угодно, а продолжить работу можно только на месте.

**ГДЕ.** Проверка identity в `pkg/evidence/resumeverify.go` и `run.json`.

**КАК ПРОВЕРИТЬ.** Либо поведение задокументировано явно как инвариант, либо
идентичность target становится относительной с явным флагом переноса.

<a id="pdd-25"></a>

### PDD-25 — неоднородные права файлов в bundle

**ЧТО.** В собранном bundle `gate.json` и `dsse.json` записаны как `-r--r--r--`,
а `index.json` — как `-rw-r--r--`.

**ПОЧЕМУ важно.** Само по себе безвредно: подмена ловится дайджестом. Но
неоднородность читается как недосмотр в том самом месте, где продукт
демонстрирует аккуратность к неизменяемости.

**ГДЕ.** Запись bundle в `pkg/export` / `pkg/gate` (`WriteBundle`).

<a id="pdd-26"></a>

### PDD-26 — слабо покрытые пакеты вне safety-floors

**ЧТО.** Замеренное покрытие: `pkg/ui` — 0%, `pkg/worker` — около 41%,
`pkg/report` — около 50%, `pkg/artifactstore` — около 64%, `pkg/eval` — около
65%. Ни один из них не входит в per-package floors, поэтому ratchet их не
удерживает.

**ПОЧЕМУ важно.** `pkg/worker` исполняет job'ы в многопользовательском
сценарии, `pkg/artifactstore` хранит артефакты — оба ближе к safety-контуру,
чем к косметике. `pkg/ui` и `pkg/report` менее критичны.

**ГДЕ.** `scripts/coverage-floors.env`.

## Процессные задачи

Эта задача пришла не из аудита, а из работы над границей «issue ↔ OpenSpec
change» (см. CONTRIBUTING.md). Записана здесь, чтобы жить в одном списке с
остальными.

<a id="pdd-27"></a>

### PDD-27 — механическая проверка связи PR и OpenSpec change

**ЧТО.** Правило «поведенческое изменение обязано ссылаться на change»
держится только на внимательности ревьюера. PR-шаблон предлагает отметить один
из двух чекбоксов, но ничто не проверяет, что отмеченный «Behavioural change»
действительно сопровождается существующим каталогом в `openspec/changes/`.

**ПОЧЕМУ важно.** Это тот же класс расхождения, что PDD-11: документ
утверждает одно, репозиторий содержит другое, и обнаруживается это через
месяцы. Spec-first — заявленная дисциплина проекта, и она единственная сейчас
ничем не подпёрта, кроме дисциплины.

**ПОЧЕМУ низкий приоритет.** Пока мейнтейнер один и внешнего потока PR нет,
цена пропуска мала, а цена ошибки в обратную сторону — заметна: жёсткая
блокировка на первом же PR от внешнего человека отталкивает ровно тех, кого
проект хочет привлечь. Задача имеет смысл к моменту, когда появится поток
чужих PR, а не раньше.

**ГДЕ.** Новая job в `.github/workflows/ci.yaml`; договор о формате —
`.github/PULL_REQUEST_TEMPLATE.md`.

**РЕШИТЬ ДО РЕАЛИЗАЦИИ.** Задача не готова к реализации, пока не выбрано:

1. **Откуда брать факт наличия change.** Из тела PR (хрупко — человек может
   ошибиться в пути), из имени ветки (навязывает соглашение) или из самого
   diff — наличие добавленных файлов под `openspec/changes/<name>/`. Третий
   вариант устойчивее прочих и работает для PR из форков, где нет доступа к
   секретам.
2. **Блокировать или предупреждать.** Для внешних контрибьюторов разумнее
   предупреждение с объяснением и ссылкой на CONTRIBUTING, блокировка — для
   PR из основного репозитория. Это решение должно быть записано, а не
   подразумеваться.
3. **Нужна ли обратная ссылка** из `proposal.md` на номер issue. Инварианту
   «не повторять» это не противоречит — номер является указателем, а не
   дублированием содержания, — но требует решения, обязателен он или нет.

**КАК ПРОВЕРИТЬ.** PR, помеченный как поведенческий, без каталога
`openspec/changes/<name>/` в diff — проверка срабатывает с внятным сообщением
и ссылкой на CONTRIBUTING. PR, помеченный как неповеденческий, проверку
пропускает. Проверка корректно отрабатывает на PR из форка. Выбранный режим
(блокировка или предупреждение) задокументирован в CONTRIBUTING.
