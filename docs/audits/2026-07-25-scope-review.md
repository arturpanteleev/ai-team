# Обзор объёма ai-team: что лишнее, что работает, куда двигаться

Дата: 2026-07-25. Срез кода: `5bc99f0` («propose: strict-sandbox-and-candidate-isolation»),
ветка `master`. Файл не закоммичен — обычный untracked-файл в рабочей директории.

Это **не** аудит качества и не поиск багов: для этого уже есть
`INDEPENDENT_AUDIT_2026-07-23.md`. Здесь другой вопрос — **сложность против
ценности**: что можно удалить, не потеряв замысла, и где сложность накручена
ради самой себя.

## Эталон, против которого всё измеряется

Замысел автора, сформулированный им самим:

1. Простой цикл разработки: постановка задачи → архитектура → написание кода → проверка.
2. Этапы выполняются разными агентами независимо.
3. Workflow задаётся конфигом как **граф**: вершины — этапы, рёбра — допустимые переходы.
4. **Веб-интерфейс — главная поверхность**: там видно всё, оттуда же создаётся
   задача и правится конфиг. CLI — вспомогательный.
5. По духу — аналог «Ralph» / петля review-revise, а не enterprise control plane.

## Метод и границы достоверности

Обзор собран из двух источников:

- **Живой прогон** реальной задачи в чистом репозитории (см. раздел «Живой
  прогон»). Все утверждения оттуда воспроизведены командами.
- **Семь параллельных разборов подсистем** (ядро цикла, delivery+evidence, веб,
  периферия, мета-процесс, роли агентов, граф-конфиг) плюс личная проверка
  грепом самых дорогих вердиктов «удалить».

**Чего в этом обзоре не хватает, и это важно знать:** скептическая
(опровергающая) проверка вердиктов и восьмой разбор — «какие из 17 находок
прошлого аудита уже исправлены» — не были выполнены из-за исчерпания лимита.
Поэтому:

- Всё, что помечено **«проверено лично»**, — это личный греп по коду или живой
  прогон. Этому можно доверять.
- Оценки в строках, тройная сверка digest в delivery, разбор содержания промптов
  — **один непроверенный источник каждый**. Перед удалением этих кусков стоит
  перепроверить самостоятельно.

## 1. Живой прогон: что действительно работает

Настроен чистый Go-репозиторий (`strkit`), задача «добавить `Reverse(s string) string`
с тестами на ASCII / пустую строку / UTF-8», локальный bare-remote вместо GitHub,
мок вместо `opencode` (реальный LLM-прогон невозможен: `opencode auth list` →
**0 credentials**). Мок написан так, чтобы выдавать **валидный код под задачу**, а
не заглушки.

### Работает

- **Все 7 этапов проходят.** Настоящие `go test -json` / `go vet` выполняются как
  required checks. Коммит содержит **ровно 2 файла** (`reverse.go`,
  `reverse_test.go`) на ветке `ai-team/reverse-func`, push и PR выполнены.
- **Гарантии не декоративные.** В первом прогоне мок написал код с конфликтующим
  `package` — required checks честно уронили пайплайн на стадии tester, до
  доставки дело не дошло.
- **Двухфазное одобрение плана работает** ровно как описано: первый прогон печатает
  canonical plan + его SHA-256 и останавливается, второй с `--approve-plan <hash>`
  доставляет.
- **Петля review→revise работает** — но только через TTY (см. ниже). В прогоне через
  настоящий pty: reviewer выдал `CHANGES_REQUESTED` → возврат к coder → coder
  pass=2 → reviewer `APPROVED` → доставка. Весь цикл — **4 ответа человека**
  (2 checkpoint + 1 возврат + 1 подтверждение плана).
- **Живой мониторинг через веб работает** — через поллинг. На 7-й секунде прогона
  API отдал `status: running` и `[analyst passed, architect running]`; на 19-й —
  `[analyst passed, architect passed, coder failed]`.
- Бэкенд отдаёт больше, чем показывает фронт: `checks_json`, `mutations_json`,
  `delivery_json` (со всеми git-шагами доставки), `config_snapshot`.

### Сломано или расходится с замыслом

**Н-1. Первый запуск гарантированно падает.** `ai-team init` дописывает `.ai-team/`
в `.gitignore` → workspace становится грязным → следующий же `run` отбивается
baseline-гардом: `новый run требует clean git workspace; сохраните или удалите
пользовательские изменения: .gitignore`. Сценарий «поставил, запустил» не работает
никогда, ни в одном репозитории. Починка — ~10 строк.

**Н-2. Петля review→revise живёт только в TTY.** `pipeline.go:1749` — возврат к
coder обёрнут в `if rs.p.prompter.Interactive()`. Неинтерактивный прогон (то есть
любой запуск из веба или CI) на негативном вердикте **просто останавливается**,
проваливаясь в `on_negative_verdict: stop`. Ядро замысла #5 недоступно ниоткуда,
кроме терминала автора. *Проверено лично: прогон без TTY остановился на
`CHANGES_REQUESTED`, прогон через pty прошёл петлю.*

**Н-3. WebSocket-слой мёртв.** `Hub.BroadcastEvent` (`websocket.go:98`) не
вызывается нигде в проде — только в `websocket_test.go`. Хаб поднимается, клиенты
подключаются, события не приходят никогда. Во фронтенде есть честный комментарий:
`// CLI пишет в SQLite без WebSocket-пуша — активный run поллим`.
*Проверено лично грепом.*

**Н-4. Веб не знает состояния «ждёт подтверждения».** Контракт `Recorder`
(`pipeline.go:49-56`) — это `ReconcileInterrupted / RunStarted / StageStarted /
StageFinished / AttemptsInvalidated / RunFinished`. `applyCheckpoint` блокируется
на `prompter.Ask` и **не уведомляет recorder вообще**. Поэтому остановка на гейте
приходит в дашборд как `stopped` — неотличимо от падения. Без нового события
«апрувить из веба» не построить.

**Н-5. `--retry-from` создаёт отдельный ран.** Продолжение доставки появилось в
дашборде как второй ран с единственной стадией `deployer`. Вместо одной ленты по
фиче получаются осколки.

**Н-6. Commit message обрезается посреди слова:**
`"reverse-func Добавить функцию Reverse(s string) string в пакет strkit с"`.

**Н-7. `.ai-team/` в самом репозитории ai-team отсутствует** — на себе инструмент
не запускался. Прошлый аудит предположил обратное («автор, по всей видимости,
использует ai-team для разработки ai-team») — это неверно: `openspec/changes`
появились обычной ручной работой с агентами.

**Н-8. Про opencode.** Авторизации нет (0 credentials). Отдельно: env теперь
передаётся по allow-list (`PATH`, `HOME`, `USER`, `LANG`, `TMPDIR`, `TERM`, …),
поэтому при авторизации ключом через переменную окружения понадобится
`AI_TEAM_OPENCODE_ENV_ALLOW=ANTHROPIC_API_KEY` — иначе ключ до подпроцесса не
дойдёт.

**Н-9. `make verify` сейчас красный, и CI-джоб `frontend` тоже.** Цепочка
падает на `npm audit --audit-level=high` (`Makefile:37`, `ci.yaml:128`):
`react-router-dom ^7.18.1` попадает в уязвимый диапазон 7.12.0–8.2.0 (2 high,
GHSA-qwww-vcr4-c8h2, «RSC Mode CSRF Bypass»), а `npm audit fix` предлагает
downgrade до 7.11.0 как breaking change. *Проверено лично: `npm audit
--audit-level=high` → exit 1.* Практический нюанс: advisory про RSC-режим и
server actions, которых в этом SPA нет, — то есть эксплуатируемости здесь
вероятно нет, но гейт блокирует всё равно, и `npm run lint && npm test &&
npm run build` локально даже не доходят до запуска. Это находка из
`CODEX-PLAN.MD` §4.5, которую я подтвердил; в разделе 9 ниже она корректирует
вывод «находка №8 прошлого аудита исправлена».

**Н-10. E2E-тесты маскируют Н-1.** `e2etest/e2e_test.go:165` и `:445` вручную
делают `git add .gitignore` перед запуском pipeline — ровно тот шаг, которого
нет у настоящего пользователя. Поэтому сломанный сценарий `init → run` зелёный
в CI. *Проверено лично; находка из `CODEX-PLAN.MD` §4.1.* Мне пришлось сделать
тот же обход руками, чтобы прогон вообще начался (см. раздел 10).

**Н-11. Даже если WebSocket подключить, дашборд его не поймёт.** `Recorder`
пишет события `run_started`, `attempt_started`, `attempt_finished`,
`attempts_invalidated`, `run_finished`, а `Dashboard.tsx:44` проверяет
`event.type === 'pipeline_completed'` — имя, которое не эмитит никто. Вдобавок
существуют **два несовместимых контракта события**: Go-структура
`web.Event{Type, PipelineID, RunID, AttemptID, Agent, Status, DurationMs}` для
WS и persisted-запись `{run_uid, sequence, type, attempt_uid, timestamp,
data_json}` в SQLite. *Проверено лично; находка из `CODEX-PLAN.MD` §4.4.*

## 2. Диагноз

Проект не разросся случайно — у него **сместился центр тяжести**. Задумывался
движок workflow, построен криптографический контур доверия к git-доставке.

| | строк |
|---|---|
| Всего Go (с тестами) | 17 026 |
| Ядро замысла: цикл этапов + артефакты как интерфейс + вердикт + петля + один checkpoint | **~500** |
| Сейчас на это отведено (`pkg/pipeline` + `pkg/workflow`) | 2 800 |
| Обвязка гарантий: delivery 1 867 + evidence ~1 400 + candidate-evidence 330 + attestation в checks 280 + mutation-снапшоты 300 | **~4 200** |
| Мета-процесс (markdown) | **11 590** — больше, чем 10 841 строка прод-Go |

Модель угроз, под которую написаны эти 4 200 строк: «противник может подменить
план доставки или подделать журнал». Противник здесь — сам автор на своём
ноутбуке. Строгость настоящая (это подтверждено и прошлым аудитом, и живым
прогоном), но она защищает от того, чего нет, и **не** дала того, что было нужно.

Три из четырёх функций «главной поверхности» отсутствуют полностью, а петля
review-revise требует человека у терминала. То есть ровно две вещи, которые автор
называет смыслом проекта, — единственные, которых нет.

## 3. Что лишнее: четыре корзины

### Корзина 1. Мёртвое — удаляется без обсуждения

Каждая строка этой таблицы проверена личным грепом.

| что | строк | проверка |
|---|---|---|
| `pkg/evidence/replay.go` | 345 | 0 вызовов вне тестов |
| `pkg/eval/suite.go` (`RunSuite`, `Case`, `Layer`) | 100 | 0 вызовов |
| `agent.NewRegistry`, `notifier.NotifierChain` | ~10 | 0 вызовов |
| Vite-шаблон: `App.css`, `src/assets/*` | 190 | не подключён |
| `X-Total-Count` + пагинация | 35 | фронт не читает, страниц в UI нет |
| `runStatus(err)`, `authorizeStage()` (no-op), `verdict.ReadBlockedSince`, `verdict.FromOutputs` | ~43 | не вызываются |
| `openspec/changes/archive` | 5 531 md | история уже в git |

**Итого: ~770 строк Go и 5 531 строка markdown.** Риск — нулевой.

**Два вердикта отсюда отозваны после сверки с `CODEX-PLAN.MD` (см. раздел 11):**

- **Таблица `events` в SQLite (45 строк) — НЕ удалять.** У неё действительно нет
  ни одного `SELECT`, но *проверено лично*: схема уже содержит
  `run_uid, sequence, ... UNIQUE(run_uid, sequence)` — то есть это готовый
  cursor-ordered event store, ровно то, что нужно для WS-моста с replay по
  `last_sequence`. Это не мёртвый груз, а вторая половина никогда не собранного
  моста; не хватает только цикла «читать по sequence → broadcast» (~50–80 строк).
- **WebSocket Hub + `useWebSocket` (477 строк) — не удалять, а достроить.**
  Канал сегодня мёртв (Н-3), но polling каждые 5 секунд не может дать
  «событие в вебе за 1–2 секунды» и не может показать «жду твоего решения» в
  момент возникновения. Клиент к тому же уже умеет reconnect с exponential
  backoff — не хватает cursor и дедупликации. Удалять — значит выкинуть уже
  оплаченные 80% транспорта.

### Корзина 2. Дублирующие поверхности

Пока веб умел только читать, вокруг CLI наросли его заменители.

| что | строк | почему лишнее |
|---|---|---|
| `pkg/report` (генератор + шаблоны) | 570 | SQLite уже хранит `checks/mutations/delivery_json`, API их отдаёт, фронт не объявил поля. 570 строк существуют вместо ~30 строк TSX. Вдобавок дашборд отдаёт этот HTML как `text/plain` — он нечитаем. |

проверок.

### Корзина 3. Переусложнено относительно угрозы

Здесь не «удалить», а «упростить впятеро» — ~3 000 строк.

- **Восемь синтаксисов для одного поведения.** `transition: gate|by_confirm`,
  `gate_after`, `gate_before`, `checkpoint_after/before: interactive|require_explicit`
  — всё сходится в `applyCheckpoint`. **Проверено лично:** там единственное
  сравнение `policy == config.CheckpointAuto`, то есть `interactive` и
  `require_explicit` ведут себя **идентично**, хотя спека обещает разницу.
  Нормализация — `config.go:191-212`, запрет смешивания — `config.go:271-278`.
  Восемь синтаксисов → два поведения.
- **`schema_version` 1/2/3 одновременно + `migrateV2ToV3`**, ~230 строк. Обратная
  совместимость для единственного пользователя — самого автора.
- **Write-only данные.** Candidate-evidence 330; `checkpointSubjectHash` 52
  (печатает 64 hex-символа, которые никто не сверяет); `ControllerIdentity`
  (SHA-256 самого бинарника `ai-team` на каждом старте рана); immutable
  `config.json`/`workflow.json` в режиме 0444 — дубль `config_snapshot` в SQLite.
  Hash-chained `events.jsonl` (230 строк) верифицируется только внутри самого
  evidence и мёртвого `replay.go`; CLI-команды для чтения evidence не существует,
  веб берёт историю из SQLite. *Проверено лично: единственный прод-вызывающий
  `VerifyEventLog` — `store.go:457`, второй — мёртвый `replay.go:43`.*

  **Важная оговорка (после сверки с `CODEX-PLAN.MD`).** «Write-only» — это
  свойство *сегодняшней* архитектуры, а не приговор самим механизмам. Как только
  approval становится **асинхронным** (человек решает из браузера, возможно
  через минуты и из другого процесса), `checkpointSubjectHash` перестаёт быть
  ритуалом и становится несущим: он единственный способ отклонить решение,
  принятое по устаревшему предмету. Аналогично `events.jsonl` получает первого
  настоящего читателя — WS-мост с replay. Поэтому корректный вердикт:
  `checkpointSubjectHash` → **оставить и сделать частью `ApprovalDecision`**;
  `events.jsonl` → **оставить, но выбрать ОДНО хранилище событий** (файл или
  SQLite-таблица), а не держать оба. Под удаление здесь остаются только
  `ControllerIdentity` и immutable `config.json`/`workflow.json`, у которых
  читателя не появляется ни в одной из целевых схем.
- **Хеширование дерева.** Две несовместимые реализации (`checks.workspaceDigest`
  и `pipeline.captureFilesystemSnapshot`), 15–20 полных проходов по репозиторию
  за прогон, `node_modules` не исключён. Прошлый аудит измерил это независимо:
  9 247 файлов, 1.6 с холодного прохода.
- **Тройная сверка одних и тех же байт** перед коммитом (`WorkspaceDigest` →
  `VerifyPreparedWorkspace` → цикл сверки), плюс отдельная сверка blob-sha256 в
  index и ещё раз в коммите — при отключённых git-хуках.
- **Crash-safe resume** со state-машиной schema v4 (330 строк) + ~40 атомарных
  fsync-перезаписей полного state-файла за одну доставку.
- **Реимплементация грамматики git ref-name** (`branchPattern`, `remotePattern`,
  `gitHashPattern` + 6 дополнительных правил) — вместо `git check-ref-format`.
- **`--retry-from`** (~200 строк) — второй, независимый механизм «прыгнуть на
  стадию N», не пересекающийся с loopback. В графе это просто стартовая вершина.

### Корзина 4. Роли: 7 → 4–5

`reviewer`, `tester`, `verifier` проверяют **один и тот же кандидат**. `tester`
сам себя дискредитирует в промпте: «фактический запуск выполняет controller»,
«PASS не утверждает, что тесты прошли» — а тесты и так пишет coder по своей же
спеке. `verifier` отличается от `reviewer` не критериями (AC, edge cases,
security, performance — почти теми же словами у обоих), а только тем, что видит
результаты детерминированных checks.

Движок это уже позволяет: checks мержатся из def.yaml агента и per-stage конфига
и выполняются **для любой стадии** (`pipeline.go:1071-1073`), а test-evidence
ищется по всем результатам рана, а не по имени стадии. Значит одна ревью-стадия
**после** checks даёт всё, что дают три — минус два LLM-вызова и два вида
candidate-evidence.

Два этапа планирования, наоборот, оправданы: это единственные две точки
`checkpoint_after: require_explicit` — ровно та ручная петля, ради которой всё
строилось. Лишние там документы, а не стадии: `proposal.md` и `spec.md` требуют
одних и тех же AC, `design.md` и `tasks.md` — один и тот же план. Причём
`proposal.md` с AC **не доходит ни до coder, ни до reviewer**: read-rules деняют
`.ai-team/**` кроме объявленных inputs.

Минимальный набор, реализующий замысел:
`analyst → architect → coder → reviewer (после checks) → deployer`.

Теряется только формальная независимость автора тестов и различение
`CHANGES_REQUESTED` / `REJECTED` — которое и сейчас не имеет поведенческих
последствий, потому что `IsNegative()` их объединяет.

## 4. Граф переходов

### Сейчас это не граф

Упорядоченный `[]AgentConfig`; вперёд — только `i++`; назад — одно ребро;
валидация `loopback_to` **структурно запрещает** forward-рёбра («должен точно
ссылаться на предыдущий этап»). Три значения вердикта схлопываются в
`IsNegative()`, поэтому маршрут не может зависеть от того, какой именно
негативный вердикт пришёл. Самое важное ребро (`rejected → coder`) вообще не в
конфиге: его создаёт `defaultLoopbackTarget` в Go по признаку `mutation: source`.

Из восьми per-stage полей переходы задают ровно два (`loopback_to` и позиция в
списке), остальные шесть — политика остановки. Одно реальное ребро описано в двух
местах: `loopback_to` на источнике, `max_retries` на цели.

### Код структурно готов к переходу

- Точка итерации ровно одна: `execute` (`pipeline.go:405-478`, 121 строка).
- Решение «куда дальше» уже централизовано: `enforce` + `checkpoints`.
- `pkg/workflow` уже детерминированно вычисляет 9 значений `Outcome` — это готовые
  метки рёбер, которые `execute` игнорирует, заново ветвясь на сырых
  `r.Status` / `r.Err` / `r.Verdict`.

### Целевой формат

Восемь per-stage полей сворачиваются в одно `on:`:

```yaml
schema_version: 4
stages:
  - name: analyst
    on: { passed: architect, blocked: stop }
    pause_after: true            # вместо 8 синтаксисов checkpoint
  - name: architect
    on: { passed: coder, rejected: analyst }
    pause_after: true
  - name: coder
    on: { passed: reviewer }
  - name: reviewer
    checks: [go-test, go-vet]
    on: { approved: deployer, changes_requested: coder, blocked: stop }
    max_visits: 3                # вместо max_retries на цели
  - name: deployer
    on: { passed: done }
```

Тот же формат для замысла #1 в минимальном виде — четыре вершины:
`analyst → architect → coder → reviewer`, ребро `changes_requested: coder`.

**Цена перехода:** ~350 строк переписать, ~700 удалить (прод + тесты + ~350 из
416 строк спек про переходы).

## 5. Веб как главная поверхность: чего не хватает

Сейчас `pkg/web` регистрирует **исключительно GET** (`server.go:64-69`): пять
API-эндпоинтов + `/ws` + SPA. Ни одного `POST`/`PUT`/`DELETE` во всём пакете.
Разделение на два процесса через SQLite (WAL + busy_timeout + MaxOpenConns(1)) —
**не тупик**, а хорошая база для чтения; менять надо только сторону записи.

| что нужно | оценка | что уже есть и переиспользуемо |
|---|---|---|
| `POST /api/runs` — создать задачу и запуск | ~450 | `pipeline.RunWithResult` — библиотечный API, готов к вызову из процесса сервера |
| Approval checkpoint/gate из веба | ~330 | шов `WithPrompter` существует и никогда не использовался; в `pipeline.go:80` буквально написано «тесты, будущий web-режим» |
| Новое событие `CheckpointPending` в `Recorder` | ~50 | без него веб не может показать «жду решения» (Н-4) |
| Живой лог агента | ~230 | логи уже пишутся в `.ai-team/logs`, эндпоинта нет |
| `GET`/`PUT /api/config` | ~300 | `config.Load` + `Validate` + `Marshal` уже есть, включая строгую валидацию |
| Граф этапов в вебе | ~110 | заблокирован не вебом, а моделью конфига (раздел 4) |
| Проброс target-каталога в `Server` | ~15 | структурная предпосылка для всех write-функций |
| Рендер `checks`/`mutations`/`delivery` во фронте | ~30 | API их уже отдаёт; сейчас `grep delivery web/src` не находит ничего |

**Минимальное изменение, дающее сразу три вещи** (петлю без TTY, апрув из веба,
живой лог): запускать `pipeline.RunWithResult` горутиной внутри веб-процесса через
существующие швы `WithRecorder` / `WithPrompter`, добавив `WebPrompter` и событие
`CheckpointPending`. Single-flight уже обеспечен workspace-локом.

## 8. Порядок работ

Последовательность сведена с `CODEX-PLAN.MD` (обоснование расхождений — раздел
11). После каждого шага проект остаётся рабочим.

**Шаг 0. Разблокировать проверяемость.** Полдня, и без этого шага нельзя
достоверно сказать «стало лучше».

- **0a. Починить `npm audit`** (Н-9): либо pin `react-router-dom@7.11.0`, либо
  `overrides` в `package.json`, либо задокументированное исключение для этого
  advisory (RSC-режима в SPA нет). Пока это не сделано, `make verify` и CI-джоб
  `frontend` красные, а `lint`/`test`/`build` фронта локально даже не запускаются.
- **0b. Починить `init` → `run`** (Н-1). Решение из `CODEX-PLAN.MD` §4.1 лучше
  моего: писать `.ai-team/` в `.git/info/exclude` и **не трогать tracked
  workspace** при обычном `init`, а для желающих закоммитить общее правило
  добавить явный `--write-gitignore`. Плюс E2E `init → run` **без** ручного
  `git add .gitignore` — иначе тесты продолжат маскировать баг (Н-10).

**Шаг 1. Удалить бесспорно мёртвое** (корзина 1, уже без таблицы `events` и без
Hub): ~770 строк Go + 5 531 строка markdown. Нулевой риск. Критерий: `make verify`
проходит, греп по удалённым именам пуст.

**Шаг 2. Ввести approval как доменную сущность** — самый ценный шаг, закрывает
Н-2 и Н-4 сразу. Из `CODEX-PLAN.MD` §2–§3 берётся модель, из моего обзора —
конкретные места в коде:

- typed `PendingApproval` / `ApprovalDecision`: кто решил, **в какой роли**, что
  именно было показано, точный `subject_hash`, действие, комментарий, timestamp;
- отвязать loopback и checkpoint от `Prompter.Interactive()`: ядро фиксирует
  предмет approval, создаёт persisted-запрос и переводит run в
  `waiting_for_approval` — вместо `pipeline.go:1749`, где решение и способ его
  получить сейчас одно и то же;
- действия для `CHANGES_REQUESTED`: `return_to_coder`, `reject`,
  `request_information`, `override_approve`. Технический loopback после
  `return_to_coder` выполняется автоматически, но **санкционирует его человек**;
- CLI становится одним из транспортов решения, а не единственным.

Критерий: неинтерактивный прогон на `CHANGES_REQUESTED` не падает, а встаёт в
`waiting_for_approval`; решение, поданное **без TTY**, возвращает работу coder-у и
продолжает **тот же** run.

**Шаг 3. `RunEngine` + persisted state machine** (`CODEX-PLAN.MD` §5, §6.1).
Вынести владение runs из `cmd/ai-team`; CLI и HTTP используют один engine.
Состояния: `queued → running → waiting_for_approval → revising → running →
blocked → completed` + терминальные `failed/rejected/canceled/interrupted`.
Restart восстанавливает тот же run, его lineage и pending approvals — это же
закрывает Н-5 (`--retry-from` перестаёт быть созданием логически нового рана).

**Шаг 4. Write API + мост событий** (`CODEX-PLAN.MD` §6.2–§6.4 + gap-таблица
раздела 5):

- `POST /api/runs`, `POST /api/runs/{id}/approvals/{aid}/decisions`,
  `POST /api/runs/{id}/cancel`, `POST /api/runs/{id}/resume`;
- read API дополнительно отдаёт pending approvals, allowed actions, required
  role, subject hash и тот самый diff/candidate, который человек подтверждает;
- **единый versioned event contract** и одно хранилище событий вместо двух
  несовместимых (Н-11); мост «читать persisted events по `sequence` →
  `hub.BroadcastEvent`» (~50–80 строк, схема таблицы уже готова); исправить
  `pipeline_completed` во фронте; polling оставить как fallback до появления
  cursor/replay;
- **защита write API обязательна в этом же шаге**: session token, проверка
  Origin/Host, CSRF, audit actor. Пока API только читает, DNS-rebinding из
  находки №4 прошлого аудита — утечка; с появлением `POST /api/runs` это
  становится запуском произвольного пайплайна в чужом репозитории;
- фронт: страница pending approvals + рендер `checks`/`mutations`/`delivery`
  (~30 строк, бэкенд за это уже платит).

**Шаг 5. Граф в конфиге** (раздел 4): ~350 строк переписать, ~700 удалить.
В `CODEX-PLAN.MD` этого нет вовсе — это моя часть. Делать **после** approvals
(рёбра должны уметь вести к «ждёт решения») и **до** схлопывания ролей.

**Шаг 6. Схлопнуть AI-роли 7 → 5** + починить промпты (см. корзину 4 и оговорку
про человеческие роли в разделе 11).

**Шаг 7. Candidate worktree** (`CODEX-PLAN.MD` §7, P2) — вместо простого «убрать
хеширование дерева»: отдельный worktree на run, immutable candidate identity,
привязка review/checks/approvals/delivery к одному candidate hash, инвалидация
устаревших approvals после мутации, live workspace не меняется до promotion.
Хеширование дерева при этом не «удаляется», а **становится ненужным**.

**Шаг 8. Срезать корзину 2** — только после того, как фронт рисует чеки:
`report` / консольные `ui`-поверхности / `notifier` / `eval`. ~1 670 строк.

**Шаг 9. Упростить (не удалить) delivery/evidence**: одно хранилище событий вместо
двух, одна сверка digest вместо трёх, убрать `ControllerIdentity` и immutable
`config.json`/`workflow.json`. `--approve-plan` и сверку digest перед коммитом
**оставить** — при асинхронном approval они становятся несущими.

**Шаг 10. Спеки: 50 → 8–12**, удалить архив, оставить одну копию `/opsx`,
добавить `openspec/project.md`.

### Ожидаемый итог

Честная оценка после сверки: **не «в два раза меньше кода»**. Уходит ~770 строк
мёртвого + ~1 670 дублирующих поверхностей + ~1 000–1 200 от упрощения
delivery/evidence и legacy-конфига ≈ **−3 500**. Но добавляется approval-модель,
`RunEngine`, write API с защитой, граф и candidate worktree ≈ **+1 500…2 000**.
Итого Go: с 17 026 до примерно **13 000–14 000** — при том что появятся граф,
управление из веба и петля без TTY, которых сейчас нет. Markdown: с 11 590 до
~3 000.

Мой первоначальный расчёт «до 9 000–10 000» был получен при допущении, что
evidence и часть delivery-гарантий вырезаются целиком. Это допущение снято:
при асинхронных approvals у них появляется настоящий читатель.

### Метрики готовности (взято из `CODEX-PLAN.MD` §10)

Оценивать не числом абстракций, а вертикальными результатами:

- `init → первый pending approval` без ручной правки workspace;
- каждый значимый переход имеет exact human approval;
- живое событие доезжает в веб за 1–2 секунды;
- reconnect WebSocket восстанавливает события без дубликатов;
- restart продолжает **тот же** run;
- approval по устаревшему subject/candidate всегда отклоняется;
- задача доходит до draft PR **без доступа к TTY**;
- deterministic checks и delivery-гарантии при этом сохранены.

## 11. Сверка с `CODEX-PLAN.MD`

Два документа смотрят на один проект с противоположных сторон и почти не
конфликтуют: этот обзор — **вычитающий** («что убрать и почему проект уехал от
замысла», с числами), `CODEX-PLAN.MD` — **строящий** («что построить и в каком
порядке», с продуктовой моделью). Ниже — что взято, что уточнено и где реальное
расхождение.

### 11.1. Независимое совпадение — четыре находки

Найдены обоими независимо, разными методами (я — живым прогоном, план — чтением
кода). Это существенно повышает достоверность:

| находка | здесь | `CODEX-PLAN.MD` |
|---|---|---|
| `init → run` не работает | Н-1 | §4.1 |
| loopback завязан на TTY | Н-2 | §4.2 |
| веб — read-only витрина | раздел 5 | §4.3 |
| WebSocket без продюсера | Н-3 | §4.4 |

Совпадает и вывод «не строить сейчас»: OS-sandbox backends, quotas, network
allow-list, новые языковые адаптеры и delivery-провайдеры — преждевременны
(раздел 6 здесь, §8 там).

### 11.2. Что взято из плана — и почему оно лучше моего

1. **`npm audit` роняет `make verify`** (§4.5). Я этого не заметил, потому что
   не запускал полную цепочку. Подтвердил лично → Н-9. Это единственная находка
   плана, которая делает всю остальную работу непроверяемой, поэтому она стала
   шагом 0a.
2. **E2E маскируют `init → run`** (§4.1). Я обошёл проблему руками и не проверил,
   делают ли то же тесты. Делают → Н-10. Отсюда требование «E2E без ручного
   коммита» в шаге 0b.
3. **Решение для `init`** (§4.1): `.git/info/exclude` + `--write-gitignore`, то
   есть «не трогать tracked workspace вообще». Строго лучше моего варианта
   «пусть `init` сам коммитит `.gitignore`»: инструмент не должен создавать
   коммиты в чужом репозитории на этапе установки.
4. **Typed `PendingApproval` / `ApprovalDecision`** (§2). Существенно сильнее
   моего «добавить `CheckpointPending` в `Recorder`»: решение фиксирует actor,
   **роль**, показанный предмет, subject hash, действие и комментарий. Мой
   вариант дал бы вебу видимость паузы, но не аудируемое решение.
5. **Полная state machine рана** (§5) и вывод, что restart не должен требовать
   `--retry-from`. Я нашёл симптом (Н-5: осколочные раны в дашборде), план
   объясняет причину: run не является durable resumable сущностью.
6. **`RunEngine`, которым владеют и CLI, и HTTP** (§6.1). Чище моей формулировки
   «перенести пайплайн в веб-процесс»: у меня CLI неявно становился вторым
   сортом, здесь оба остаются равноправными транспортами.
7. **Защита write API** (§6.4): session token, CSRF, Origin/Host, audit actor.
   В моём обзоре этого не было вовсе — прямой пробел. Существенно: пока API
   только читает, DNS-rebinding из находки №4 прошлого аудита — утечка данных;
   с появлением `POST /api/runs` та же дыра означает запуск произвольного
   пайплайна в репозитории пользователя.
8. **Candidate worktree до sandbox** (§7). Я рекомендовал закрыть proposal
   `strict-sandbox-and-candidate-isolation`, забрав только «убрать хеширование
   дерева». План аргументирует лучше: worktree полезен **не как безопасность**, а
   потому что даёт одну сущность, к которой относятся review, checks, approval и
   delivery, упрощает retry/recovery и **делает полные снапшоты дерева
   ненужными**. Это не удаление сложности, а её замена на более дешёвую.

### 11.3. Чего в плане нет — и это надо добавить именно из этого обзора

- **Граф переходов в конфиге отсутствует как тема.** `CODEX-PLAN.MD` сохраняет
  линейный pipeline и навешивает на него approvals. Замысел #3 (вершины и рёбра
  в конфиге) в плане не адресован ни разу. Раздел 4 здесь — единственное место,
  где он проработан, включая целевой YAML и цену перехода.
- **Числа.** План не оценивает объёмы: что сколько стоит в строках, какой пакет
  сколько занимает, где именно дублирование. Без этого «упростить» не операционно.
- **Инвентарь мёртвого кода** (корзина 1) — `replay.go` 345, `suite.go` 100,
  `NewRegistry`, `NotifierChain`, Vite-скелет 190, `X-Total-Count`.
- **Дублирующие поверхности** (корзина 2, ~1 670 строк): `pkg/report`, консольный
  прогресс-бар/статус-бар, `pkg/notifier`, `ai-team eval`. План их не видит,
  потому что смотрит вперёд, а не по сторонам.
- **Восемь синтаксисов checkpoint**, из которых `interactive` и
  `require_explicit` поведенчески идентичны (проверено лично). Для введения
  `PendingApproval` это прямо релевантно: иначе новая модель унаследует восемь
  способов сказать одно и то же.
- **Мета-процесс**: 11 590 строк markdown, 50 спек, `agent-orchestration`,
  нормативно **запрещающая** граф. Если оставить спеки как есть, они будут
  сопротивляться и графу, и approvals.
- **Дефекты промптов**: coder ссылается на недоступную ему спецификацию, verifier
  обязан сверяться с `design.md`, которого нет в его inputs, у `proposal.md` с AC
  нет ни одного читателя. Это дешёвые правки с прямым влиянием на качество.
- **Эмпирика**: pty-прогон, доказывающий что петля работает; снимки API на 7-й и
  19-й секунде; два независимых хешера дерева; отсутствие `.ai-team/` в самом
  репозитории.

### 11.4. Единственное реальное расхождение

`CODEX-PLAN.MD` §11: «Сильная сторона проекта — реальные deterministic checks,
evidence и строгая delivery. **Их не нужно упрощать.**»
Этот обзор (корзина 3, шаг 9) предлагал срезать ~1 400–1 600 строк evidence и
delivery.

**Разрешение — в пользу плана, но не целиком.** Мои вердикты были верны для
*сегодняшней* архитектуры: `events.jsonl` действительно не имеет читателя,
`checkpointSubjectHash` печатает хеш, который никто не сверяет, тройная сверка
digest избыточна для человека, который сам себе противник. Но целевая
архитектура плана **создаёт этим механизмам настоящих читателей**:

- асинхронный approval из браузера → `subject_hash` становится единственной
  защитой от решения по устаревшему предмету;
- WS-мост с replay по `sequence` → у event-лога появляется первый потребитель;
- решение, принятое другим актором через минуты → повторная сверка workspace
  digest перед коммитом перестаёт быть паранойей.

Поэтому итоговая позиция: **сохранить механизмы, но не их дублирование.** Одно
хранилище событий вместо двух (файл ИЛИ SQLite-таблица), одна сверка digest
вместо трёх, `subject_hash` — поле `ApprovalDecision`, а не строка в консоль.
Под удаление остаётся только то, у чего читателя не появляется ни в одной схеме:
`ControllerIdentity`, immutable `config.json`/`workflow.json`, `replay.go`.

### 11.5. Одна оговорка, которую надо решить сознательно

План вводит **человеческие роли** (Product Owner, Architect, Developer,
Reviewer, QA, Release Manager) — каждая санкционирует свой переход. Этот обзор
предлагает схлопнуть AI-роли 7 → 5, убрав `tester` и `verifier` как отдельные
стадии.

Это частично конфликтует: убрав стадию `tester`, вы убираете и естественную
точку approval для роли **QA**, а убрав `verifier` — вторую точку для
**Reviewer**. Конфликт разрешается тем, что approval привязывается не к стадии,
а к переходу: одна ревью-стадия после checks может создавать **два** pending
approval (Reviewer и QA) на один и тот же candidate. Но это надо спроектировать
явно, а не получить случайно. Если человеческие роли действительно нужны в
продукте (а по плану они — центральная часть), то схлопывание AI-ролей стоит
делать **после** шага 2, когда approvals уже отвязаны от стадий, — как и
предписано порядком в разделе 8.
