# Демонстрация S17: сквозной локальный сценарий

Реальной дев/стейдж-среды у проекта нет, поэтому демонстрация идёт **локально** на
собранном бинаре: настоящий `ai-team web` в локальном режиме, браузер (Playwright)
как человек, затем те же ключевые действия по сетевому MCP. Всё, что нельзя взять
настоящим, заменено явной заглушкой (см. «Заглушки»). Секретов и сети не нужно,
кроме одного `docker pull` закреплённого образа alpine.

## Как повторить

Нужны Go (минимум из `go.mod`, `setup.sh` собирает бинарь тулчейном-пином из `.tool-versions`, как `make`), Node.js 22+, Git, Docker с работающим демоном.

```bash
bash scripts/demo/run-demo.sh                       # весь сценарий, окружение во временном каталоге
DEMO_PORT=18527 bash scripts/demo/run-demo.sh       # другой порт, если 18080 занят
DEMO_REAL_CLIENTS=1 bash scripts/demo/run-demo.sh   # плюс настоящие claude и codex
DEMO_KEEP=1 bash scripts/demo/run-demo.sh           # не удалять окружение (журнал сервера — web.log)
```

Скрипт идемпотентен: каждый запуск пересоздаёт окружение, по завершении гасит сервер и
удаляет контейнеры демо. Каталог окружения удаляется только если он создан демо (маркер
`.ai-team-demo`); пустой `DEMO_HOME`, `/`, `$HOME` и его предки отклоняются
(`scripts/demo/lib/guard.sh`, проверка — `bash scripts/demo/lib/guard_test.sh`). Контейнеры демо
находятся двумя отдельными запросами по меткам `ai-team.stage-attempt` и `ai-team.gate-attempt`
(несколько `--filter label=` объединяются по И) и удаляются, только если в них смонтирован каталог
этого демо. Код возврата 0 означает, что все проверки сценария прошли.
Прогон занимает 10–15 минут (Docker-гейты и контейнерный ревьюер стартуют контейнеры).
На macOS запускайте под `caffeinate -i`, чтобы машина не засыпала посреди сценария.

| Файл | Назначение |
|---|---|

## Что проходит и что нет

Последний полный прогон на macOS (Docker Desktop, Go 1.26.9 по пину `.tool-versions`, Playwright Chromium):

| Часть | Итог |
|---|---|
| Web UI, основной сценарий | **30/30** проверок |
| Сетевой MCP (скрипт на JSON-RPC) | **10/10** проверок |
| Web UI, цикл код-ревью (внешний и внутренний) | **6/6** проверок |
| Claude Code 2.1.300: `whoami`, `list_projects`, действие `create_backlog_item` | работает (реальный клиент, локальный токен, `Authorization: Bearer`) |
| Codex CLI 0.162.1: `whoami` | работает (`bearer_token_env_var`, `--skip-git-repo-check`) |

Персональные токены `aitm_…` и роли облачного режима с настоящими клиентами **не**
проверялись: токены выпускает только браузерная сессия облачного режима. Их покрывают
Go-тесты с клиентом официального SDK (`pkg/web/mcp_e2e_test.go`, `mcp_actions_*_test.go`,
`TestMCPParityMatrix`). Подключение через claude.ai connectors не проверялось. Настоящие
клиенты в этой среде выполнили чтения и одно действие; полный сценарий они не проходили,
его проходит скрипт на JSON-RPC с теми же вызовами.

## Откуда берутся команды

Гейты `external_program` и `docker_program` (команда на хосте, образ и mounts контейнера),
`executor_adapters`, `checks` и `mcp_servers` задают программы, которые запускает хост, поэтому
они берутся **только из файлового конфига репозитория** (`.ai-team/config.yaml`, правится как код).
Шаблон, присланный через REST, MCP или страницу «Шаблон», с такими гейтами отклоняется
(`400`, код `trusted_config_only`), а определения адаптеров, проверок и серверов принимаются, только
если совпадают с уже заданными в файловом конфиге: этап вправе сослаться на них по имени. Поэтому демо
кладёт полный шаблон в файловый конфиг, а через UI публикует короткие шаблоны цикла код-ревью:
внешний ссылается на адаптер `container-review` из файлового конфига по имени (доверенная ссылка),
внутренний команд не содержит. Короткие шаблоны несут инфраструктурные секции
(`tracker`, `cli`, `effort`, `stage_timeout`) без изменений: веб принимает отличия только в
процессных полях (S18), пропущенная или изменённая секция даёт `trusted_config_only`. В фазе `loops` сценарий дополнительно проверяет отказ: публикация
полного демо-шаблона с командными гейтами через REST возвращает `400 trusted_config_only`, активный
шаблон не меняется. Из-за этого страница «Шаблон» не годится для правки шаблона с командными гейтами:
его правят в файле.

## Заглушки и что не проверялось

- **GitHub нет.** Commit и push выполняет настоящий Git в локальный bare-репозиторий
  (`state/origin.git`); PR создаёт заглушка `gh` с выдуманными адресами
  (`https://example.test/demo/repo/pull/N`). Реальные `gh pr create`, защита ветки и CI не проверялись.
- **Jira нет.** Трекер — встроенный фейковый адаптер; внешние изменения подаёт файл
  `tracker/inbox.jsonl` (переменная `AI_TEAM_FAKE_TRACKER_DIR`, только для демо и локального запуска).
  Каталог моста — локальный доверенный канал: кто может писать в него, тот подаёт «внешний» статус
  (он всё равно проходит через контроллер и правила `tracker.inbound`); файлы открываются без следования
  символьным ссылкам, а при усечении inbox чтение начинается с начала. Jira-адаптер покрыт
  контрактными тестами на моках (`pkg/tracker/jira_test.go`), живая Jira не использовалась.
- **Модели нет.** Рантайм `opencode` заменён детерминированным моком; LLM-гейт и агенты
  `demo-coder`, `demo-reviewer` отвечают по заготовке. Качество настоящих агентов демо не оценивает.
- **CoreKit не подключался.** Внешний контейнерный ревьюер — воспроизводимая фикстура
  `e2etest/container-review-agent`; реального образа CoreKit нет.
- Проверено только на macOS; Linux и Windows не запускались.

## Известные ограничения

Найдено демонстрацией и **не исправлено**:

1. **Возврат из ревью → повторная доставка той же ветки невозможна.** Если `code_review`
   вернул задачу на `implementation` в шаблоне с `delivery`, второй план не строится:
   планировщик требует «чистую ветку от base» (`pkg/delivery/planner.go`), а в ветке уже есть
   доставленный коммит. Задача останавливается с понятной ошибкой на этапе реализации. Поэтому
   цикл ревью показан на коротких шаблонах без доставки. Чтобы он работал с доставкой, нужна
   поддержка обновления уже открытого PR (коммит поверх, fast-forward push, повторное использование PR).
2. **Встроенные агенты и этапы, которые ведёт человек.** Если у этапа `executor: human` указан
   `agent` со встроенным контрактом (`tester`, `analyst`, `observer`), агент ищет вход (например,
   `design.md`), которого человек не создаёт, и задача падает на этапе. В демо-шаблоне такие этапы
   не привязаны к агентам.
3. **Агент реализации и PR-этап.** Первый не-Markdown выход агента на этапе `link_kind: pr`
   принимается за ссылку на PR; агент с дополнительным не-Markdown выходом ломает гейты `pr_*`.
   Демо-агент отдаёт diff как `change-diff.md`.
4. **Переход без `human_approval`.** В шаблоне v6 без гейта `human_approval` после успешных гейтов
   всё равно ждёт подтверждение перехода (справочник говорит, что подтверждения нет). Автоматически
   переходы подтверждает только режим `auto`.
5. **Окружение при прогоне.** При засыпании машины контроллер «замирает» на минуты посреди этапа
   (замечено без `caffeinate`). Если подтверждение записалось, а задача не пошла дальше, страница
   предлагает «Продолжить задачу», и сценарий нажимает её сам. Порт 18080 бывает занят чужим
   сервером: тогда задайте `DEMO_PORT`.
6. Docker-тесты `pkg/stageexec` при общем демоне и `pkg/gaterun TestRelativeProgramAndCWD`
   нестабильны и перепроверяются одиночно.

## Демо `gate → bundle → verify` (без модели)

Файлы для демонстрации `ai-team gate` без модели и API-ключей на небольшом Python-репозитории.
Пошаговое руководство с разбором сценариев и подключением к GitHub Actions —
[Проверки в CI без модели](../guides/ci-gate.md).

Быстрый запуск из корня ai-team (нужны `bash`, `git` и Go 1.26.9+):

```bash
bash docs/demo/run-demo.sh
```

Ожидаемый итог: `pass=0 (0), policy-fail=1 (1), junit-fail=1 (1)`.

| Файл | Назначение |
|---|---|
| [`run-demo.sh`](run-demo.sh) | Собирает ai-team, создаёт временный репозиторий и прогоняет три сценария |
| [`gate.yaml`](gate.yaml) | Конфигурация gate: `test_modify: required` и проверка `junit-xml` |
| [`pytest-pass.xml`](pytest-pass.xml), [`pytest-fail.xml`](pytest-fail.xml) | Готовые JUnit-отчёты вместо настоящего запуска pytest |
| [`ci-gate-demo.yaml`](ci-gate-demo.yaml) | Workflow GitHub Actions с зафиксированной версией ai-team; `go-version` в нём должна соответствовать сборке ai-team |
