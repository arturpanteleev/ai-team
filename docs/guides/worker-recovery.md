# Worker recovery and workspace continuity

The first supported continuity model uses a **shared persistent workspace volume**. Every worker eligible for a job must mount the same project volume at the same canonical absolute path. The web process, scheduler workers, and replacement workers must also point to the same persistent scheduler database, web database, and artifact store. Recovery from a copied archive on an unrelated path is not supported in this version.

The scheduler filters claims by the worker's canonical target path. A mismatched worker leaves the job queued. Each claim has a unique lease token; only the current token may renew or complete the job. If a worker process exits, its lease expires and another compatible worker can claim the same durable job. The former owner cannot complete that queue record after reassignment.

The first claim runs the original `start` admission. A reclaimed start is delivered as `recover`. The worker checks the durable lifecycle checkpoint: if creation never committed it runs `start`; if the run exists it resumes that exact run from its checkpoint. Explicit human resume remains a separate `resume` operation. This prevents replaying start against an existing run identity. If the evidence directory exists but `run_started` was not yet appended, recovery validates its immutable manifest and snapshots, appends the missing initial event, then creates lifecycle state. If candidate worktree creation stopped before candidate metadata was saved, recovery reconstructs metadata only when the existing detached worktree matches the same repository and exact current baseline commit.

Pipeline lifecycle state, evidence, candidate files, approvals, and project configuration remain on the shared workspace. The run's workspace lock serializes pipeline execution. Lease loss cancels the worker subprocess; only the current lease holder may publish queue completion. A browser reload only reconnects to the web process and does not affect a run. A web-process restart reconstructs queue projections from the durable queue. A worker-process loss expires its lease and causes recovery on another compatible worker. `run_finished` alone does not complete a recovered job when evidence contains a deferred-delivery marker: recovery validates the durable delivery record or runs the existing delivery reconciliation path first. A delivery outage leaves the queue job visibly `failed`; failed jobs are not automatically reclaimed, and this version has no queue retry operation, so an operator must use the supported delivery/recovery workflow or explicitly create a new admission after assessing the durable run.

Back up the shared workspace, scheduler database, web database, and artifact store as one recovery set. This implementation does not make a local filesystem volume a multi-region storage system, and it does not claim exactly-once behavior for external Git hosting or CI effects. Delivery steps must continue to use their own idempotency checks and persisted evidence.

Recovery is covered by separate boundary tests: `TestPipelineWorkerCrashRecovery` kills a real pipeline process during a live stage and resumes the run without replaying its completed stage; `TestClaimForTargetAndKilledWorkerRecovery` kills a queue claimant and verifies lease reclaim and stale-completion rejection; `TestRecoverInitialLifecycleRebuildsOnlyRunStartedCheckpoint` and `TestRecoverInitialLifecycleRebuildsRunManifestBeforeRunStarted` cover both initial evidence checkpoints; `TestCreateRecoversWorktreeCreatedBeforeMetadata` covers orphan worktree setup; `TestRecoveryDispatchCompletesQueueFromFinishedEvidenceBeforeTerminalLifecycle` covers lifecycle reconciliation; `TestRecoveryDispatchDoesNotCompleteJobBeforeDeferredDelivery` covers interruption between `run_finished` and delivery completion; and `TestPollerRequiresFixedWorkerTarget` rejects unconstrained executors. These are not yet a single end-to-end test connecting a live-stage kill to lease reclaim and resumed pipeline execution. The split keeps pipeline's same-package scripted runtime fixture isolated: scheduler depends on pipeline, so importing scheduler into pipeline tests would create an import cycle; moving that fixture across package boundaries would duplicate substantial harness code. External Git/PR/CI provider effects are not guaranteed exactly once by these tests or this recovery design.
