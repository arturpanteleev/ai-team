# Конфигурация

Вся настройка проекта живёт в одном файле — `.ai-team/config.yaml`. Его
создаёт `ai-team init`. Здесь описаны все поля, профили `init` и то, как
рантайм агента получает ключи провайдера.

> [!IMPORTANT]
> Единственный источник истины — файл, который `init` создал в вашем проекте.
> Примеры на этой странице сокращены, чтобы показать структуру.

## Как читается конфиг

Контроллер строго проверяет конфиг до первого вызова модели. Отклоняются:

- неизвестные и повторяющиеся поля, несколько YAML-документов в файле;
- `schema_version`, отличная от `4`; конфиги схем 1–3 больше не
  поддерживаются;
- неизвестный рантайм в `cli`, недопустимый `effort`, непарсящиеся длительности;
- неоднозначные переходы, недостижимые этапы, циклы без ограничения
  `max_visits`;
- некорректные проверки (`checks`) и пути.

Ошибки выводятся списком, сразу все:

```text
невалидный config.yaml:
  - effort "max" недопустим (low|medium|high)
  - stage_timeout "soon" не парсится (пример: 30m)
```

## Пример

Так выглядит начало конфига профиля `standard`, который `init` создаёт в
Go-проекте (переходы сокращены):

```yaml
schema_version: 4
pipeline:
  - name: analyst
  - name: architect
  - name: coder
  - name: reviewer
  - name: tester
    checks:
      - name: go-test
        class: unit
        adapter: go-test-json
        command: [go, test, -json, -count=1, ./...]
        policy: required
        timeout: 20m
      - name: go-vet
        class: lint
        command: [go, vet, ./...]
        policy: required
        timeout: 10m
  - name: verifier
  - name: deployer
workflow:
  entry: analyst
  max_visits: {coder: 3, reviewer: 3, tester: 3, verifier: 3}
  edges:
    - from: analyst
      outcome: passed
      to: architect
      approval:
        roles: [product_owner]
        quorum: any
        actions: {approve: architect, reject: $stop}
        deferred: true
    # остальные переходы passed задаются так же
    - from: deployer
      outcome: passed
      to: $complete
    - from: reviewer
      outcome: rejected
      to: coder
      approval:
        roles: [reviewer]
        quorum: any
        actions:
          return_to_coder: coder
          override_approve: tester
          reject: $stop
cli: opencode
effort: medium
stage_timeout: 30m
```

## Поля верхнего уровня

| Поле | Обязательно | По умолчанию | Что задаёт |
|---|---|---|---|
| `schema_version` | да | — | версия схемы; поддерживается только `4` |
| `pipeline` | да | — | список этапов (агентов) и их настроек; см. [ниже](#этапы-pipeline) |
| `workflow` | да | — | граф переходов между этапами и подтверждения; см. [ниже](#переходы-workflow) |
| `cli` | нет | из определения агента (у встроенных — `opencode`) | рантайм агента: `opencode`, `codex` или `claude` |
| `model` | нет | выбирает рантайм | модель; `auto` или пусто — на усмотрение рантайма |
| `effort` | нет | — (`init` пишет `medium`) | усилие модели: `low`, `medium`, `high` |
| `stage_timeout` | нет | `30m` | таймаут одного этапа; см. [лимиты](#лимиты-времени-и-попыток) |
| `preflight_timeout` | нет | `60s` | бюджет одной внешней команды preflight |
| `delivery_timeout` | нет | `10m` | бюджет всей поставки: commit, push и PR |
| `budget` | нет | `24h`, `100` | жёсткие лимиты всего прогона; см. [лимиты](#лимиты-времени-и-попыток) |
| `redaction` | нет | блок экспорта включён | правила поиска секретов |
| `retention` | нет | `720h`, `20` | умолчания для `ai-team gc` |
| `tree_hash` | нет | — | дополнительные каталоги, которые не входят в хеш дерева |
| `containment` | нет | `trusted-local` | профиль изоляции; см. предупреждение ниже |

Длительности пишутся в формате Go: `90s`, `30m`, `2h`.

### Бюджет preflight

Поле `preflight_timeout` — бюджет одной внешней команды preflight: запроса версии рантайма, вызовов `git`
и `gh`. Превышение даёт проваленную обязательную проверку, и прогон не
стартует. Поднимите значение, если рантайм долго стартует: холодный старт
`opencode` занимает секунды против долей секунды у прогретого, и слишком
тесный бюджет делает рабочий рантайм неотличимым от отсутствующего.

```yaml
preflight_timeout: 60s
```

### Бюджет поставки

Поле `delivery_timeout` ограничивает всю поставку целиком: `git commit`, `git push` и `gh pr view/create` вместе. Поставка идёт уже после того, как вы подтвердили план и прогон завершился, поэтому лимит времени прогона (`budget.max_wall_time`) её не обрывает. Но её команды сетевые, и без своего срока зависший `git` или `gh` держал бы контроллер бесконечно.

Поставку прерывает исчерпание этого бюджета или сигнал процессу (`Ctrl-C`). Значения по умолчанию хватает с запасом: поставка до живого remote занимает секунды. Поднимите его для медленной сети или очень больших push.

```yaml
delivery_timeout: 10m
```

Команды поставки работают без вопросов в терминале (`GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, askpass-хуки не наследуются): у контроллера нет терминала, и запрос пароля превратился бы в зависание. Если для доступа к remote нужна своя настройка SSH, задайте `GIT_SSH_COMMAND` — поставка её уважает.

### Лимиты времени и попыток

Прогон ограничен всегда, даже если в конфиге нет ни одного из полей ниже: значения по умолчанию применяет код, а не только `init`.

| Поле | По умолчанию | Что ограничивает |
|---|---|---|
| `budget.max_wall_time` | `24h` | общее время прогона, включая ожидание ваших решений |
| `budget.max_attempts` | `100` | суммарное число попыток всех этапов |
| `stage_timeout` | `30m` | время одного этапа; `init` пишет это значение явно |
| `timeout` (у этапа в `pipeline`) | значение `stage_timeout` | время конкретного этапа, перекрывает общее |

```yaml
budget:
  max_wall_time: 24h
  max_attempts: 100
stage_timeout: 30m
```

Сутки по умолчанию выбраны так, чтобы прогон пережил ожидание человека: «запустил вечером, подтвердил утром» не упирается в лимит. Если прогоны идут без человека (CI, пакетный запуск), уменьшите `max_wall_time` до нескольких часов.

Превышение лимита прогона останавливает его с причиной, где назван лимит: `run budget: превышен max_wall_time 24h` или `run budget: превышен лимит попыток max_attempts=100`. Превышение `stage_timeout` — таймаут одного этапа, а не конец прогона: его можно продолжить через `ai-team run --resume <run_id>`.

Неверное или неположительное значение длительности отвергается проверкой конфига до первого вызова модели.

### redaction

Правила поиска секретов в доказательствах для `ai-team redact`, `export` и
`gate`. По умолчанию экспорт с найденными секретами запрещён.

| Поле | Что делает |
|---|---|
| `include`, `exclude` | glob-шаблоны путей относительно корня репозитория |
| `disable_export_block` | `true` разрешает экспорт даже с находками; не рекомендуется |
| `scan_sensitive_fields`, `raw_logs` | зарезервированы: принимаются, но пока ни на что не влияют |

### retention

Умолчания для `ai-team gc`. Флаги командной строки важнее.

| Поле | По умолчанию | Что делает |
|---|---|---|
| `older_than` | `720h` | убирать завершённые прогоны старше этого |
| `keep_last` | `20` | всегда сохранять столько последних прогонов |
| `prune_runs` | `false` | разрешить удаление доказательств прогонов с проверенным экспортом |

### tree_hash

`ignore_dirs` — простые имена каталогов (без `/` и шаблонов), которые
добавляются к стандартному списку исключений при хешировании дерева.
Например, каталог кеша сборки.

```yaml
tree_hash:
  ignore_dirs: [.cache, node_modules]
```

### containment

Допустимые значения — `trusted-local` и `strict`.

> [!WARNING]
> В текущей версии секция `containment` принимается конфигом, но её значение
> не применяется: прогон всегда идёт с профилем `trusted-local`. Профиль
> `trusted-local` — это ограничения на уровне приложения, а не песочница ОС.
> Подробнее — в [Граница безопасности](security.md).

## Этапы pipeline

Каждый элемент `pipeline` — этап конвейера. Имя должно совпадать с агентом
из реестра (`ai-team list`). Можно написать просто имя строкой или объект:

| Поле | Что задаёт |
|---|---|
| `name` | имя агента, обязательно |
| `cli`, `model`, `effort` | переопределяют глобальные значения для этого этапа |
| `timeout` | таймаут этапа вместо `stage_timeout` |
| `checks` | проверки, которые контроллер запускает после этапа |

Что делает каждый встроенный агент — в [Агенты и этапы](pipeline.md).

### Проверки (checks)

Проверки запускает контроллер, а не модель. Обязательные (`required`)
проверки должны пройти, иначе поставка запрещена.

| Поле | Что задаёт |
|---|---|
| `name` | имя проверки, уникальное внутри этапа |
| `class` | вид: `formatter`, `lint`, `build`, `unit`, `integration`, `e2e`, `coverage`, `race`, `security` |
| `command` | команда списком аргументов, без shell |
| `adapter` | как читать результат: `command` (по коду выхода, по умолчанию), `go-test-json`, `junit-xml` |
| `report_file` | путь к JUnit XML внутри проекта; только для `junit-xml` |
| `policy` | `required` или `optional` |
| `timeout` | таймаут проверки |
| `working_dir` | каталог запуска внутри проекта |

`go-test-json` требует команду вида `[go, test, -json, ...]`. Адаптеры
`go-test-json` и `junit-xml` допустимы только для классов `unit`,
`integration` и `e2e`.

```yaml
- name: tester
  checks:
    - name: pytest
      class: unit
      adapter: junit-xml
      command: [pytest, --junitxml=report.xml]
      report_file: report.xml
      policy: required
      timeout: 15m
```

Пошаговая настройка для разных стеков — в
[Настроить проверки проекта](../guides/project-checks.md).

## Переходы workflow

`workflow` описывает граф: какой этап идёт после какого и где нужен человек.

| Поле | Что задаёт |
|---|---|
| `entry` | первый этап |
| `max_visits` | сколько раз можно зайти в этап; ограничивает циклы возврата |
| `edges` | список переходов |

Переход (`edges[]`):

| Поле | Что задаёт |
|---|---|
| `from` | этап-источник |
| `outcome` | исход этапа; встроенные профили используют `passed` и `rejected`, схема допускает также `failed`, `blocked`, `canceled`, `skipped`, `warning` |
| `to` | следующий этап или `$complete` |
| `approval` | подтверждение человека на этом переходе, необязательно |

Подтверждение (`approval`):

| Поле | Что задаёт |
|---|---|
| `roles` | какие роли могут решать: `product_owner`, `architect`, `developer`, `reviewer`, `qa`, `release_manager` |
| `quorum` | `any` — достаточно одной роли, `all` — нужны все |
| `actions` | действия и куда они ведут; `$stop` останавливает прогон |
| `deferred` | `true` — не останавливаться, а подтвердить вместе с поставкой |

Подтверждение поставки — отдельное и обязательное всегда. Его нельзя
отключить конфигом. Подробнее — в [Агенты и этапы](pipeline.md#где-решает-человек).

## Профили init

Флаг `ai-team init --profile` выбирает, как часто спрашивать человека.

| Профиль | Этапы | Подтверждения переходов | Когда выбирать |
|---|---|---|---|
| `standard` (по умолчанию) | `analyst → architect → coder → reviewer → tester → verifier → deployer` | отложенные: одно решение вместе с поставкой, `quorum: any` | обычный режим: одно решение на фичу |
| `fast` | `analyst → coder → tester → reviewer → deployer` | отложенные, как в `standard`; `max_visits` — 2 | прототипы и внутренние фичи, где хочется быстрее |
| `regulated` | как в `standard` | пошаговые: каждый переход ждёт человека, `quorum: all`; `max_visits` — 2 | рискованные изменения, где нужен контроль на каждом шаге |

В `fast` нет этапов `architect` и `verifier`. Вместо отдельной верификации
`init` кладёт в проект переопределённого агента
`.ai-team/agents/reviewer/`: он делает ревью и верификацию за один проход.

Переходы возврата (`rejected → coder`) не откладываются ни в одном профиле:
если ревьюер или тестировщик вернул работу, решение нужно сразу.

```bash
ai-team init --profile regulated
```

## Runtime и ключи

Агент работает через внешний CLI-рантайм. Его выбирает поле `cli`.

| Рантайм | `cli:` | Выбор модели | Что проверяет preflight |
|---|---|---|---|
| OpenCode | `opencode` (по умолчанию) | `-m <model>` или `auto` | `opencode --version`, ключи провайдера и их разрешение, Git-репозиторий |
| Codex | `codex` | `-m <model>` или `auto` | `codex --version`; авторизация Codex (токен или `CODEX_API_KEY`), sandbox `workspace-write` |
| Claude Code | `claude` | `--model <model>` или `auto` | `claude --version`; `ANTHROPIC_API_KEY` или подписка, `--permission-mode acceptEdits` |

Каждый рантайм ставится и настраивается отдельно от ai-team. Пошагово —
в учебнике [Подключить настоящую модель](../tutorial/real-model.md).

### Изолированное окружение

Рантайм запускается в изолированном окружении. У каждого свой временный
каталог настроек на время запуска: `XDG_CONFIG_HOME` у OpenCode, `CODEX_HOME`
у Codex, `CLAUDE_CONFIG_DIR` у Claude. В процесс попадают только базовые
переменные ОС (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `PWD`, `LANG`,
`LC_ALL`, `LC_CTYPE`, `TMPDIR`, `TERM`, `COLORTERM`, `NO_COLOR`) и
переменные, которые вы разрешили по имени.

### Передать ключ провайдера

Ключ в вашем shell **не виден** агенту, пока вы не разрешите его имя в
`AI_TEAM_HARNESS_ENV_ALLOW` (несколько имён — через запятую). Иначе прогон
упадёт на авторизации, хотя тот же CLI отдельно работает.

```bash
export ANTHROPIC_API_KEY='<ваш-ключ>'
AI_TEAM_HARNESS_ENV_ALLOW=ANTHROPIC_API_KEY ai-team run --feature add-jwt-auth --task "…"
```

Разрешённая переменная передаётся в процесс рантайма вместе со значением.
ai-team не пишет значение в логи, отчёты и доказательства. Старое имя
`AI_TEAM_OPENCODE_ENV_ALLOW` работает так же.

## Другие переменные окружения

| Переменная | Что делает |
|---|---|
| `AI_TEAM_HARNESS_ENV_ALLOW` | имена переменных, которые можно передать рантайму |
| `AI_TEAM_AGENT_PATH` | дополнительные каталоги агентов (список через `:`), слой между проектом и пользователем |
| `AI_TEAM_AUTH_SECRET` | секрет облачной аутентификации дашборда (имя меняется флагами `--auth-secret-env` и `--secret-env`) |

Агенты ищутся по слоям: `.ai-team/agents/` проекта, каталоги из
`AI_TEAM_AGENT_PATH`, пользовательский каталог `ai-team/agents` в системном
каталоге настроек, затем встроенные. Как разрешаются конфликты слоёв — в
[архитектуре](../ARCHITECTURE.md#layered-agent-registry).
