# Конфигурация

Вся настройка проекта живёт в одном файле — `.ai-team/config.yaml`. Его
создаёт `ai-team init`. Здесь описаны все поля, профили `init` и то, как
рантайм агента получает ключи провайдера.

> [!IMPORTANT]
> Единственный источник истины — файл, который `init` создал в вашем проекте.
> Примеры на этой странице сокращены, чтобы показать структуру.

## Как читается конфиг

Контроллер строго проверяет конфиг до первого вызова модели. Отклоняются:

- неизвестные и повторяющиеся поля, несколько YAML-документов в файле;
- конфиги схемы, отличной от `5`; v4 явно отклоняется с подсказкой о запуске
  `ai-team init --force` или ручном переносе;
- уникальность ID этапов, наличие ссылочных агентов и допустимость результатов,
  ссылок и возвратов;
- неизвестный рантайм в `cli`, недопустимый `effort`, непарсящиеся длительности;
- некорректные проверки (`checks`) и пути.

Ошибки выводятся списком, сразу все:

```text
невалидный config.yaml:
  - effort "max" недопустим (low|medium|high)
  - stage_timeout "soon" не парсится (пример: 30m)
```

## Пример

Ниже сокращённый фрагмент профиля `standard`, который `init` создаёт в
Go-проекте:

```yaml
schema_version: 5
template: idea-to-prod
title: От идеи до продакшена
stall_after: 24h
stages:
  - id: intent
    title: Бизнес-идея
    function: bo
    result: approve
    executor: human
  - id: product_spec
    title: Продуктовая спецификация
    function: po
    result: md
    executor: human
    agent: analyst
    required_sections: [Критерии приёмки]
  - id: tech_design
    title: Техническое решение
    function: architect
    result: md
    executor: agent
    agent: architect
    confirm: required
  - id: implementation
    title: Реализация
    function: developer
    result: link
    link_kind: pr
    executor: human
    agent: coder
    delivery:
      require_checks: [go-test, go-vet]
  - id: acceptance
    title: Окончательная готовность
    function: bo
    result: approve
    executor: human
returns:
  - {from: tech_design, to: product_spec}
  - {from: implementation, to: tech_design}
checks:
  - name: go-test
    class: unit
    adapter: go-test-json
    command: [go, test, -json, -count=1, ./...]
    policy: required
  - name: go-vet
    class: lint
    command: [go, vet, ./...]
    policy: required
cli: opencode
effort: medium
stage_timeout: 30m
```

## Поля верхнего уровня

| Поле | Обязательно | По умолчанию | Что задаёт |
|---|---|---|---|
| `schema_version` | да | — | версия схемы; поддерживается только `5` |
| `template` | да | — | ID единственного шаблона процесса проекта |
| `title` | да | — | название шаблона для людей |
| `stages` | да | — | упорядоченные этапы шаблона; см. [ниже](#этапы-шаблона) |
| `returns` | нет | — | разрешённые возвраты между этапами; только назад по списку |
| `max_visits` | нет | `3` | лимиты повторов для этапов, куда ведут возвраты |
| `stall_after` | нет | — | срок, после которого незавершённый run считается застоявшимся |
| `checks` | нет | — | проверки проекта, доступные delivery-переходам |
| `cli` | нет | из определения агента (у встроенных — `opencode`) | рантайм агента: `opencode`, `codex` или `claude` |
| `model` | нет | выбирает рантайм | модель; `auto` или пусто — на усмотрение рантайма |
| `effort` | нет | — (`init` пишет `medium`) | усилие модели: `low`, `medium`, `high` |
| `stage_timeout` | нет | `30m` | таймаут одного этапа; см. [лимиты](#лимиты-времени-и-попыток) |
| `preflight_timeout` | нет | `60s` | бюджет одной внешней команды preflight |
| `delivery_timeout` | нет | `10m` | бюджет всей delivery: commit, push и PR |
| `budget` | нет | `24h`, `100` | жёсткие лимиты всего прогона; см. [лимиты](#лимиты-времени-и-попыток) |
| `redaction` | нет | блок экспорта включён | правила поиска секретов |
| `retention` | нет | `720h`, `20` | умолчания для `ai-team gc` |
| `tree_hash` | нет | — | дополнительные каталоги, которые не входят в хеш дерева |
| `containment` | нет | `trusted-local` | профиль изоляции; см. предупреждение ниже |

Длительности пишутся в формате Go: `90s`, `30m`, `2h`.

### Бюджет preflight

Поле `preflight_timeout` — бюджет одной внешней команды preflight: запроса версии рантайма, вызовов `git`
и `gh`. Превышение даёт проваленную обязательную проверку, и прогон не
стартует. Поднимите значение, если рантайм долго стартует: холодный старт
`opencode` занимает секунды против долей секунды у прогретого, и слишком
тесный бюджет делает рабочий рантайм неотличимым от отсутствующего.

```yaml
preflight_timeout: 60s
```

### Бюджет delivery

Поле `delivery_timeout` ограничивает всю delivery целиком: `git commit`, `git push` и `gh pr view/create` вместе. Delivery идёт после подтверждения плана; её команды сетевые, и без отдельного срока зависший `git` или `gh` держал бы контроллер бесконечно.

Delivery прерывает исчерпание этого бюджета или сигнал процессу (`Ctrl-C`). Значения по умолчанию хватает с запасом: delivery до живого remote занимает секунды. Поднимите его для медленной сети или очень больших push.

```yaml
delivery_timeout: 10m
```

Команды delivery работают без вопросов в терминале (`GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, askpass-хуки не наследуются): у контроллера нет терминала, и запрос пароля превратился бы в зависание. Если для доступа к remote нужна своя настройка SSH, задайте `GIT_SSH_COMMAND` — delivery её уважает.

### Лимиты времени и попыток

Прогон ограничен всегда, даже если в конфиге нет ни одного из полей ниже: значения по умолчанию применяет код, а не только `init`.

| Поле | По умолчанию | Что ограничивает |
|---|---|---|
| `budget.max_execution_time` | `24h` | время одного исполнения pipeline до паузы или завершения |
| `budget.max_attempts` | `100` | суммарное число попыток всех этапов |
| `stage_timeout` | `30m` | время одного этапа; `init` пишет это значение явно |
| `timeout` (у агента этапа) | значение `stage_timeout` | время конкретного этапа, перекрывает общее |

```yaml
budget:
  max_execution_time: 24h
  max_attempts: 100
stage_timeout: 30m
```

`max_execution_time` применяется заново к каждому вызову `run` или `run --resume`. Пауза в ожидании решения человека не расходует этот лимит; длительность задачи в отчёте при этом считается от её первоначального создания и включает все паузы. Старое `budget.max_wall_time` продолжает приниматься как устаревший псевдоним для одного исполнения. Задавать оба ключа одновременно нельзя.

Превышение лимита исполнения останавливает текущий вызов с причиной `run budget: превышен max_execution_time 24h`; задачу можно продолжить через `ai-team run --resume <run_id>`, и продолжение получит новый бюджет исполнения. Перебор суммарных попыток останавливает задачу с причиной `run budget: превышен лимит попыток max_attempts=100`. Превышение `stage_timeout` — таймаут одного этапа, а не конец задачи: её можно продолжить через `ai-team run --resume <run_id>`.

Неверное или неположительное значение длительности отвергается проверкой конфига до первого вызова модели.

### Usage и подписка

По умолчанию `ai-team usage <run_id>` показывает только входные, выходные и суммарные токены. Если runtime (включая OpenCode) не предоставил полный attested usage, вместо нулей выводится `нет данных`. Денежная доля необязательна и считается только при явной настройке месячной стоимости подписки:

```yaml
usage:
  monthly_subscription_amount: 20
  monthly_subscription_currency: USD
```

Показываемая сумма — приблизительное распределение стоимости подписки пропорционально токенам этого run среди записанных usage за тот же UTC-месяц. Это не цена API и не счёт за отдельный запрос. Если месячная сумма, полный usage или знаменатель недоступны, команда пишет `оценка недоступна`. Сводки формата v1 читаются для совместимости, но их токены считаются неизвестными: прежний формат мог помечать частичную сумму полной.

### redaction

Правила поиска секретов в доказательствах для `ai-team redact`, `export` и
`gate`. По умолчанию экспорт с найденными секретами запрещён.

| Поле | Что делает |
|---|---|
| `include`, `exclude` | glob-шаблоны путей относительно корня репозитория |
| `disable_export_block` | `true` разрешает экспорт даже с находками; не рекомендуется |
| `scan_sensitive_fields`, `raw_logs` | зарезервированы: принимаются, но пока ни на что не влияют |

### retention

Умолчания для `ai-team gc`. Флаги командной строки важнее.

| Поле | По умолчанию | Что делает |
|---|---|---|
| `older_than` | `720h` | убирать завершённые прогоны старше этого |
| `keep_last` | `20` | всегда сохранять столько последних прогонов |
| `prune_runs` | `false` | разрешить удаление доказательств прогонов с проверенным экспортом |

### tree_hash

`ignore_dirs` — простые имена каталогов (без `/` и шаблонов), которые
дополнительно исключаются из workspace identity digest. По умолчанию исключены
только `.git` и `.ai-team`; каталоги сборки и зависимостей входят в digest.
Эта настройка не меняет mutation guard: он всегда видит все каталоги проекта.
Например, так можно исключить кеш, который не является частью identity проекта.

```yaml
tree_hash:
  ignore_dirs: [.cache, node_modules]
```

### containment

Допустимые значения — `trusted-local` и `strict`.

> [!WARNING]
> В текущей версии секция `containment` принимается конфигом, но её значение
> не применяется: прогон всегда идёт с профилем `trusted-local`. Профиль
> `trusted-local` — это ограничения на уровне приложения, а не песочница ОС.
> Подробнее — в [Граница безопасности](security.md).

## Этапы шаблона

`stages` задаёт единственный процесс проекта. ID этапа — отдельный от имени
агента ключ, а список определяет порядок обычных переходов.

| Поле | Что задаёт |
|---|---|
| `id` | уникальный ID этапа |
| `title` | название для людей |
| `function` | отвечающая за этап функция, например `po`, `architect` или `qa` |
| `result` | тип результата: `md`, `link` или `approve` |
| `executor` | `human` (по умолчанию) или `agent` |
| `agent` | существующий агент из `ai-team list`, если для этапа доступно исполнение агентом |
| `link_kind` | для `result: link`: `pr`, `build` или `other` |
| `required_sections` | обязательные заголовки, только для `result: md` |
| `check` | проверка результата: `{kind: hard, rules: [...]}` или `{kind: agent, agent: ...}` |
| `confirm` | `required` или `auto`; по умолчанию `auto` для `approve`, иначе `required` |
| `skippable` | можно ли пропустить этап с причиной; по умолчанию `false` |
| `delivery` | требования delivery для PR-этапа с указанным `agent`, например `require_checks: [go-test]` |

Если указан `executor: agent`, поле `agent` обязательно. Все agent-ссылки,
включая `check.agent`, проверяются по registry. `required_sections` нельзя
задавать для `link` или `approve`.

Шаблон содержит возвраты между этапами. `to` должен быть раньше `from` в
списке `stages`; для каждого этапа, в который ведёт возврат, действует лимит
`max_visits` (по умолчанию 3). Граф строится контроллером из порядка этапов и
списка `returns`, поэтому отдельный раздел `workflow` в конфиге отсутствует.

### Проверки (checks)

Проверки запускает контроллер, а не модель. Определения находятся на верхнем
уровне конфига; PR delivery может ссылаться на них по имени. Обязательные
(`required`) проверки должны пройти до delivery.

| Поле | Что задаёт |
|---|---|
| `name` | уникальное имя проверки проекта |
| `class` | `formatter`, `lint`, `build`, `unit`, `integration`, `e2e`, `coverage`, `race` или `security` |
| `command` | команда списком аргументов, без shell |
| `adapter` | чтение результата: `command`, `go-test-json` или `junit-xml` |
| `report_file` | путь к JUnit XML; только для `junit-xml` |
| `policy` | `required` или `optional` |
| `timeout` | таймаут проверки |
| `working_dir` | каталог запуска внутри проекта |

`go-test-json` требует команду вида `[go, test, -json, ...]`. Адаптеры
`go-test-json` и `junit-xml` допустимы только для классов `unit`,
`integration` и `e2e`.

Пошаговая настройка для разных стеков — в
[Настроить проверки проекта](../guides/project-checks.md).

### Переход с v4

Конфиг schema v4 больше не загружается. Выполните `ai-team init --force`,
чтобы создать встроенный шаблон заново, либо перенесите настройки вручную по
примеру выше. `init` без `--force` сохраняет существующий конфиг.

## Профили init

Флаг `ai-team init --profile` материализует один из трёх шаблонов в
`.ai-team/config.yaml`.

| Профиль | Этапы | Подтверждения переходов | Когда выбирать |
|---|---|---|---|
| Профиль | ID шаблона | Отличие |
|---|---|---|
| `standard` (по умолчанию) | `idea-to-prod` | стандартные `confirm`, лимит возвратов — 3 |
| `fast` | `idea-to-prod-fast` | все этапы с `confirm: auto`, лимит возвратов — 2 |
| `regulated` | `idea-to-prod-regulated` | все этапы с `confirm: required`, лимит возвратов — 2 |

Каждый профиль хранит обычный список этапов и возвратов; специальные runtime-
режимы профиля не сохраняются. Встроенный `idea-to-prod` включает этапы от
`intent` до `acceptance`.

```bash
ai-team init --profile regulated
```

## Runtime и ключи

Агент работает через внешний CLI-рантайм. Его выбирает поле `cli`.

| Рантайм | `cli:` | Выбор модели | Что проверяет preflight |
|---|---|---|---|
| OpenCode | `opencode` (по умолчанию) | `-m <model>` или `auto` | `opencode --version`, ключи провайдера и их разрешение, Git-репозиторий |
| Codex | `codex` | `-m <model>` или `auto` | `codex --version`; способ входа (API-ключ / подписка / не найден), sandbox `workspace-write` |
| Claude Code | `claude` | `--model <model>` или `auto` | `claude --version`; способ входа (API-ключ / подписка / не найден), `--permission-mode acceptEdits` |

Каждый рантайм ставится и настраивается отдельно от ai-team. Пошагово —
в учебнике [Подключить настоящую модель](../tutorial/real-model.md).

### Изолированное окружение

Рантайм запускается в изолированном окружении. У каждого свой временный
каталог настроек на время запуска: `XDG_CONFIG_HOME` у OpenCode, `CODEX_HOME`
у Codex, `CLAUDE_CONFIG_DIR` у Claude. В процесс попадают только базовые
переменные ОС (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `PWD`, `LANG`,
`LC_ALL`, `LC_CTYPE`, `TMPDIR`, `TERM`, `COLORTERM`, `NO_COLOR`) и
переменные, которые вы разрешили по имени.

### Передать ключ провайдера

Ключ в вашем shell **не виден** агенту, пока вы не разрешите его имя в
`AI_TEAM_HARNESS_ENV_ALLOW` (несколько имён — через запятую). Иначе прогон
упадёт на авторизации, хотя тот же CLI отдельно работает.

```bash
export ANTHROPIC_API_KEY='<ваш-ключ>'
AI_TEAM_HARNESS_ENV_ALLOW=ANTHROPIC_API_KEY ai-team run --feature add-jwt-auth --task "…"
```

Разрешённая переменная передаётся в процесс рантайма вместе со значением.
ai-team не пишет значение в логи, отчёты и доказательства. Старое имя
`AI_TEAM_OPENCODE_ENV_ALLOW` работает так же.

Для Claude Code вместо API-ключа можно использовать подписку Claude: получите
`CLAUDE_CODE_OAUTH_TOKEN` командой `claude setup-token`. Claude-адаптер
передаёт эту переменную только в процесс Claude Code; добавлять её в
`AI_TEAM_HARNESS_ENV_ALLOW` не нужно. Обычный `ANTHROPIC_API_KEY` по-прежнему
передаётся только после явного разрешения имени переменной.

Для Codex можно войти через подписку ChatGPT командой `codex login`. Если
`CODEX_API_KEY` или `OPENAI_API_KEY` не разрешён и не передаётся рантайму,
адаптер копирует `~/.codex/auth.json` во временный `CODEX_HOME` с правами
`0600`; временный каталог имеет права `0700` и удаляется после этапа. Файл
авторизации не выводится в логи. Preflight показывает только способ входа,
не значение токена, и не проверяет действительность учётных данных у сервиса.

## Другие переменные окружения

| Переменная | Что делает |
|---|---|
| `AI_TEAM_HARNESS_ENV_ALLOW` | имена переменных, которые можно передать рантайму |
| `AI_TEAM_WORKER_ENV_ALLOW` | имена переменных, которые контроллер передаёт disposable worker; его runtime получает тот же список |
| `AI_TEAM_AGENT_PATH` | дополнительные каталоги агентов (список через `:`), слой между проектом и пользователем |
| `AI_TEAM_AUTH_SECRET` | секрет облачной аутентификации дашборда (имя меняется флагами `--auth-secret-env` и `--secret-env`) |

Агенты ищутся по слоям: `.ai-team/agents/` проекта, каталоги из
`AI_TEAM_AGENT_PATH`, пользовательский каталог `ai-team/agents` в системном
каталоге настроек, затем встроенные. Как разрешаются конфликты слоёв — в
[архитектуре](../ARCHITECTURE.md#layered-agent-registry).
