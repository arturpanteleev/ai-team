# Конфигурация

Вся настройка проекта живёт в одном файле — `.ai-team/config.yaml`. Его
создаёт `ai-team init`. Здесь описаны все поля, профили `init` и то, как
рантайм агента получает ключи провайдера.

> [!IMPORTANT]
> Единственный источник истины — файл, который `init` создал в вашем проекте.
> Примеры на этой странице сокращены, чтобы показать структуру.

В веб-интерфейсе раздел **«Шаблон»** показывает этот единственный шаблон как
последовательность этапов и возвратов. Product Owner и Architect могут
проверить YAML и опубликовать новую версию. Публикация обновляет
`.ai-team/config.yaml` и сохраняет неизменяемый экземпляр версии. Каждая
задача закрепляет версию при первом запуске; продолжение и восстановление
используют её же, а новые задачи берут текущую опубликованную версию.

## Как читается конфиг

Контроллер строго проверяет конфиг до первого вызова модели. Отклоняются:

- неизвестные и повторяющиеся поля, несколько YAML-документов в файле;
- конфиги схемы, отличной от `5` и `6`; v4 явно отклоняется с подсказкой о запуске
  `ai-team init --force` или ручном переносе;
- уникальность ID этапов, наличие ссылочных агентов и допустимость результатов,
  ссылок и возвратов;
- неизвестный рантайм в `cli`, недопустимый `effort`, непарсящиеся длительности;
- некорректные проверки (`checks`) и пути.

Ошибки выводятся списком, сразу все:

```text
невалидный config.yaml:
  - effort "max" недопустим (low|medium|high)
  - stage_timeout "soon" не парсится (пример: 30m)
```

## Пример

Ниже сокращённый фрагмент профиля `standard`, который `init` создаёт в
Go-проекте:

```yaml
schema_version: 6
template: idea-to-prod
title: От идеи до продакшена
stall_after: 24h
stages:
  - id: intent
    title: Бизнес-идея
    function: bo
    result: approve
    executor: human
  - id: product_spec
    title: Продуктовая спецификация
    function: po
    result: md
    executor: human
    agent: analyst
    exit_gate_groups:
      - - gate: required_sections
          version: 1
          params: {sections: [Критерии приёмки]}
      - - gate: agent_review
          version: 1
          params: {agent: spec-checker, mode: grill, max_rounds: 3}
      - [human_approval@1]
  - id: tech_design
    title: Техническое решение
    function: architect
    result: md
    executor: agent
    agent: architect
    exit_gate_groups:
      - - gate: agent_review
          version: 1
          params: {agent: verifier}
      - [human_approval@1]
  - id: implementation
    title: Реализация
    function: developer
    result: link
    link_kind: pr
    executor: human
    agent: coder
    exit_gate_groups:
      - [pr_exists@1, pr_open@1, pr_base_branch@1]
      - [human_approval@1]
    delivery:
      require_checks: [go-test, go-vet]
  - id: acceptance
    title: Окончательная готовность
    function: bo
    result: approve
    executor: human
returns:
  - {from: tech_design, to: product_spec}
  - {from: implementation, to: tech_design}
checks:
  - name: go-test
    class: unit
    adapter: go-test-json
    command: [go, test, -json, -count=1, ./...]
    policy: required
  - name: go-vet
    class: lint
    command: [go, vet, ./...]
    policy: required
cli: opencode
effort: medium
stage_timeout: 30m
```

## Поля верхнего уровня

| Поле | Обязательно | По умолчанию | Что задаёт |
|---|---|---|---|
| `schema_version` | да | — | версия схемы: `6` (текущая) или `5` (совместимая, см. [перенос v5 → v6](#гейты-этапа-и-перенос-на-схему-v6)) |
| `template` | да | — | ID единственного шаблона процесса проекта |
| `title` | да | — | название шаблона для людей |
| `stages` | да | — | упорядоченные этапы шаблона; см. [ниже](#этапы-шаблона) |
| `returns` | нет | — | разрешённые возвраты между этапами; только назад по списку |
| `max_visits` | нет | `3` | лимиты повторов для этапов, куда ведут возвраты |
| `stall_after` | нет | — | срок, после которого незавершённый run считается застоявшимся |
| `forbid_self_approval` | нет | `false` | запретить участнику подтверждать этап, который он сам брал или сдавал; см. [права по функциям](#права-по-функциям) |
| `checks` | нет | — | проверки проекта, доступные delivery-переходам |
| `mcp_servers` | нет | — | именованные stdio MCP-серверы Codex; этапы выбирают их явно |
| `executor_adapters` | нет | — | именованные доверенные внешние исполнители этапа; этап выбирает один полем `adapter`; см. [внешний исполнитель этапа](#внешний-исполнитель-этапа) |
| `cli` | нет | из определения агента (у встроенных — `opencode`) | рантайм агента: `opencode`, `codex` или `claude` |
| `model` | нет | выбирает рантайм | модель; `auto` или пусто — на усмотрение рантайма |
| `effort` | нет | — (`init` пишет `medium`) | усилие модели: `low`, `medium`, `high` |
| `stage_timeout` | нет | `30m` | таймаут одного этапа; см. [лимиты](#лимиты-времени-и-попыток) |
| `gate_concurrency` | нет | `4` | сколько гейтов одной группы работают одновременно (1..64); см. [гейты этапа](#гейты-этапа-и-перенос-на-схему-v6) |
| `preflight_timeout` | нет | `60s` | бюджет одной внешней команды preflight |
| `delivery_timeout` | нет | `10m` | бюджет всей delivery: commit, push и PR |
| `budget` | нет | `24h`, `100` | жёсткие лимиты всего прогона; см. [лимиты](#лимиты-времени-и-попыток) и [бюджет токенов](#бюджет-токенов) |
| `auto_pickup` | нет | выключен | автоподбор задач из бэклога; см. [автоподбор](#автоподбор-задач) |
| `tracker` | нет | — | исходящая интеграция с трекером задач; см. [Внешний трекер задач](#внешний-трекер-задач) |
| `cicd` | нет | — | CI/CD-провайдер этапа выкладки; см. [TeamCity](#выкладка-через-teamcity) |
| `notifications` | нет | — | уведомления о событиях задач; см. [уведомления](#уведомления-webhook-slack-e-mail) |
| `redaction` | нет | блок экспорта включён | правила поиска секретов |
| `retention` | нет | `720h`, `20` | умолчания для `ai-team gc` |
| `tree_hash` | нет | — | дополнительные каталоги, которые не входят в хеш дерева |
| `containment` | нет | `trusted-local` | профиль изоляции; см. предупреждение ниже |

Длительности пишутся в формате Go: `90s`, `30m`, `2h`.

### Бюджет preflight

Поле `preflight_timeout` — бюджет одной внешней команды preflight: запроса версии рантайма, вызовов `git`
и `gh`. Превышение даёт проваленную обязательную проверку, и прогон не
стартует. Поднимите значение, если рантайм долго стартует: холодный старт
`opencode` занимает секунды против долей секунды у прогретого, и слишком
тесный бюджет делает рабочий рантайм неотличимым от отсутствующего.

```yaml
preflight_timeout: 60s
```

### Бюджет delivery

Поле `delivery_timeout` ограничивает всю delivery целиком: `git commit`, `git push` и `gh pr view/create` вместе. Delivery идёт после подтверждения плана; её команды сетевые, и без отдельного срока зависший `git` или `gh` держал бы контроллер бесконечно.

Delivery прерывает исчерпание этого бюджета или сигнал процессу (`Ctrl-C`). Значения по умолчанию хватает с запасом: delivery до живого remote занимает секунды. Поднимите его для медленной сети или очень больших push.

```yaml
delivery_timeout: 10m
```

Команды delivery работают без вопросов в терминале (`GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, askpass-хуки не наследуются): у контроллера нет терминала, и запрос пароля превратился бы в зависание. Если для доступа к remote нужна своя настройка SSH, задайте `GIT_SSH_COMMAND` — delivery её уважает.

### Лимиты времени и попыток

Прогон ограничен всегда, даже если в конфиге нет ни одного из полей ниже: значения по умолчанию применяет код, а не только `init`.

| Поле | По умолчанию | Что ограничивает |
|---|---|---|
| `budget.max_execution_time` | `24h` | время одного исполнения pipeline до паузы или завершения |
| `budget.max_attempts` | `100` | суммарное число попыток всех этапов |
| `stage_timeout` | `30m` | время одного этапа; `init` пишет это значение явно |
| `timeout` (у агента этапа) | значение `stage_timeout` | время конкретного этапа, перекрывает общее |

```yaml
budget:
  max_execution_time: 24h
  max_attempts: 100
stage_timeout: 30m
```

`max_execution_time` применяется заново к каждому вызову `run` или `run --resume`. Пауза в ожидании решения человека не расходует этот лимит; длительность задачи в отчёте при этом считается от её первоначального создания и включает все паузы. Старое `budget.max_wall_time` продолжает приниматься как устаревший псевдоним для одного исполнения. Задавать оба ключа одновременно нельзя.

Превышение лимита исполнения останавливает текущий вызов с причиной `run budget: превышен max_execution_time 24h`; задачу можно продолжить через `ai-team run --resume <run_id>`, и продолжение получит новый бюджет исполнения. Перебор суммарных попыток останавливает задачу с причиной `run budget: превышен лимит попыток max_attempts=100`. Превышение `stage_timeout` — таймаут одного этапа, а не конец задачи: её можно продолжить через `ai-team run --resume <run_id>`.

Неверное или неположительное значение длительности отвергается проверкой конфига до первого вызова модели.

### Бюджет токенов

Расход токенов (input + output) можно ограничить на задачу и на сутки. По умолчанию лимитов нет.

| Поле | По умолчанию | Что ограничивает |
|---|---|---|
| `budget.max_task_tokens` | `0` (без лимита) | токены одной задачи |
| `budget.max_daily_tokens` | `0` (без лимита) | токены всех задач инстанса за сутки UTC |

```yaml
budget:
  max_task_tokens: 2000000
  max_daily_tokens: 20000000
```

Бюджет проверяется перед каждой попыткой агента, которая вызывает модель, и перед каждым запуском агента-проверяющего этапа (включая раунды grill); этапы доставки токенов не расходуют и не останавливаются. Расход проверяющих записывается в `.ai-team/runs/<run>/checker-usage/` и входит и в бюджет задачи, и в дневной. Перед вызовом модели проверяющий оставляет маркер начала; если процесс умер посреди вызова, при resume маркер без итоговой записи превращается в запись с неизвестным расходом — задача останавливается, а дневной итог этих суток становится неизвестным. Идущий прямо сейчас проверяющий (как и попытка агента до публикации манифеста) в дневной итог попадает только по завершении. Записи пишутся атомарно (временный файл, fsync, link). Ровно на лимите бюджет считается исчерпанным. Расход берётся из attempt-манифестов в `.ai-team/runs`, а не из памяти процесса, поэтому рестарт сервера дневной счётчик не сбрасывает. Попытка относится к суткам UTC своего завершения; граница суток — `00:00 UTC` независимо от пояса хоста.

Если расход неизвестен (рантайм не сообщил подтверждённый usage, манифест повреждён или у disposable-worker нет полного локального evidence), лимит считается исчерпанным: проверка fail-closed.

При исчерпании задача пишет событие `budget_exceeded` (`scope`: `task` или `daily`, `tokens_used`, `limit`, `usage_unknown`, для суток — `day`) и встаёт на паузу: статус `stopped`, в событии `run_paused` — `reason: budget_exceeded`. Сама она не продолжается. Продолжить её может только человек — `ai-team run --resume <run_id>` или `POST /api/runs/{runID}/resume`. Resume сам по себе новый бюджет **не выдаёт**: после остановки по бюджету задачи обычный resume снова остановит задачу перед вызовом модели (новое `budget_exceeded`). Ещё один бюджет того же размера, отсчитанный от расхода в момент последней остановки, выдаётся только явным решением человека с причиной: в вебе — `POST /api/runs/{runID}/resume` с телом `{"grant_budget_allowance": true, "reason": "<причина>"}` (кнопка «Выдать бюджет и продолжить»), в CLI — `ai-team run --resume <run_id> --grant-budget-allowance "<причина>"`. Выдача пишется в evidence событием `budget_allowance_granted` (`actor_id`, `reason`, `baseline_tokens`) и действует на одну остановку; следующая остановка снова требует решения. Дневной бюджет не выдаётся и не сбрасывается никогда: при resume он проверяется заново, и в те же сутки UTC задача снова остановится, даже с выдачей.

Лимиты закрепляются вместе с шаблоном задачи при её создании, поэтому изменение конфига не меняет бюджет уже созданных задач. Если пауза случилась перед проверяющим уже завершённой попытки этапа, resume не повторяет оплаченную попытку, а запускает только проверку на выданный бюджет. Перед этим resume сверяет попытку: манифест связан с `attempt_finished`, а копия каждого выхода в evidence и файл в рабочей директории совпадают с хешем из манифеста. Если выход поправили после остановки, проверка не запускается и этап не перезапускается: задача снова встаёт на паузу (`run_paused` с `reason: pending_check_output_changed`) — верните файл или отмените задачу. Повтор этапа платный и происходит только по решению человека (возврат, новая версия после проваленной проверки) — тогда этапу нужен бюджет на попытку и на проверяющего; если одна попытка этапа вместе с проверяющим не помещается в `max_task_tokens`, задача через проверку не пройдёт и будет останавливаться на каждом повторе: поднимите лимит для новых задач. Веб-resume пишет событие `run_resume_requested` с `actor_id` и признаком `budget_allowance_granted`, который равен `true` только при явной выдаче (тогда в событии есть и `reason`). Выдача без причины отклоняется (`400`), выдача без непокрытой остановки по бюджету задачи (в том числе после дневной остановки) — `409`. Веб считает остановку покрытой уже по `run_resume_requested` с `budget_allowance_granted: true`: если задача упала после этого события, но до записи `budget_allowance_granted` в evidence, повторная выдача через веб даёт `409`, а обычный resume снова остановит задачу. В этом случае выдайте бюджет через CLI (`--grant-budget-allowance` сверяется с evidence задачи и без непокрытой остановки отказывает до запуска). Disposable worker записывает `budget_allowance_granted` через worker API только в resume-job, где контроллер передал явную выдачу: автор и причина должны совпадать с ней, выдача в операции одна, а `baseline_tokens` равен расходу последней непокрытой остановки в проверенной цепочке событий; иначе запись отвергается. Деталь задачи в API (`GET /api/pipelines/{id}`) отдаёт `budget_allowance_grantable` — можно ли сейчас выдать бюджет; кнопка выдачи показывается только тогда.

Ограничения:

- В режиме `--worker-command` (disposable worker) у worker нет полного локального evidence: при заданном `budget.max_daily_tokens` дневной расход неизвестен и **все** задачи останавливаются перед первым вызовом модели. В этом режиме дневной бюджет не задавайте.
- Нечитаемый (повреждённый) attempt-манифест или запись проверяющего нельзя отнести ни к каким суткам, поэтому дневной расход остаётся неизвестным и дневной бюджет блокирует задачи до ручного исправления файла. Запись с неподтверждённым расходом блокирует только сутки UTC, к которым относится. Свои записи проверяющих ai-team пишет атомарно, поэтому частичный JSON возникает только при внешнем повреждении.

### Автоподбор задач

Секция `auto_pickup` включает подбор задач из чернового бэклога веб-сервером (`ai-team web`).

| Поле | По умолчанию | Смысл |
|---|---|---|
| `auto_pickup.enabled` | `false` | включить подборщик |
| `auto_pickup.max_parallel_tasks` | `1` | лимит незавершённых задач инстанса |
| `auto_pickup.poll_interval` | `1m` | период проверки очереди |

```yaml
budget:
  max_task_tokens: 2000000
  max_daily_tokens: 20000000
auto_pickup:
  enabled: true
  max_parallel_tasks: 1
```

Включённый автоподбор требует `budget.max_task_tokens` и `budget.max_daily_tokens` больше нуля — иначе конфиг отвергается. Подборщик берёт только элементы бэклога со статусом `ready` (его ставит человек), по одному за проверку, в порядке пометки, и запускает их в режиме `auto`. Черновики (`draft`) и элементы с любым другим статусом не запускаются.

Незавершённой считается любая задача, чей lifecycle не terminal, включая ожидание человека и паузу по бюджету. Если слотов нет или дневной бюджет исчерпан, элемент остаётся в очереди, а в ленту пишется событие `auto_pickup_deferred` с причиной (`parallel_limit`, `daily_budget`, `budget_not_configured`) — одно на элемент, причину и сутки UTC. Неудачный запуск переводит элемент в `failed` с событием `auto_pickup_failed`; вернуть его в очередь может только человек. На одну базу `web.db` рассчитан один подборщик. Захват элемента атомарен, поэтому два процесса не возьмут один элемент, но лимит параллельных задач они проверяют независимо; второй запуск в этом случае упирается в workspace lock target и элемент становится `failed`. Автоподбор работает с локальным контроллером; режимы `--scheduler-db` и `--worker-command` режим `auto` не поддерживают, и запуск завершится `failed`.

### Usage и подписка

По умолчанию `ai-team usage <run_id>` показывает только входные, выходные и суммарные токены. Если runtime (включая OpenCode) не предоставил полный attested usage, вместо нулей выводится `нет данных`. Денежная доля необязательна и считается только при явной настройке месячной стоимости подписки:

```yaml
usage:
  monthly_subscription_amount: 20
  monthly_subscription_currency: USD
```

Показываемая сумма — приблизительное распределение стоимости подписки пропорционально токенам этого run среди записанных usage за тот же UTC-месяц. Это не цена API и не счёт за отдельный запрос. Если месячная сумма, полный usage или знаменатель недоступны, команда пишет `оценка недоступна`. Сводки формата v1 читаются для совместимости, но их токены считаются неизвестными: прежний формат мог помечать частичную сумму полной.

### Тарифы провайдера

Страница «Наблюдаемость» и `GET /api/metrics/flow` показывают стоимость по тарифу провайдера: подтверждённые токены каждой попытки агента × цена её модели. ai-team не поставляет цен: таблица тарифов пуста по умолчанию, и стоимость показывается как `нет данных` с причиной «тариф не задан». Цены вносит проект, указывая для каждой записи дату и источник:

```yaml
usage:
  tariffs:
    - model: <модель, как в model агента>
      input_per_mtok: <цена за 1M входных токенов>
      output_per_mtok: <цена за 1M выходных токенов>
      cached_input_per_mtok: <цена за 1M токенов, прочитанных из кеша>   # необязательно
      cache_write_per_mtok: <цена за 1M токенов, записанных в кеш>        # необязательно
      currency: USD
      effective_date: "YYYY-MM-DD"   # дата прайса, с которой он применяется (UTC)
      source: <ссылка на прайс провайдера>
```

- `model` сравнивается точно со значением `model` агента (или глобальным `model`), записанным в попытку. Попытка без заданной модели (использовалась модель CLI по умолчанию) и попытки, записанные до появления учёта модели, не оцениваются.
- Для попытки берётся запись её модели с самой поздней `effective_date`, не позже даты завершения попытки. Новые цены добавляются новой записью с новой датой; прежние попытки остаются оценены по прежнему тарифу.
- Кеш: claude сообщает чтение и запись в кеш отдельно от входных токенов, codex включает чтение из кеша во входные токены — расчёт учитывает обе конвенции. Если в попытке есть кешированные токены, а цены кеша в записи нет, попытка не оценивается.
- Сумма показывается, только если оценены все попытки агента выбранного периода (или этапа) и все тарифы в одной валюте; иначе — `нет данных` и причина. Неизвестное никогда не превращается в ноль.
- Готовые записи с официальными ценами Anthropic и OpenAI, датой снятия и источником — в [Официальные цены провайдеров](provider-tariffs.md).
- Стоимость по тарифу не заменяет оценку доли подписки (`monthly_subscription_amount`) и не использует `cost_usd`, который сообщает runtime: это три разных величины.

### Внешний трекер задач

Необязательная интеграция связывает задачу ai-team с одной карточкой во внешней
системе управления задачами и отправляет туда переходы и комментарии. Трекер
абстрактный: `tracker.adapter` называет адаптер, Jira — один из них (`jira`),
второй встроенный — детерминированный `fake` для тестов и демо. Интеграция
исходящая: она не читает изменения трекера и не меняет граф этапов. Адаптер
предоставляет также чтение изменений с курсором (`Tracker.Changes`), на нём
строится входящая синхронизация, но сама она здесь не включена.

```yaml
tracker:
  adapter: jira            # можно опустить, если настроен ровно один адаптер
  web_base_url: https://ai-team.example   # адрес ai-team для ссылки в комментарии
  on_enter:                # статус/переход трекера при ВХОДЕ в этап
    implementation: In Progress
  on_pass:                 # статус/переход при УСПЕШНОМ завершении этапа
    implementation: In Review
    acceptance: Done
  jira:
    base_url: https://example.atlassian.net
    email: ai-team@example.com
    token_env: AI_TEAM_JIRA_TOKEN
    web_base_url: https://ai-team.example   # устарело как место для адреса; используйте tracker.web_base_url
    auth: basic            # basic (по умолчанию: email + API token) или bearer (чистый PAT Jira Server/DC)
    api_version: 3         # 3 (по умолчанию, комментарии ADF) или 2 (простой текст, Jira Server/DC)
  fake:                    # адаптер для тестов и демо; обычно вместо jira
    statuses: [To Do, In Progress, In Review, Done]
    issues:
      - {key: DEMO-1, summary: Демо-карточка, status: To Do}
```

`on_enter` и `on_pass` сопоставляют ID этапа из единственного выбранного
шаблона/графа проекта с именем статуса трекера (Jira принимает также имя
перехода). Старое поле `tracker.jira.stage_statuses` читается как `on_pass`;
запись в `on_pass` приоритетнее. Что именно отправляется:

| Событие | Переход | Комментарий |
|---|---|---|
| вход в этап (`attempt_started`) | `on_enter[этап]`, если задан | нет |
| этап завершён (`attempt_finished`) | `on_pass[этап]`, **только** если попытка прошла: `status=passed`, `outcome=passed`, `decision` не `rejected` | всегда, с честным исходом |
| обход проверки (`check_overridden`) | нет | `outcome=overridden` |

Повторное завершение той же попытки с изменившимся результатом (гейт провалился после
успешного этапа) добавляет новое событие `attempt_finished` с `revision: N` (N ≥ 2); комментарий в трекере
содержит `revision=N` и пометку, что это исправление прежнего результата. Обратного перехода карточки нет:
если `on_pass` уже сработал по первой ревизии, статус не откатывается.

Провал, пропуск, отклонение, предупреждение и любой неизвестный исход
комментируются как есть (`outcome=failed`, `skipped`, `rejected`, …) с
пометкой, что этап не пройден; они никогда не выдаются за успех и не
переводят карточку. Тип исхода расширяем: события override/advisory следующих
спринтов добавляются без изменения планировщика. Переход, который трекер не
разрешает из текущего статуса, не мешает комментарию: оба результата
сохраняются, ошибка перехода видна оператору.

#### Связь задача — карточка

Связь хранится отдельным проверяемым полем (`tracker` + `issue_key`), а не
выводится из массива `external_links`; ссылки в `external_links` остаются
обычным справочным текстом. **У новых задач ссылка в `external_links` карточку
автоматически не связывает**: связь появляется только явным
`PUT /api/runs/{runID}/tracker/link` (автоматически переносятся лишь задачи,
существовавшие при первом старте с трекером, см. ниже). Связь строго 1:1: задача ссылается максимум на одну
карточку, карточка — максимум на одну задачу (это держит и база данных:
`PRIMARY KEY(task_id)` и `UNIQUE(tracker, issue_key)`). Без явной связи задача
в трекер ничего не отправляет.

- `PUT /api/runs/{runID}/tracker/link` с `{"issue_key":"APP-12"}` проверяет
  формат ключа (`PROJECT-123`), что карточка существует и доступна текущей
  учётной записи, и что ни задача, ни карточка не связаны с чем-то другим.
  Иначе: `400 invalid_issue_key`, `422 issue_not_found` / `issue_forbidden`,
  `502 tracker_unavailable`, `409 task_already_linked` / `issue_already_linked`.
  Повтор той же пары безопасен.
- `DELETE /api/runs/{runID}/tracker/link` снимает связь — единственный способ
  исправить конфликт: молчаливой перезаписи нет.
- Нужно право `tracker:link` (владелец продукта и архитектор).

При первом старте с настроенным трекером существующие ссылки переносятся один
раз: задача получает связь, только если адаптер распознал в её `external_links`
ровно один ключ и на этот ключ не ссылается другая задача. Всё остальное (у
задачи несколько ключей, карточка у нескольких задач) связью не становится, а
записывается как **конфликт** и показывается в `GET /api/tracker/conflicts` и в
`GET /api/runs/{runID}/tracker` (`sync_status: conflict`). Конфликт снимается
явным `PUT` или `DELETE` связи этой задачи. Повторный старт ничего не
переносит заново и не воскрешает исправленное. Перенос офлайн и не проверяет,
что карточка существует: ключ-подобное поле целиком (например `UTF-8`) будет
связано, а доставка к нему упадёт видимой ошибкой `issue_not_found`.

#### Идемпотентность, курсор, ошибки и повтор

Комментарий несёт ключ идемпотентности из ID события (`<run_id>#<event_id>`) и
ID попытки; в Jira это отдельные строки `ai-team event: <ключ>` и
`ai-team attempt: <attempt_id>`. Перед отправкой адаптер листает комментарии
карточки постранично (по 100, новые первыми, до 50 страниц) до ключа и не пишет
второй с тем же ключом, поэтому повтор события или ручной повтор дубля не
создают при любом числе комментариев; для этого токену нужно право читать
комментарии, а при сбое чтения (или карточке с более чем 5000 комментариев)
комментарий не отправляется. Переход к статусу, в котором карточка уже
находится, ничего не отправляет.

Курсор интеграции хранится в SQLite per adapter: при первом включении он
ставится на текущий край событий, затем после перезапуска повторяются
необработанные события. Если курсор не читается или не записывается при старте
`ai-team web`, интеграция в этом запуске не включается (в stderr —
предупреждение): адаптер не начинает с начала истории.

Ошибка трекера не откатывает и не блокирует локальный прогон, но не исчезает:
каждая доставка записывается в `tracker_deliveries` (статус `delivered`/`failed`,
число попыток, последняя ошибка), а сбой — ещё и warning-событием
`integration_error`. Если результат доставки не удалось сохранить, событие
остаётся в очереди, а повторы идут с экспоненциальной паузой (0,5 с, 1 с, ...
до минуты), а не каждые 250 мс. Ещё два терминальных статуса не считаются
ошибкой и не повторяются: `abandoned` (доставка не удалась, затем связь задачи
сняли — старое событие не уходит на новую карточку без явного решения) и
`superseded` (при ручном повторе по той же карточке уже выполнен более новый
переход, поэтому устаревший, например `on_enter`, пропущен, чтобы не откатить
карточку назад; комментарий идемпотентно доставляется). Более новым считается
только событие, чья доставка реально выполнила переход (`transition_to` в строке
доставки): событие с одним комментарием переход не заменяет, и повтор его
выполнит. У `superseded`/`abandoned` исходная ошибка остаётся в `last_error`, а
причина закрытия — в `note`. Ошибка содержит только класс сбоя: ни токена, ни
заголовков, ни URL, ни текста ошибки транспорта.

- `GET /api/runs/{runID}/tracker` — связь, конфликты, последние доставки и
  `sync_status` (`ok`, `failed`, `conflict`, `not_linked`, `not_configured`).
- `GET /api/tracker` — адаптер, карты, число неудачных доставок и конфликтов;
  `GET /api/tracker/deliveries?status=failed` (также `delivered`, `abandoned`,
  `superseded`), `GET /api/tracker/conflicts`.
- `POST /api/runs/{runID}/tracker/retry` повторяет все неудачные доставки
  задачи; `POST /api/runs/{runID}/tracker/deliveries/{eventID}/retry` — одну.
  Повтор идёт по текущей связи, нужен `tracker:link`; доставленное событие
  повторить нельзя (`409 delivery_not_failed`).

Аутентификация Jira выбирается полем `tracker.jira.auth`. `basic` (по умолчанию) —
`Authorization: Basic email:token`, нужен `email`. `bearer` — «чистый» personal
access token Jira Server/Data Center, отправляется как `Authorization: Bearer <токен>`;
`email` тогда необязателен. В обоих случаях секрет берётся только из переменной
окружения `token_env`, в YAML его нет, а поле `auth` (как и `token_env`) нельзя
менять из веб-шаблона. Неизвестное значение отвергается при загрузке конфигурации.

Чтение входящих изменений (`Changes`) проходит все страницы поиска
(`nextPageToken` для `/search/jql`, `startAt` для `/search`), а если Jira вложила в
задачу не весь changelog, дочитывает его через `/issue/{key}/changelog`. Поиск идёт в порядке `ORDER BY key`: набор ключей задан запросом, поэтому задача, обновлённая между
страницами, не переезжает на другую страницу и не теряется при `startAt`-постраничности. Признак неполного
вложенного changelog — `total` больше числа историй, а если сервер `total` не отдаёт, то полная страница историй
(100 или `maxResults`). Старый Data Center без `/issue/{key}/changelog` (404) не блокирует опрос: используется
вложенная часть, откат считается (`ChangelogFallbacks`) и попадает в `warnings` страницы изменений; поздние
изменения такой задачи могут быть пропущены. Токен `bearer` с пробелом или управляющим символом внутри
отклоняется без показа значения (пробелы по краям, например перевод строки из файла секрета, отбрасываются);
для `basic` токен кодируется в base64 как есть. Если
цепочка страниц не заканчивается (более 200 страниц), опрос завершается ошибкой, а
курсор не сдвигается: обрезанный список молча потерял бы изменения. Адаптер отличает собственные изменения от внешних по
идентификатору/e-mail пользователя из `/myself`; если Jira Cloud скрывает e-mail,
а `/myself` недоступен, собственные изменения могут быть восприняты как
внешние (эхо), и входящая синхронизация (S15) должна это учитывать.

Храните API token только в переменной окружения, названной в `token_env`.
Секрет не записывается в YAML. `base_url` — адрес, на который уходит токен,
поэтому меняйте его так же осторожно, как сам токен (см.
[Граница безопасности](security.md)).

### Выкладка через TeamCity

Этап выкладки может выполнять контроллер, а не человек и не модель. Для этого
этапу с `result: link` и `link_kind: build` назначают встроенного агента
`cicd-deploy` (`kind: deploy`, без модели и без промпта) и настраивают
провайдера в `cicd`:

```yaml
stages:
  # ... implementation с delivery и hard-проверкой pr_exists ...
  # ... code_review / qa: человек мержит PR и подтверждает переход ...
  - id: deploy
    title: Выкладка
    function: deployer
    result: link
    link_kind: build
    executor: agent
    agent: cicd-deploy

cicd:
  teamcity:
    base_url: https://teamcity.example.com
    build_type: Project_DeployProduction
    token_env: AI_TEAM_TEAMCITY_TOKEN
    branch: main
    merge_timeout: 30m  # необязательно, по умолчанию 30m, от 0 до 24h
    timeout: 30m        # необязательно, по умолчанию 30m, максимум 24h
    poll_interval: 15s  # необязательно, по умолчанию 15s, от 1s до 10m
```

Порядок работы этапа:

1. Ссылка на PR и коммит PR берутся из controller receipt более раннего
   PR-этапа (`delivery` + гейт `pr_exists@1`; в v5 — `check: pr_exists`). Без такого этапа выкладка не
   начинается.
2. Контроллер ждёт мержа: опрашивает `gh pr view` раз в `poll_interval` не
   дольше `merge_timeout`. Открытый PR — ожидание, закрытый без мержа или
   слитый в другую ветку — отказ. Каждая проверка ограничена тремя минутами;
   зависшая проверка считается временной ошибкой и повторяется до
   `merge_timeout`. `merge_timeout: 0` — одна проверка без ожидания. Сам
   ai-team PR не мержит; кто подтверждает мерж — в разделе
   [«Кто подтверждает выкладку»](#кто-подтверждает-выкладку).
3. PR должен принадлежать репозиторию задачи, зафиксированному при старте run,
   и его `headRefOid` должен совпадать с коммитом, который опубликовал
   контроллер.
4. Вершину ветки сообщает GitHub API (`gh api repos/<owner>/<repo>/branches/<branch>`),
   а не remote рабочей копии. Вся проверка идёт во временном отдельном
   bare-репозитории: контроллер скачивает туда ветку и `refs/pull/<N>/head` по
   URL репозитория задачи (не `origin`) и требует, чтобы вершина оказалась
   среди скачанных объектов. Рабочая копия — её `.git/config`, атрибуты,
   credential helper'ы, replace refs, grafts, commit-graph и объекты — не
   читается. Git запускается без system/global-конфига и без шаблона
   каталога (`git init --template=`, `GIT_TEMPLATE_DIR` удаляется из
   окружения); для приватного репозитория учётные данные даёт только явно
   заданный helper `!gh auth git-credential` (вход `gh` контроллера),
   остальные helper'ы сбрасываются. Скачивание, которое дольше 60 секунд идёт
   медленнее 1000 байт/с, обрывается (`http.lowSpeedLimit`/`http.lowSpeedTime`).
   `gh` запускается в отдельном пустом временном каталоге, а не в рабочем
   каталоге процесса.
5. GitHub только называет merge commit, решает Git: merge commit должен входить
   в вершину и содержать изменения PR. Либо голова PR — его предок (merge
   commit, fast-forward), либо его собственный diff совпадает с diff PR от
   merge base с точностью до номеров строк (squash и rebase одного коммита).
   Diff строится с `--no-textconv --no-ext-diff --binary
   --ignore-submodules=none` и явными параметрами, поэтому drivers и
   настройки не могут скрыть лишние изменения; концы строк не нормализуются.
   Ограничения squash и rebase merge — в разделе
   [«Ограничения squash и rebase merge»](#ограничения-squash-и-rebase-merge).
6. Выкладывается не голова PR, а вершина ветки: она содержит merge commit и
   всё, что смёржили после него, поэтому выкладка не откатывает чужие
   изменения.
7. В `build_type` ставится сборка на `branch` с ревизией, закреплённой на этом
   SHA, и с параметрами `env.AI_TEAM_DEPLOY_COMMIT` (SHA) и
   `env.AI_TEAM_DEPLOY_ID` — случайным 128-битным идентификатором этого
   запуска. Перед запуском в квитанцию пишется отметка «запуск в процессе»
   вместе с этим идентификатором. Отметка снимается без поиска только при явном
   отказе TeamCity: HTTP 400, 401, 403, 404, 405 или 415. Любой другой ответ
   (потерян, нечитаем, 5xx, 408, 409, 429 и прочие 4xx) оставляет исход
   неизвестным. Повтор этапа тогда не запускает сборку заново, а ищет в
   TeamCity сборку с этим `env.AI_TEAM_DEPLOY_ID` (`/app/rest/builds`, любые
   состояния и ветки). Найденная сборка принимается, только если она одна,
   относится к настроенному `build_type`, закреплена ровно на записанном SHA
   и несёт тот же `env.AI_TEAM_DEPLOY_COMMIT`; сборки без этого
   идентификатора не рассматриваются вовсе. Если сборка не найдена (запрос
   мог ещё не дойти), найдено несколько или найденная не совпала по
   конфигурации или ревизии, повтор отказывается и просит проверить TeamCity
   вручную и удалить квитанцию, чтобы не выложить дважды.
   Идентификатор сборки записывается в
   `.ai-team/state/deploy/<run>-<stage>.json`. Квитанция — только указатель:
   при повторе сборка перечитывается из TeamCity (статус, ссылка, build
   configuration), квитанция другого run или этапа отклоняется. Повтор
   продолжает ждать ту же сборку или переиспользует успешную; если ветка
   ушла вперёд, незавершённая старая сборка отменяется и ставится новая.
8. Статус опрашивается раз в `poll_interval`; сетевые ошибки, HTTP 5xx и 429
   при опросе повторяются до дедлайна. По истечении `timeout` или при отмене
   задачи контроллер отменяет сборку в TeamCity.
9. Этап успешен, только если сборка из настроенного `build_type` завершилась
   `SUCCESS` и TeamCity сообщает ровно выкладываемую ревизию. Ссылка на сборку
   (`webUrl` на хосте `base_url`) записывается в `<feature>/deploy/build.link`
   и становится результатом этапа.

При любой ошибке попытка этапа завершается неуспешно, а в поток событий
задачи пишется предупреждение `integration_error` с `integration: cicd`.
Ревизия, которую сообщил TeamCity, в тексте ошибки и в событии обрезается до
80 символов.

`webUrl` сборки принимается только на хосте и порту `base_url`: имя хоста
сравнивается без учёта регистра, отсутствующий порт равен 443, поэтому
`https://tc.example` и `https://TC.example:443` совпадают, а
`https://tc.example:8443` — нет. По тому же правилу проверяются редиректы.

#### Ограничения squash и rebase merge

- **Merge commit и fast-forward** доказываются предком: голова PR входит в
  merge commit.
- **Squash** доказывается сравнением diff: изменение squash-коммита
  относительно первого родителя должно совпасть с изменением PR относительно
  их merge base с точностью до номеров строк. Если при squash содержимое
  изменилось (разрешённый конфликт, правка в окне мержа) или в ветке успел
  измениться контекст строк вокруг изменений, diff не совпадёт и выкладка
  будет отклонена. Это осознанный fail-closed: ложный отказ возможен, ложное
  принятие — нет.
- **Rebase merge одного коммита** проверяется так же, как squash.
- **Rebase merge нескольких коммитов не поддерживается**: GitHub сообщает
  последний переписанный коммит, его собственный diff не равен всему PR, и
  выкладка отклоняется. Для веток с выкладкой через ai-team используйте
  merge commit или squash.

#### Кто подтверждает выкладку

ai-team сам PR никогда не мержит: этап выкладки только ждёт мержа, а затем
выкладывает вершину ветки. Решение «это можно в прод» — это сам мерж в
GitHub. Шаблон этого не проверяет и не может проверить:

- этап с гейтом `human_approval@1` (в v5 — `confirm: required`) между PR-этапом и выкладкой рекомендуется (ревью,
  QA), но валидацией не требуется: `--approve-gates` и auto mode подтверждают
  такие гейты автоматически, поэтому обязательность в шаблоне дала бы ложную
  гарантию;
- агент и контроллер работают под одним пользователем ОС с одним входом
  `gh`, поэтому смёржить PR технически может и агент; ai-team не различает,
  кто нажал «Merge».

Поэтому человеческий гейт перед выкладкой в прод обеспечивайте в GitHub:
защита ветки `branch` с обязательным одобряющим ревью другого человека
(«Require a pull request before merging» и «Require approvals»), без права
обхода для учётной записи, под которой работает `gh` контроллера. Тогда
мерж, а значит и выкладка, невозможен без решения человека.

Токен TeamCity хранится только в переменной окружения из `token_env` процесса
контроллера (`ai-team run` или `ai-team web` без `--worker-command`). Он
передаётся заголовком `Authorization: Bearer` и не попадает в YAML, evidence,
события и тексты ошибок; в ошибках нет и URL запросов. Дочерние `git` и `gh`
запускаются без этой переменной. `base_url` обязан быть `https`, редирект на
другой хост или схему не выполняется. Disposable worker провайдера не
получает: в этом режиме этап `cicd-deploy` завершается ошибкой. Этап
выкладки не использует `stage_timeout`: его бюджет — `merge_timeout` +
`timeout` + 5 минут, чтобы долгое ожидание мержа не оборвало уже идущую
выкладку. Общий бюджет run (`budget.max_execution_time`) по-прежнему действует.

### Уведомления: webhook, Slack, e-mail

`ai-team web`, локальный `ai-team run` и `ai-team scheduler-worker` отправляют
события задач во внешние каналы по одному и тому же разделу `notifications`. Каждый канал
подписывается на типы событий (`events`) и, при желании, на функции этапов
шаблона (`functions`: `developer`, `qa`, `bo` и т. п.). Без `functions` канал
получает выбранные типы событий любого этапа, включая события без этапа
(`run_started`, `run_finished`); с `functions` — только события этапов этих
функций.

```yaml
notifications:
  web_base_url: https://ai-team.example   # ссылка на /tasks/<run_id>, необязательно
  channels:
    - name: ops-hook
      type: webhook
      url_env: AI_TEAM_NOTIFY_WEBHOOK_URL
      events: [stage_stalled, check_overridden, integration_error]
    - name: team-slack
      type: slack
      url_env: AI_TEAM_SLACK_WEBHOOK_URL
      events: [attempt_finished, approval_requested]
      functions: [developer, qa]
    - name: leads
      type: email
      smtp_url_env: AI_TEAM_SMTP_URL          # smtp://user:pass@host:587 или smtps://user:pass@host:465
      from: ai-team <bot@example.com>
      to: [lead@example.com]
      events: [check_overridden]
```

| Тип | Что отправляется | Откуда адрес |
|---|---|---|
| `webhook` | `POST` JSON: `event_id`, `type`, `run_id`, `task_id`, `stage`, `function`, `severity`, `timestamp`, `task_url`, `summary`, `data`; заголовки `Idempotency-Key: ai-team-event-<id>` и `X-AI-Team-Event-ID` | `url_env` |
| `slack` | incoming webhook, поле `text` с кратким описанием и ссылкой; Slack не поддерживает `Idempotency-Key`, см. ниже | `url_env` |
| `email` | `text/plain` письмо, `Message-ID: <ai-team-event-<id>@ai-team.invalid>` | `smtp_url_env` |

Адреса webhook и Slack — только `https`, без логина в URL. Редирект
разрешён только на тот же хост и порт по `https`; редирект на другой хост,
другой порт или на `http` отклоняется, и тело запроса туда не уходит. Каждая
доставка ограничена 10 секундами. Для SMTP при `smtp://` STARTTLS обязателен:
если сервер не-loopback-хоста его не предлагает, письмо не отправляется и
записывается `integration_error`. Без TLS разрешён только loopback-сервер
(`localhost`, `127.0.0.0/8`, `::1`). Адреса задаёт оператор через окружение;
политика SSRF описана в [Граница безопасности](security.md).

Неизвестный тип события в `events`, неизвестный `type` канала или функция,
которой нет в шаблоне, — ошибка конфигурации. Список допустимых событий:
`approval_decided`, `approval_requested`, `attempt_finished`,
`attempt_started`, `attempts_invalidated`, `check_error`, `check_overridden`,
`delivery_deferred`, `delivery_plan_approved`, `delivery_retry_failed`,
`delivery_retry_requested`, `delivery_retry_succeeded`, `description_missing`,
`executor_changed`, `grill_completed`, `human_result_edited_agent`,
`integration_error`, `queue_updated`, `run_canceled`, `run_cancel_requested`,
`run_finished`, `run_paused`, `run_queued`, `run_resumed`, `run_started`,
`stage_returned`, `stage_skipped`, `stage_stalled`, `stage_taken`,
`transition_selected`.

Адреса и пароли хранятся только в переменных окружения процесса, который
отправляет уведомления (`ai-team web`, `ai-team run`, `ai-team scheduler-worker`);
в YAML пишутся лишь их имена. Если переменная не задана или
канал недоступен, задача продолжается, а в поток событий пишется durable
предупреждение `integration_error` с `integration: notifier` и именем канала;
URL, тело ответа и учётные данные в него не попадают. Об ошибках самих
уведомлений канал не уведомляет, даже если подписан на `integration_error`.

Уведомления читают события из SQLite (`.ai-team/web.db`) по собственному
курсору каждого процесса. У `ai-team web` и `ai-team scheduler-worker` курсор
durable; при первом включении он ставится на текущий край, старые события не
рассылаются. Если этот курсор не читается или не записывается, уведомления в
этом процессе не включаются (предупреждение в stderr), а не начинают с начала
истории. `ai-team run` начинает с края базы на момент запуска и отправляет
только события своих run; его курсор живёт в памяти. Перед выходом он
дожидается отправки до 30 секунд. Остаток — и все события, если `ai-team run`
упал до отправки, — доставит только процесс с durable-курсором на той же базе
(`ai-team web` или `ai-team scheduler-worker`), у которого уведомления были
включены ещё до этих событий. Если такого процесса нет, неотправленные
события run так и останутся неотправленными. Без `.ai-team/web.db` журнала
доставок нет, и `ai-team run` уведомления не отправляет.

`ai-team scheduler-worker` после первого Ctrl-C (или SIGTERM) дожидается
отправки оставшихся уведомлений до 30 секунд; второй Ctrl-C прерывает это
ожидание сразу.

Каждая пара «канал — событие» перед отправкой захватывается в общем журнале
доставок и фиксируется в нём после отправки. Ключ один для всех процессов,
поэтому повтор события после переподключения, перезапуска, отката курсора, а
также одновременная работа `ai-team web` и `ai-team run` на одной базе второе
уведомление не создают. Захват, чей владелец упал до отправки, истекает через
2 минуты, и событие отправляет следующий процесс. Захват принадлежит
владельцу: записать исход или снять захват может только тот, кто его взял,
поэтому процесс, чей захват истёк и перешёл к другому, не затрёт и не
освободит чужой. Окно повтора остаётся одно: если процесс завершился (или не
смог записать исход в журнал) после того, как канал принял запрос, событие
уйдёт ещё раз — для этого случая webhook несёт `Idempotency-Key`, а письмо —
стабильный `Message-ID`. Slack incoming webhook ключа идемпотентности не
поддерживает, и в этом окне сообщение в Slack может прийти дважды.
Предупреждение `integration_error` о сбое канала записывается не больше одного
раза на пару «канал — событие», даже если событие повторяется.

`ai-team web` удаляет из журнала доставок записи с итоговым исходом старше
30 дней — при старте и затем каждые 6 часов. Активные захваты не удаляются
независимо от возраста. Запись удаляется, только если её событие не выше
самого отстающего durable-курсора уведомлений (`notifier` у `ai-team web`,
`notifier:scheduler-worker` у `scheduler-worker`): процесс, чей курсор отстал
больше чем на 30 дней (например, `scheduler-worker`, который месяц не
запускался), повторно такие события не отправит — их записи ждут, пока курсор
его догонит. Курсор `ai-team run` живёт только в памяти процесса и записи не
удерживает.

### redaction

Правила поиска секретов в доказательствах для `ai-team redact`, `export` и
`gate`. По умолчанию экспорт с найденными секретами запрещён.

| Поле | Что делает |
|---|---|
| `include`, `exclude` | glob-шаблоны путей относительно корня репозитория |
| `disable_export_block` | `true` разрешает экспорт даже с находками; не рекомендуется |
| `scan_sensitive_fields`, `raw_logs` | зарезервированы: принимаются, но пока ни на что не влияют |

### retention

Умолчания для `ai-team gc`. Флаги командной строки важнее.

| Поле | По умолчанию | Что делает |
|---|---|---|
| `older_than` | `720h` | убирать завершённые прогоны старше этого |
| `keep_last` | `20` | всегда сохранять столько последних прогонов |
| `prune_runs` | `false` | разрешить удаление доказательств прогонов с проверенным экспортом |

### tree_hash

`ignore_dirs` — простые имена каталогов (без `/` и шаблонов), которые
дополнительно исключаются из workspace identity digest. По умолчанию исключены
только `.git` и `.ai-team`; каталоги сборки и зависимостей входят в digest.
Эта настройка не меняет mutation guard: он всегда видит все каталоги проекта.
Например, так можно исключить кеш, который не является частью identity проекта.

```yaml
tree_hash:
  ignore_dirs: [.cache, node_modules]
```

### containment

Допустимые значения — `trusted-local` и `strict`.

> [!WARNING]
> В текущей версии секция `containment` принимается конфигом, но её значение
> не применяется: прогон всегда идёт с профилем `trusted-local`. Профиль
> `trusted-local` — это ограничения на уровне приложения, а не песочница ОС.
> Подробнее — в [Граница безопасности](security.md).

## Этапы шаблона

`stages` задаёт единственный процесс проекта. ID этапа — отдельный от имени
агента ключ, а список определяет порядок обычных переходов.

| Поле | Что задаёт |
|---|---|
| `id` | уникальный ID этапа |
| `title` | название для людей |
| `function` | отвечающая за этап функция, например `po`, `architect` или `qa` |
| `approver_function` | необязательная функция подтверждающего; должна отличаться от `function` (с учётом синонимов `po`/`product_owner`, `deployer`/`release_manager`) |
| `result` | тип результата: `md`, `link` или `approve` |
| `executor` | `human` (по умолчанию) или `agent` |
| `agent` | существующий агент из `ai-team list`, если для этапа доступно исполнение агентом. При `executor: human` агент задаёт только контракт (выходы и входы): человек работает по тем входам, что уже есть, а отсутствующий вход агента не ошибка этапа; он понадобится, только если этап переключат на агента |
| `adapter` | имя из верхнеуровневого `executor_adapters`: этап `executor: agent` исполняет внешняя программа вместо внутреннего агента; `agent` остаётся контрактом этапа (входы, выходы, verdict, mutation scope) |
| `mcp_servers` | имена серверов из верхнеуровневого allowlist; применяются только к этому этапу и только с `cli: codex` |
| `link_kind` | для `result: link`: `pr`, `build` или `other`. На этапе `pr` ссылкой на PR считается только выход, целиком состоящий из URL PR (`.../pull/<n>`) или номера, либо JSON-объект с полем `pr_url` (при его отсутствии используется `url`). Хост URL должен быть `github.com` или хостом из переменной окружения `GH_HOST` (GitHub Enterprise), иначе вывод игнорируется; прочие не-Markdown выходы агента (diff, лог) игнорируются |
| `exit_gate_groups` | (v6) гейты, которые должен пройти результат, чтобы этап можно было покинуть; см. [гейты этапа](#гейты-этапа-и-перенос-на-схему-v6) |
| `required_sections`, `check`, `confirm` | (только v5, в v6 отклоняются) прежняя запись тех же проверок; заменяются на `exit_gate_groups` |
| `skippable` | можно ли пропустить этап с причиной; по умолчанию `false` |
| `delivery` | требования delivery для PR-этапа с указанным `agent`: `require_checks` выбирает controller checks проекта, `require_verdicts` — дополнительные verdict stages |

Этап `link_kind: build` с агентом `cicd-deploy` выполняет выкладку силами
контроллера; см. [выкладку через CI/CD](#выкладка-через-teamcity).

> **Только файловый конфиг.** Команды (`executor_adapters`, `checks`,
> `mcp_servers`, гейты `external_program` и `docker_program`) и вся
> инфраструктура (`tracker`: адаптер, адреса, `token_env`, `inbound`; `cicd`,
> `notifications`, `containment`, `cli`/`model`/`effort`, таймауты, `budget`,
> `auto_pickup`, `usage`, `tree_hash`, `redaction`, `retention`, `delivery`
> этапа) задаются в `.ai-team/config.yaml` репозитория. Шаблон, присланный через
> REST, MCP или страницу «Шаблон», может менять только процесс: `template`,
> `title`, `schema_version`, `stall_after`, `forbid_self_approval`, `stages`
> (названия, функции, результаты, исполнители, агенты, гейты без команд,
> ссылки на адаптер и MCP-сервер по имени), `returns`, `max_visits` и карты
> статусов `tracker.on_enter`, `tracker.on_pass`, `tracker.jira.stage_statuses`.
> Всё остальное в присланном документе должно совпадать с активным (файловым)
> шаблоном (разобранные структуры равны), иначе `400` с кодом
> `trusted_config_only` и названием секции или поля. Поскольку веб заменяет
> весь документ, присылайте инфраструктурные секции без изменений (скопируйте
> их из текущего шаблона): пропущенная секция считается изменением. Адаптер,
> проверку и MCP-сервер из веба можно указать только по имени, если определение
> совпадает с файловым. См. [границу безопасности](security.md#веб-дашборд).

### Внешний исполнитель этапа

Исполнитель этапа создаёт результат; гейт его проверяет. Это разные измерения:
внешний исполнитель не связан с запуском внешней программы как гейта.

```yaml
executor_adapters:
  demo-shell:
    argv: ["./scripts/stage-executor.sh"]   # без shell; относительный путь — от каталога проекта
    timeout: 5m                             # по умолчанию 10m, максимум 24h
    max_output_bytes: 1048576               # лимит лога stderr, по умолчанию 1 MiB
    max_result_bytes: 1048576               # лимит JSON-результата на stdout
    env_allow: [PATH, DEMO_API_KEY]         # единственные переменные окружения контроллера

stages:
  - id: tech
    function: architect
    result: md
    executor: agent
    agent: tech          # контракт этапа
    adapter: demo-shell  # исполняет внешняя программа
```

Контроллер пишет в stdin один JSON-запрос (`schema_version: 1`, `run_id`,
`attempt_id`, `stage`, `feature`, `task`, `instructions`, `workdir`,
`artifact_root`, `inputs[{name,path,size}]`, `outputs[{name,path}]`, `mutation`,
`allowed_paths`) и читает со stdout ровно один JSON-ответ: `schema_version: 1`,
`status` (`ok` или `error`), необязательные `error`, `summary`, `verdict`,
`outputs` (`{имя: {content}}`: контроллер сам запишет файл по объявленному пути)
и `metadata` (до 32 строковых пар). Программа может вместо `content` записать
выходной файл сама. Ненулевой код выхода, превышение времени или лимита,
невалидный JSON, `status: error`, неизвестное поле, необъявленный выход и
отсутствие объявленного выхода — ошибка исполнения: этап не считается
завершённым. После программы контроллер проверяет выходы, mutation scope и
verdict тем же путём, что для внутреннего агента; заявленный программой
`verdict` лишь сверяется с разобранным из выходов. Процесс получает только
`env_allow` (и `PATH` по умолчанию `/usr/local/bin:/usr/bin:/bin`), а также
`AI_TEAM_PROTOCOL`, `AI_TEAM_RUN_ID`, `AI_TEAM_ATTEMPT_ID`, `AI_TEAM_STAGE`;
в лог, summary и метаданные не попадают значения разрешённых переменных
`env_allow` длиной от 4 байт (`PATH` не маскируется) и секретоподобные
фрагменты, найденные общим редактором (`redact`); порог тот же, что у запуска
внешних гейтов. Секрет вне `env_allow` (например, прочитанный программой из
файла) контроллер не знает: его закрывает только общий редактор по шаблонам, так
что не печатайте такие значения в stderr. Если все agent-этапы шаблона
исполняются адаптерами, `ai-team` не требует CLI агента и его credentials; вместо
этого preflight проверяет, что программа адаптера существует и исполняема
(относительный путь должен оставаться внутри репозитория). Лог попытки сохраняется рядом с логами агентов. Фактический
исполнитель (`internal_agent` с типом runtime либо `external` с именем адаптера)
записывается в манифест попытки (`executor_info`) и в события `attempt_finished`
(`executor_kind`, `executor_name`).

`adapter` недопустим для controller operation (`delivery`, `deploy`): конфиг с
такой парой отвергается при валидации.

#### Контейнерный исполнитель и code review

Тот же адаптер можно запустить в Docker: добавьте блок `docker`, а `argv`
станет командой внутри образа. Протокол не меняется, граф и маршруты тоже: этап
`code_review` остаётся этапом с контрактом агента-ревьюера, а `approve` и
`changes requested` идут по обычным маршрутам, включая возврат к
`implementation`.

```yaml
executor_adapters:
  container-review:
    argv: ["/bin/sh", "/agent/review.sh"]   # внутри образа
    timeout: 10m
    env_allow: [REVIEW_API_TOKEN]           # единственные переменные, попадающие в контейнер
    docker:
      image: alpine@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc
      network: none          # по умолчанию none; bridge — явное исключение
      cpus: "1"              # по умолчанию 1
      memory_mb: 512         # по умолчанию 512
      pids_limit: 128        # по умолчанию 128
      tmpfs_mb: 64           # scratch /tmp; 0 — без него
      output_mb: 64          # потолок размера /stage/out (по умолчанию 64, максимум 1024)
      repo: ro               # необязательно: репозиторий только для чтения в /stage/repo
      mounts:                # необязательно: файлы/каталоги репозитория только для чтения
        - e2etest/container-review-agent:/agent
      # user: "1000:1000"    # по умолчанию uid:gid контроллера (nobody, если он root)
      # pull: never          # по умолчанию missing
      # allow_unpinned_image: true   # только осознанно: образ без digest

stages:
  - id: code_review
    function: reviewer
    result: md
    executor: agent
    agent: reviewer
    adapter: container-review
```

Правила изоляции задаёт `pkg/dockerrun`, и конфигурация их не отключает: образ
закреплён digest (`name@sha256:<64 hex>`), корень контейнера только для чтения,
все capabilities сброшены, `no-new-privileges`, лимиты CPU/памяти/процессов,
сеть `none`, без Docker-сокета, домашнего каталога и окружения контроллера.
В контейнер монтируются только:

| Путь в контейнере | Что | Режим |
|---|---|---|
| `/stage/in/<имя входа>` | каждый объявленный вход этапа (diff/PR-данные, спецификации, документы) | только чтение |
| `/stage/out` | приватный каталог результата попытки | запись |
| `/stage/repo` | репозиторий, только при `repo: ro` | только чтение |
| пути из `mounts` | файлы самой программы | только чтение |

В JSON-запросе программа видит только контейнерные пути (`inputs[].path` =
`/stage/in/<имя>`, `outputs[].path` = `/stage/out/<имя>`, `workdir` =
`/stage` или `/stage/repo`); пути хоста наружу не попадают. Результат
программа отдаёт либо как `outputs.<имя>.content` в JSON, либо файлом
`/stage/out/<имя>`; контроллер сам копирует файл в объявленное место, и только
при `status: ok`. Одно и то же имя и как `content`, и как файл — неоднозначный
ответ и ошибка исполнения. Файлы результата читаются в память во время запуска, а
в объявленные пути записываются только после того, как весь ответ прошёл
проверку контракта (лишний или необъявленный ключ, неверный `status`, нечитаемый
JSON), поэтому отклонённый ответ ничего не оставляет на диске; если же вердикт,
заявленный исполнителем, расходится с вердиктом в выходах, контроллер удаляет
записанные выходы попытки. Переменные окружения не из `env_allow` в контейнер
не попадают; `PATH`, `HOME`, `DOCKER_*` и подобные имена docker-клиента в
`env_allow` для контейнера запрещены. Значения переменных не записываются в
argv docker-команды, лог и метаданные редактируются так же, как у хостового
адаптера.

Каталог `/stage/out` лежит внутри приватного (0700, только владелец) временного
каталога контроллера и удаляется после попытки. По умолчанию контейнер работает
под uid:gid контроллера, и сам `/stage/out` — 0700. При явном `user:` контейнеру
нужно писать под чужим uid, поэтому `/stage/out` открыт на запись (0777), но он
недостижим для остальных учётных записей хоста, потому что родительский каталог
закрыт. Размер каталога ограничен `output_mb` (по умолчанию 64 МБ): это
bind-mount с хоста, а не tmpfs, поэтому контроллер опрашивает размер примерно
раз в 200 мс и останавливает контейнер при превышении; попытка завершается
технической ошибкой. Ограничение мягкое: до остановки программа успевает
записать столько, сколько позволит диск за интервал опроса. Забирается файл
результата не больше 16 МБ.

Ошибка контейнера (ненулевой код, образ не найден, таймаут, OOM, лимит вывода),
невалидный JSON, `status: error`, `verdict`, не совпадающий с разобранным из
отчёта, и неоднозначный ответ — всегда техническая ошибка попытки, а не
выдуманный вердикт. Контейнер удаляется по имени при отмене и таймауте; при
первом запуске контроллер удаляет контейнеры с меткой `ai-team.stage-attempt`,
оставшиеся от умершего контроллера (старше 24 ч 15 мин).

В `executor_info` попытки (манифест и события) контроллер записывает в
`metadata` поверх ключей программы: `container.image` (с digest),
`container.image_pinned`, `container.network`, `container.user`,
`container.cpus`, `container.memory_mb`, `container.pids_limit`,
`container.mounts`, `container.exceptions` (всё, что шире строгих значений по
умолчанию, имена, но не значения, переданных переменных) и `container.name`.
Лог попытки (stderr и stdout контейнера, с редакцией) сохраняется рядом с
логами агентов. Preflight проверяет наличие `docker` в `PATH` и путей из
`mounts`, а не команду внутри образа.

Воспроизводимый внешний агент для проверки лежит в
[`e2etest/container-review-agent/review.sh`](../../e2etest/container-review-agent/review.sh):
shell-скрипт в alpine по digest читает вход `diff` и выдаёт `APPROVED` либо
`CHANGES_REQUESTED` (есть строка `FIXME`); флаги `--fail`, `--crash`,
`--garbage`, `--mismatch`, `--file`, `--both` воспроизводят ошибки и вариант с
файлом. Интеграционные тесты: `pkg/stageexec/docker_test.go` и
`pkg/pipeline/stage_executor_docker_test.go` (пропускаются без Docker).

#### Подключение другого агента

Любой контейнерный агент подключается без изменения движка одним из двух
способов.

1. **Конфигурацией**, если агент уже говорит по контракту `schema_version: 1`
   (JSON запроса на stdin, один JSON-ответ на stdout или файл в `/stage/out`):
   достаточно `image`, `argv` и `env_allow`.
2. **Узким адаптером его формата**, если не говорит: небольшая программа или
   скрипт в образе (или смонтированный через `mounts`), которая читает запрос,
   достаёт входы из `/stage/in`, запускает агента, переводит его результат в
   `outputs.<имя>.content` или файл и `verdict` и печатает ответ контракта.
   Адаптер живёт рядом с агентом, а не в графовом движке; контроллер по-прежнему
   сам проверяет выходы, mutation scope и verdict.

Требования к агенту: завершаться с кодом 0 после записи ответа; писать результат
только в `/stage/out` или в JSON; не требовать сети (иначе `network: bridge` —
явное исключение, видно в `container.exceptions`); получать секреты только через
`env_allow`.

**CoreKit как пример (не встроен).** Внутренний `kit review`
(`propellerads/kit`) принимает GitHub PR (`repository` и
`pull_request_number`), сам клонирует репозиторий, публикует результат в
GitHub-review и локального файла результата не создаёт; образ лежит во
внутреннем registry. Адаптер для него не входит в ai-team. Чтобы он прошёл этот
контракт, от CoreKit нужен **флаг вывода результата в файл JSON** (например,
`--output-json /stage/out/kit-result.json`) с вердиктом (одобрено, нужны правки
или ошибка), текстом отчёта и ссылкой на созданный GitHub-review. Тогда узкий
адаптер берёт `repository` и номер PR из PR-входа этапа, запускает
`kit review ... --output-json`, превращает файл в отчёт с
`**Verdict:** APPROVED|CHANGES_REQUESTED` и ответ контракта; GitHub-токен
передаётся только через `env_allow`, сеть `bridge` включается явно. Пока флага
нет, надёжно отличить «одобрено» от «нужны правки» нельзя, и адаптер обязан
вернуть `status: error`, а не угадывать вердикт. Команду и формат ответа CoreKit
нужно проверить отдельно, когда появится ссылка на образ.

Если указан `executor: agent`, поле `agent` обязательно. Все agent-ссылки,
включая `agent` в параметрах гейта `agent_review`, проверяются по registry.
Гейт `required_sections` применим только к `result: md`.

Named `delivery.require_checks` запускаются контроллером на указанном PR-этапе
реализации и должны иметь `policy: required`. Delivery принимает их только
после успешного результата с immutable evidence для текущего workspace digest.
`delivery.require_verdicts` ссылается на более ранние этапы шаблона; их
required verdict contract и immutable output snapshot входят в предусловия
плана. Review, QA и verification artifacts не нужны, если эти этапы явно не
перечислены в `require_verdicts`.

Hard-правило `project_checks` запускает `ai-team gate` на закреплённых base/head
SHA в отдельном detached worktree PR. Политика `gate.yaml` берётся из base SHA;
изменение кандидатной ветки не может ослабить собственную gate-конфигурацию.
`pr_checks_green` читает `gh pr checks` и завершается ошибкой, если PR изменился
во время запроса. Когда перед этапом `function: reviewer` уже есть успешный PR
результат, контроллер передаёт ревьюеру неизменяемый `gh pr diff` и JSON с PR,
base и head SHA вместе с объявленными входами спецификации и технического
решения. Если PR-ссылки нет, reviewer работает по обычным входам шаблона.

### Гейты этапа и перенос на схему v6

Этап производит результат (`result: md|link|approve`). **Гейт** проверяет одну
версию этого результата (по хешу) и возвращает структурированный исход;
следующий этап выбирает только контроллер. Определения гейтов живут в
версионированной библиотеке в коде (`pkg/gatelib`), меняются через PR и
показываются в только читаемом каталоге `GET /api/gates/catalog`. Загрузить
или отредактировать определение из UI/API нельзя.

`exit_gate_groups` — список групп. Группы выполняются последовательно, гейты
внутри группы независимы и запускаются параллельно (не больше
`gate_concurrency` одновременно, по умолчанию 4). Следующая группа стартует,
только когда предыдущая закончилась и все обязательные гейты прошли; после
отказа новые группы не стартуют, но уже запущенные гейты доводятся до исхода.
Ссылка на гейт — это точные ID и версия, никогда «последняя»:

```yaml
exit_gate_groups:
  - [verdict_marker@1]                 # строка: id@версия
  - - gate: agent_review               # mapping: параметры, имя, режим
      version: 1
      name: spec_llm_review            # уникально в этапе; по умолчанию = gate
      mode: required                   # required (по умолчанию) | advisory
      params: {agent: spec-checker, mode: grill, max_rounds: 3}
  - [human_approval@1]
```

| Гейт@версия | Вид | Параметры | Применим к |
|---|---|---|---|
| `required_sections@1` | код | `sections` (список, обязателен) | `md` |
| `verdict_marker@1` | код | — | `md` |
| `required_phrases@1`, `required_phrases@2` | код | `phrases`, `case`, `scope`, `match` (обязательны); `section`, `min_count`, `unit`, `regex` | `md` |
| `pr_exists@1`, `pr_open@1`, `pr_base_branch@1` | код | — | `link` |
| `project_checks@1`, `pr_checks_green@1` | код | — | `link` с `link_kind: pr` |
| `agent_review@1` | LLM | `agent` (обязателен), `mode` (`grill`), `max_rounds` (≥ 0) | любой |
| `agent_review@2` | LLM | как `@1` плюс `verdict_schema` (`verdict_marker` по умолчанию или `json`), `max_attempts` (1..5, по умолчанию 1; не вместе с `mode: grill`) | любой |
| `human_approval@1` | человек | — | любой |
| `human_approval@2` | человек | `on_reject` (`stop` по умолчанию или `stay`) | любой |
| `external_program@1` | внешняя программа | `command` (обязателен), `timeout_seconds`, `cwd`, `env_allow`, `max_output_bytes`; см. [Протокол гейта](gate-protocol.md) | любой |
| `docker_program@1` | Docker | `image` (`name@sha256:<digest>`, обязателен), `command` (обязателен), `allow_unpinned_image` (bool, исключение), `pull` (`missing` по умолчанию или `never`), `network` (`none` по умолчанию или `bridge`), `cpus` (десятичное, по умолчанию 1), `memory_mb` (≥ 1, по умолчанию 512), `pids_limit` (≥ 1, по умолчанию 128), `tmpfs_mb` (≥ 0, по умолчанию 64; 0 — без `/tmp`), `user` (`uid[:gid]` или имя; по умолчанию uid:gid контроллера), `repo_access` (`ro` по умолчанию или `rw`), `mounts` (`<путь в репозитории>:<абсолютный путь в контейнере>[:ro\|rw]`), `timeout_seconds` (≥ 1, по умолчанию 60, максимум 3600), `cwd`, `env_allow`, `max_output_bytes` (≥ 1, по умолчанию 1 МиБ, максимум 16 МиБ); см. [Протокол гейта](gate-protocol.md) | любой |

**`required_phrases@1` и `@2`** проверяют (параметры и поведение одни и те же, различается только строгость
валидации: `@1` принимает то, что принимал при выпуске; `@2` дополнительно отклоняет управляющие символы во
фразах и пересекающиеся фразы при `match: at_least`; для новых шаблонов используйте `@2`), что в md-результате есть заданные слова или
фрагменты. Всё, что меняет смысл проверки, задаётся явно, без молчаливых
умолчаний:

```yaml
- gate: required_phrases
  version: 2
  params:
    phrases: ["метрика успеха", "срок"]   # до 50 фраз, каждая до 200 байт
    case: insensitive                      # sensitive | insensitive
    scope: section                         # result (весь результат) | section
    section: "Критерии приёмки"            # обязателен только при scope: section
    match: at_least                        # all | any | at_least
    min_count: 1                           # обязателен только при match: at_least
    unit: word                             # substring (по умолчанию) | word
```

`scope: section` ищет только в теле раздела: от заголовка (регистр и
завершающее двоеточие не важны) до следующего заголовка того же или более
высокого уровня; подразделы входят в тело. Заголовок — ATX (`#`…`######`, затем пробел или конец
строки, отступ до 3 пробелов) или setext (абзац с подчёркиванием `===`/`---`);
`#Текст` без пробела, строки с отступом от 4 пробелов, блоки кода и
содержимое HTML-комментариев заголовками не считаются. Закрывающий забор кода —
тот же символ, не короче открывающего и без info-строки. `case: insensitive`
использует простую свёртку регистра Unicode (σ, ς и Σ равны; ß и ẞ равны, но
полная свёртка ß в `ss` не применяется). `unit: word` требует целое слово (буквы, цифры и `_`
не могут стоять вплотную). Регулярные выражения не поддерживаются, кроме явного
`regex: true`: тогда каждая фраза — выражение Go RE2 (линейное время, без
lookahead и обратных ссылок), которое компилируется при валидации шаблона и не
должно допускать совпадения нулевой длины (`\b`, `^`, `$`, `a|\b`, `a*`); `regex: true` несовместим с `unit: word`.
Краевые случаи определены так. Фраза не бывает пустой, не может начинаться или
заканчиваться пробельным символом (включая неразрывный пробел) и содержать
управляющий символ, кроме перевода строки и табуляции (только `@2`; `@1` такие фразы принимает); пробелы внутри фразы
сравниваются буквально (два пробела — не один, `\n` в фразе совпадает только с
переводом строки). Фразы считаются по отдельным записям списка: фраза, найденная
несколько раз, — одна запись, а пересекающиеся в тексте записи находятся обе
(`API` и `API gateway` оба найдены в «API gateway»). Поэтому в `@2` при
`match: at_least` без `regex` фраза, содержащаяся в другой фразе (с учётом
выбранного регистра), отклоняется при валидации (`@1` такой список принимает): один фрагмент текста засчитался
бы дважды. Для `all` и `any` пересечение допустимо; выражения `regex: true` на
пересечение не проверяются. Текст сравнивается как есть, кроме двух
нормализаций: CRLF и одиночный CR становятся LF, а BOM в начале файла
отбрасывается. Юникод-нормализация (NFC/NFD) **не** применяется: «é» одним
символом и «e» с комбинирующим акцентом — разные тексты, как и неразрывный пробел
и обычный; чтобы принять обе формы, используйте `regex: true` с альтернативой
(`caf(é|é)`, где вторая форма записана раскладкой «e + U+0301»). Свёртка регистра
простая: заглавная `İ` (U+0130) не равна `i`. Если заголовок с названием
раздела встречается несколько раз, областью поиска служит объединение их тел.

Пользовательских скриптов нет: логика гейта — Go-код в репозитории
(`pkg/gatephrases`). Результаты: пустой результат и отсутствующий раздел —
`fail`; нечитаемый, слишком большой или отсутствующий md-файл — `error`
(технический сбой, повторяемый), никогда не `pass`; `not_applicable` гейт не
возвращает. Неверное сочетание параметров (нет `case`/`scope`/`match`,
`section` без `scope: section`, `min_count` вне `1..число фраз`, битое
выражение, повтор фразы с учётом выбранного регистра) отклоняется при
валидации шаблона, до запуска.

**Встроенные кодовые гейты исполняются планировщиком.** `required_sections`,
`verdict_marker`, `required_phrases`, `pr_exists`, `pr_open`, `pr_base_branch`,
`project_checks` и `pr_checks_green` не имеют обходного пути в пайплайне: каждый
запускается `pkg/gatesched` как попытка с `execution` и `verdict` в журнале
run'а. Три гейта `pr_*` одной волны читают один ответ `gh pr view`. Нечитаемый
md-результат у `required_sections`/`verdict_marker` — `error`, а не `fail`.

Правила валидации (ошибки называют путь вида
`stages[1] (product_spec): exit_gate_groups[0][0]` и причину): неизвестный ID,
версия или параметр, пропущенная версия, обязательный параметр, неверный тип,
неприменимый результат, пустая группа и повторяющееся имя гейта отклоняют
шаблон до запуска. Шаблон закрепляет точные версии определений: публикация
новой версии определения в библиотеке не меняет ни опубликованный шаблон, ни
начатую задачу, потому что их YAML ссылается на `id@старая_версия`, а старые
версии остаются в библиотеке навсегда. `Config.GatePins()` возвращает
закреплённые `id`, `version` и SHA-256 определения.

Отсутствие гейта `human_approval` означает отсутствие подтверждения этапа
(в v5 это было `confirm: auto`). Единственное исключение — этап, из которого
ведёт хотя бы один возврат (`returns` с `from` этого этапа): возврат —
решение человека на переходе, поэтому переход вперёд оформляется действием
`approve` или `return_to_<этап>` даже без `human_approval` (так компилируется
граф процесса; роль — функция подтверждающего этапа). Этап без `human_approval` и без возвратов
переходит дальше сам, как только прошли гейты. Цепочка может быть произвольной: любые группы
из кодовых и LLM-гейтов, в том числе разных видов в одной группе и несколько
`agent_review` на этапе (LLM-гейты группы вызываются по одному: они делят
рабочее пространство контроллера и учёт токенов). Человеческое решение — это
подтверждение перехода этапа (оно запрашивается после всех автоматических
групп), поэтому `human_approval` допускается только в последней группе:
гейт, который стоит в одной группе с автоматическими, ждёт их, человека не
спрашивают, пока они не закончились. Автоматический гейт **после** решения
человека не предлагается: он потребовал бы второй паузы внутри перехода.
Два `agent_review` с `mode: grill` на одном этапе не допускаются (раунды вопросов
хранятся в подтверждениях этапа). `Validate` называет путь и причину для
каждого такого случая, чтобы гейт не был молча проигнорирован.

**Обязательные и рекомендательные гейты (`mode`).** `mode: required` (по
умолчанию) блокирует переход, пока гейт не прошёл. `mode: advisory` —
рекомендация: гейт запускается в своей группе и ждётся вместе с ней, но его
`fail` и техническая ошибка (`error`/`timeout`) переход **не** блокируют. Они и
не скрываются: попытка сохраняет `execution` и `verdict`, событие попытки несёт
`mode: advisory` и `advisory_warning`, событие `check_passed` — список
`warnings`, отчёт проверки показывает правило как `advisory_failed` или
`advisory_error`, UI рисует янтарное предупреждение, API отдаёт
`warning: true`. В одной группе можно смешивать оба режима: ждём всю группу,
переход зависит только от обязательных гейтов. `human_approval` (решение
человека — сам переход) и `agent_review` с `mode: grill` (раунды вопросов
должны закончиться до следующей группы) рекомендательными быть не могут.

```yaml
exit_gate_groups:
  - - required_sections@1             # обязательный
    - {gate: verdict_marker, version: 1, mode: advisory}   # только предупреждение
  - [human_approval@1]
```

**Повтор и обход.** Технически упавший обязательный гейт можно повторить на той
же версии результата (`retry_gate`, `POST /api/runs/{run}/stages/{stage}/gates/{gate}/retry`):
новая попытка, прежняя остаётся, успешные гейты группы не повторяются. Обход
проваленного обязательного гейта (`POST …/stages/{stage}/override`) — только
системное право администратора (роль `admin`), с обязательной причиной; исход
гейта он не меняет и действует только на проверенную версию результата.
Подробности — в `docs/reference/TASK-FLOW-WEB-API.md` (раздел «Gate state, retry and override»).

**LLM-гейт (`agent_review@2`).** Проверяющий получает фиксированный вход
(свои объявленные входы и выходы проверяемого этапа) и обязан ответить по
`verdict_schema`:

- `verdict_marker` — строка `Verdict: PASSED|FAILED` вне блоков кода и цитат
  (контракт всех прежних проверяющих);
- `json` — один объект `{"verdict": "pass|fail", "reason": "...", "findings":
  [{"severity": "blocker|major|minor|info", "message": "..."}]}` — весь отчёт
  либо единственный блок ```` ```json ````. Неизвестные поля, неизвестные
  `verdict`/`severity`, `fail` без `reason` и `findings`, `pass` с замечанием
  `blocker` нарушают схему.

Ответ вне схемы и отказ рантайма — `execution: error` без вердикта: ни `pass`, ни
`fail`. `max_attempts` вызовов повторяют только такие технические сбои (валидный
`fail` не повторяется); причина попытки гейта перечисляет все вызовы
(`попытка 2/3: ответ вне схемы (...)`). `mode: grill` — отдельный режим вопросов
человеку, контракт вердикта от него не зависит.

**Человеческий гейт (`human_approval@2`).** Допустимые действия — `approve`,
`reject` и возвраты по `returns` шаблона; роль — функция подтверждающего этапа
(`approver_function`, иначе `function`); кворум — любой один; решение привязано к
точному хешу предмета. Ожидание и каждое решение пишутся в историю попыток гейта
(`gate_attempt_waiting` → `gate_attempt_finished`): `approve` — `pass`, `reject`
и возвраты — `fail` с действием, ролью, автором и комментарием в причине.
`on_reject: stay` оставляет задачу на этапе после отказа: причина обязательна,
этап запускается заново, а новая версия результата повторяет всю цепочку с
первой группы (счётчик посещений не расходуется). По умолчанию (`stop`, как в
`@1`) отказ завершает задачу.

Решение человека принимает один сервис (`pkg/humandecision`): Web, REST и (позднее)
MCP вызывают его, и он в одном порядке проверяет действие, точный хеш предмета,
роль, самоподтверждение (`forbid_self_approval`), сохраняет решение и пишет
аудит `human_gate_decided` (автор, роль, действие, хеш, канал, ключ
идемпотентности `Idempotency-Key`). `POST .../stages/{stage}/confirm` принимает
тело `{"subject_hash": "..."}`: хеш, который видел человек (фронтенд и сетевой
MCP-сервер обязаны его слать). Путь без хеша **устарел (deprecated)**: сервер
подставляет хеш текущего запроса, отвечает заголовками `Deprecation: true` и
`Warning`, а аудит отмечает, что человек хеш не подтверждал
(`hash_confirmed_by_actor: false`). Человек с несколькими нужными ролями
голосует по разу на роль (каждый вызов закрывает следующую непокрытую роль,
локальный владелец закрывает кворум из двух ролей двумя вызовами); когда все его
роли покрыты, тот же запрос — повтор доставки, другое действие — отказ
«уже голосовал».

Пример цепочки `product_spec`: кодовый гейт → LLM-гейт → PO с отказом «остаться на этапе»:

```yaml
exit_gate_groups:
  - - gate: required_sections
      version: 1
      params: {sections: ["Критерии приёмки"]}
  - - gate: agent_review
      version: 2
      name: spec_llm_review
      params: {agent: spec-checker, verdict_schema: json, max_attempts: 2}
  - - gate: human_approval
      version: 2
      name: po_approval
      params: {on_reject: stay}
```

**Исполнение.** Планировщик (`pkg/gatesched`) привязывает волну к хешу результата
(SHA-256 объявленных выходов) и сверяет его до волны, после каждого гейта и
в конце. Запись в файлы результата физически не запрещается: правка во время
проверки обнаруживается (детективная, fail-closed защита), отменяет волну и не
даёт ни одного зачтённого исхода. Выход, который нельзя прочитать или который
слишком велик, тоже меняет хеш при изменении размера или времени файла. Каждая попытка гейта пишется в журнал run'а
событиями `gate_attempt_started`, `gate_attempt_waiting` (гейт ждёт ответа) и
`gate_attempt_finished`: с ID задачи, этапа, посещения, хешем результата,
определением (ID, версия, имя), группой, видом исполнителя, временем начала и
конца, раздельными `execution` и `verdict` и причиной. После перезапуска
завершённый гейт не запускается повторно, прерванный (старт без исхода)
закрывается как `canceled` и заменяется новой попыткой, ожидающий ответа
продолжает ту же попытку. Технический сбой (`error`, `timeout`) не
повторяется неявно. Успех для старого хеша не засчитывается новому: любое
изменение результата или новая попытка этапа исполняют все группы заново с
первой. При старте задачи в журнал пишется `gate_pins_recorded` (ID, версия,
вид и SHA-256 каждого закреплённого определения); при возобновлении
расхождение с библиотекой останавливает run.

`gate_concurrency` (верхний уровень конфига, 1..64, 0 — по умолчанию 4)
ограничивает число одновременно работающих гейтов одной группы; LLM-гейты
внутри группы выполняются по одному.

**Перенос v5 → v6.** Файлы `schema_version: 5` продолжают загружаться без
изменений: ключи `required_sections`, `check` и `confirm` по-прежнему
действуют, а в гейты переводятся на лету (`required_sections` → гейт
`required_sections@1`; правила `check.kind: hard` → гейты с теми же именами;
`check.kind: agent` → `agent_review@1`; `confirm: required` → `human_approval@1`
в последней группе). Явный перенос — `Config.MigrateToCurrent()`; профили
`init` создаются сразу в v6, и их путь и вердикты совпадают с v5
(`TestIdeaToProdV5AndV6AreEquivalent`). В v6 ключи `required_sections`,
`check` и `confirm` удалены, а `exit_gate_groups` в v5 недоступен: обе ошибки
подсказывают замену. Ошибки перевода v5 помечены «(из required_sections/check
v5)»: путь `exit_gate_groups[i][j]` в них указывает на переведённую цепочку, а
не на строку файла. Валидация v5 не строже прежней: пробелы по краям названий
разделов нормализуются (и повторы после обрезки схлопываются), а применимость
правила к типу результата не проверяется (правило, как и раньше, даёт
`skipped` или `failed` при проверке).

Строгость v6 и v5 расходится в одном месте исполнения: `required_sections` в v5
раньше проверялось контроллером только вместе с `check: {kind: hard}` (и при
ручной сдаче человеком), теперь это гейт цепочки и исполняется для любого
этапа, который его объявил.

Шаблон содержит возвраты между этапами. `to` должен быть раньше `from` в
списке `stages`; для каждого этапа, в который ведёт возврат, действует лимит
`max_visits` (по умолчанию 3). Граф строится контроллером из порядка этапов и
списка `returns`, поэтому отдельный раздел `workflow` в конфиге отсутствует.

### Права по функциям

Участникам команды назначаются функции (`/api/team/members/{actor}/roles`
принимает канонические роли и синонимы `bo`, `po`, `deployer`). Действия над
этапом сервер проверяет по функциям закреплённого за задачей шаблона:

| Действие | Маршруты | Нужна функция |
|---|---|---|
| брать | `take`, `executor`, `run-agent` | `function` |
| сдавать | `results`, `submit`, `grill/*` | `function` |
| обходить | `override`, `skip` | `function` |
| подтверждать | `confirm`, `return`, решение по переходу этапа | `approver_function`, а без него — `function` |

Политика fail-closed: если у участника нет нужной функции или функция этапа не
сопоставлена ни одной роли, действие отклоняется с `403`. Локальный режим
(`ai-team web` без облачной identity) работает от одного пользователя
`local-user`, которому назначены все функции, поэтому поведение локального
режима не меняется.

`forbid_self_approval: true` запрещает подтверждать этап его авторам в текущем
посещении. Посещение начинается после предыдущего подтверждения этого этапа.
Автор — тот, кто брал этап (`take`), сдавал результат, принимал решения grill
(`answer`, `new_version`, `done`) или обходил проверку, правил результат этапа
или вывод агента, запускал агента (`run-agent`) или менял исполнителя. Если
авторов определить не удалось, подтверждение отклоняется. Запрет касается
только подтверждения: возврат (`return`) под него не подпадает. Настройка
действует и в локальном режиме: единственный локальный пользователь не сможет
подтвердить свою же работу, поэтому включать её имеет смысл в командном режиме.
Этап, выполненный агентом без участия человека, авторов-людей не имеет и
подтверждается без ограничения.

### Проверки (checks)

Проверки запускает контроллер, а не модель. Определения находятся на верхнем
уровне конфига; PR delivery может ссылаться на них по имени. Обязательные
(`required`) проверки должны пройти до delivery.

| Поле | Что задаёт |
|---|---|
| `name` | уникальное имя проверки проекта |
| `class` | `formatter`, `lint`, `build`, `unit`, `integration`, `e2e`, `coverage`, `race` или `security` |
| `command` | команда списком аргументов, без shell |
| `adapter` | чтение результата: `command`, `go-test-json` или `junit-xml` |
| `report_file` | путь к JUnit XML; только для `junit-xml` |
| `policy` | `required` или `optional` |
| `timeout` | таймаут проверки |
| `working_dir` | каталог запуска внутри проекта |

`go-test-json` требует команду вида `[go, test, -json, ...]`. Адаптеры
`go-test-json` и `junit-xml` допустимы только для классов `unit`,
`integration` и `e2e`.

Пошаговая настройка для разных стеков — в
[Настроить проверки проекта](../guides/project-checks.md).

### Переход с v4

Конфиг schema v4 больше не загружается. Выполните `ai-team init --force`,
чтобы создать встроенный шаблон заново, либо перенесите настройки вручную по
примеру выше. `init` без `--force` сохраняет существующий конфиг.

## Профили init

Флаг `ai-team init --profile` материализует один из трёх шаблонов в
`.ai-team/config.yaml`.

| Профиль | Этапы | Подтверждения переходов | Когда выбирать |
|---|---|---|---|
| Профиль | ID шаблона | Отличие |
|---|---|---|
| `standard` (по умолчанию) | `idea-to-prod` | стандартные подтверждения (`human_approval`), лимит возвратов — 3 |
| `fast` | `idea-to-prod-fast` | ни одного `human_approval`, лимит возвратов — 2 |
| `regulated` | `idea-to-prod-regulated` | `human_approval` на каждом этапе, лимит возвратов — 2 |

Каждый профиль хранит обычный список этапов и возвратов; специальные runtime-
режимы профиля не сохраняются. Встроенный `idea-to-prod` включает этапы от
`intent` до `acceptance`.

```bash
ai-team init --profile regulated
```

## Runtime и ключи

Агент работает через внешний CLI-рантайм. Его выбирает поле `cli`.

| Рантайм | `cli:` | Выбор модели | Что проверяет preflight |
|---|---|---|---|
| OpenCode | `opencode` (по умолчанию) | `-m <model>` или `auto` | `opencode --version`, ключи провайдера и их разрешение, Git-репозиторий |
| Codex | `codex` | `-m <model>` или `auto` | `codex --version`; способ входа (API-ключ / подписка / не найден), sandbox `workspace-write` |
| Claude Code | `claude` | `--model <model>` или `auto` | `claude --version`; способ входа (API-ключ / подписка / не найден), `--permission-mode acceptEdits` |

Каждый рантайм ставится и настраивается отдельно от ai-team. Пошагово —
в учебнике [Подключить настоящую модель](../tutorial/real-model.md).

### Изолированное окружение

Рантайм запускается в изолированном окружении. У каждого свой временный
каталог настроек на время запуска: `XDG_CONFIG_HOME` у OpenCode, `CODEX_HOME`
у Codex, `CLAUDE_CONFIG_DIR` у Claude. В процесс попадают только базовые
переменные ОС (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `PWD`, `LANG`,
`LC_ALL`, `LC_CTYPE`, `TMPDIR`, `TERM`, `COLORTERM`, `NO_COLOR`) и
переменные, которые вы разрешили по имени.

### Передать ключ провайдера

Ключ в вашем shell **не виден** агенту, пока вы не разрешите его имя в
`AI_TEAM_HARNESS_ENV_ALLOW` (несколько имён — через запятую). Иначе прогон
упадёт на авторизации, хотя тот же CLI отдельно работает.

```bash
export ANTHROPIC_API_KEY='<ваш-ключ>'
AI_TEAM_HARNESS_ENV_ALLOW=ANTHROPIC_API_KEY ai-team run --feature add-jwt-auth --task "…"
```

Разрешённая переменная передаётся в процесс рантайма вместе со значением.
ai-team не пишет значение в логи, отчёты и доказательства. Старое имя
`AI_TEAM_OPENCODE_ENV_ALLOW` работает так же.

Для Claude Code вместо API-ключа можно использовать подписку Claude: получите
`CLAUDE_CODE_OAUTH_TOKEN` командой `claude setup-token`. Claude-адаптер
передаёт эту переменную только в процесс Claude Code; добавлять её в
`AI_TEAM_HARNESS_ENV_ALLOW` не нужно. Обычный `ANTHROPIC_API_KEY` по-прежнему
передаётся только после явного разрешения имени переменной.

Для Codex можно войти через подписку ChatGPT командой `codex login`. Если
`CODEX_API_KEY` или `OPENAI_API_KEY` не разрешён и не передаётся рантайму,
адаптер копирует `~/.codex/auth.json` во временный `CODEX_HOME` с правами
`0600`; временный каталог имеет права `0700` и удаляется после этапа. Файл
авторизации не выводится в логи. Preflight показывает только способ входа,
не значение токена, и не проверяет действительность учётных данных у сервиса.

### MCP-инструменты Codex

MCP-серверы выключены, пока проект не определит их в `mcp_servers` и не выберет
имена на конкретных этапах. Сейчас поддерживаются только локальные stdio-серверы
Codex; для других runtime конфиг с MCP блокируется. Команда должна быть
абсолютным путём к исполняемому файлу, а аргументы передаются напрямую через
argv, без shell и подстановок.

```yaml
cli: codex
mcp_servers:
  knowledge:
    command: /opt/ai-team/bin/knowledge-mcp
    args: [--readonly, --collection, engineering]
    env: {LOG_LEVEL: warn}
    startup_timeout_sec: 10
    tool_timeout_sec: 60
  monitoring:
    command: /opt/ai-team/bin/monitoring-mcp
    args: [--readonly]
stages:
  - id: product_spec
    title: Продуктовая спецификация
    function: po
    result: md
    executor: agent
    agent: analyst
    mcp_servers: [knowledge]
  - id: observation
    title: Наблюдение после выкладки
    function: deployer
    result: md
    executor: agent
    agent: observer
    mcp_servers: [monitoring]
```

Определение `mcp_servers` — это allowlist проекта, а `stages[].mcp_servers` —
выбор доступных инструментов для одного вызова агента. На один этап можно
выбрать не более четырёх серверов. Имена переменных окружения и их литеральные
значения в `env` проходят строгую проверку; значения ограничены по размеру.
`startup_timeout_sec` по умолчанию равен 10 секундам и не может быть больше 60,
`tool_timeout_sec` по умолчанию равен 60 секундам и не может быть больше 300.
Общий `stage_timeout` также ограничивает выполнение агента. При истечении
таймаута ai-team сначала даёт Codex две секунды на штатную остановку его MCP
процессов, затем принудительно останавливает оставшиеся процессы.

`env_vars` — дополнительный явный список имён переменных хоста, доступных
конкретному MCP-серверу. Каждое имя также должно быть в
`AI_TEAM_HARNESS_ENV_ALLOW`, а переменная должна быть задана. Переменные
аутентификации и секретов (включая API keys, OAuth tokens, GitHub tokens,
`CODEX_HOME` и `AI_TEAM_*_TOKEN`) запрещены даже при явном выборе; передача
service credentials в этой версии не поддерживается. Не помещайте секреты в
`env`: эти значения являются частью файла конфигурации проекта.

На каждом запуске Codex получает новый временный `CODEX_HOME` с MCP-настройками
только выбранного этапа; пользовательская и глобальная MCP-конфигурация не
объединяется. Subscription `auth.json` при необходимости по-прежнему копируется
в этот каталог только для самого Codex CLI. Сам MCP-процесс получает отдельный
временный `HOME`, и секреты runtime не добавляются в его переменные окружения.
Локальный MCP-сервер всё равно получает те данные, которые агент решит передать
ему через вызов инструмента; подключайте только доверенные серверы.

## Другие переменные окружения

| Переменная | Что делает |
|---|---|
| `AI_TEAM_HARNESS_ENV_ALLOW` | имена переменных, которые можно передать рантайму |
| `AI_TEAM_WORKER_ENV_ALLOW` | имена переменных, которые контроллер передаёт disposable worker; его runtime получает тот же список |
| `AI_TEAM_AGENT_PATH` | дополнительные каталоги агентов (список через `:`), слой между проектом и пользователем |
| `AI_TEAM_AUTH_SECRET` | секрет облачной аутентификации дашборда (имя меняется флагами `--auth-secret-env` и `--secret-env`) |

Агенты ищутся по слоям: `.ai-team/agents/` проекта, каталоги из
`AI_TEAM_AGENT_PATH`, пользовательский каталог `ai-team/agents` в системном
каталоге настроек, затем встроенные. Как разрешаются конфликты слоёв — в
[архитектуре](../ARCHITECTURE.md#layered-agent-registry).
