# Протокол гейта внешней программы

Гейт `external_program@1` запускает доверенную команду из конфигурации
репозитория, передаёт ей JSON-контекст и читает один JSON-вердикт. Тот же
протокол `ai-team.gate/v1` использует Docker-адаптер: меняется только способ
запуска, не формат документов и не правила классификации. Код — пакет
`pkg/gaterun`, демо-программа — `pkg/gaterun/testdata/demo-gate.sh`.

## Что настраивается

Параметры ссылки на гейт в `exit_gate_groups` (только конфиг репозитория;
из UI программа не вводится):

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `command` | список строк, обязателен | — | argv без shell: программа и аргументы |
| `timeout_seconds` | целое ≥ 1 | 60 (максимум 3600) | таймаут запуска |
| `cwd` | строка | `.` | рабочий каталог относительно корня репозитория |
| `env_allow` | список строк | пусто | имена переменных контроллера, которые видит программа |
| `max_output_bytes` | целое ≥ 1 | 1 МиБ (максимум 16 МиБ) | лимит stdout и stderr по отдельности |

```yaml
exit_gate_groups:
  - - gate: external_program
      version: 1
      name: license_scan
      params:
        command: ["./scripts/license-gate.sh", "--strict"]
        timeout_seconds: 120
        env_allow: ["LICENSE_API_TOKEN"]
```

Правила запуска:

- Команда запускается напрямую, без shell. Программа — абсолютный путь, путь с
  `/` относительно **корня репозитория** (не `cwd`) или имя из `PATH`
  контроллера. Нужен shell — укажите его в `command` явно. Относительный путь
  не может выходить за корень репозитория (`../tool` отклоняется); symlink
  внутри репозитория не раскрываются — содержимое репозитория считается
  доверенной конфигурацией.
- Окружение программы — только `env_allow` плюс
  `AI_TEAM_GATE_PROTOCOL` и `AI_TEAM_GATE_ATTEMPT_ID`. `PATH`, `HOME` и всё
  остальное не наследуются. Неустановленные переменные пропускаются.
- Программа запускается в своей группе процессов; по таймауту, отмене и
  превышению лимита вывода убивается вся группа, а после любого завершения
  лидера добивается и остаток группы (фоновые потомки).
- Секреты в `command` не вписываются: аргумент, похожий на токен или ключ,
  отклоняется при проверке конфигурации. Передавайте их через `env_allow`.

## Вход (stdin)

Один JSON-документ:

```json
{
  "protocol": "ai-team.gate/v1",
  "task_id": "task-42", "stage": "spec", "visit": 1,
  "attempt_id": "att-7f3a",
  "gate": {"id": "external_program", "version": 1, "name": "license_scan"},
  "artifact": {"type": "md", "sha256": "<64 hex>", "path": "/abs/result.md"},
  "paths": {"repo_root": "/abs/repo", "evidence_dir": "/tmp/ai-team-gate-work-1234"},
  "limits": {"timeout_seconds": 120, "max_output_bytes": 1048576}
}
```

`artifact.type` — `md`, `link` или `approve`; для ссылки есть `link_kind` и
`url`. `artifact.sha256` — хеш проверяемой версии результата. В `evidence_dir`
программа вправе писать файлы-доказательства; это отдельный временный каталог
вне каталога попытки, он удаляется после запуска; адаптер запуска может
переписать пути под то, что видит программа (например, путь в контейнере).

## Выход (stdout)

Ровно один JSON-документ, без текста вокруг; диагностику — в stderr:

```json
{
  "protocol": "ai-team.gate/v1",
  "verdict": "fail",
  "reason": "лицензия GPL-3.0 у зависимости foo",
  "evidence": [{"kind": "report", "path": "licenses.txt", "sha256": "<64 hex, необязательно>"}]
}
```

- `verdict` — `pass`, `fail` или `not_applicable`; для `fail` `reason`
  обязательна. `reason` — не более 2000 байт.
- До 20 ссылок на доказательства. `path` — относительный, с `/`, без `..`,
  внутри `evidence_dir`; `kind` — короткая метка `[a-z][a-z0-9_-]{0,31}`.
- Неизвестные поля, второй документ и текст после документа — ошибка.
  Неоднозначный документ тоже ошибка: повторяющийся ключ (в том числе через
  escape, `"verd\u0069ct"`) и ключ в другом регистре (`"Verdict"`) дают
  `error`, а не «побеждает последний».

## Как исход попадает в попытку

Контроллер различает пять исходов и никогда не превращает технический сбой в
вердикт:

| Что произошло | `execution` | `verdict` |
|---|---|---|
| код 0 и валидный документ `pass` / `fail` / `not_applicable` | `succeeded` | из документа |
| код ≠ 0, убит сигналом, не запустился, потеря процесса | `error` | нет |
| невалидный JSON, два документа, неверный протокол или вердикт | `error` | нет |
| превышен лимит stdout/stderr (процесс убит) | `error` | нет |
| нарушено требование к доказательству (см. ниже) | `error` | нет |
| превышен `timeout_seconds` (группа убита) | `timeout` | нет |
| отмена контекста (группа убита) | `canceled` | нет |

Валидный `fail` — это успешное исполнение с отрицательным мнением; `error` и
`timeout` — технические сбои, их можно повторить на той же версии результата
(повтор — новая попытка с новым ID, прежняя не стирается).

## Доказательства и секреты

В каталог попытки `<evidence_root>/<attempt_id>/` пишутся:
`stdout.log`, `stderr.log` (очищенные, не длиннее лимита),
`invocation.json` (argv, cwd, **имена** переменных, лимиты, код выхода),
`evidence/…` (проверенные копии файлов программы) и последним
`attempt.json` — запись попытки. Пути в записи относительные.

- Файлы доказательств копируются только если это обычный текстовый файл
  внутри `evidence_dir` (symlink отвергается), ≤ 1 МиБ, с совпавшим `sha256`
  (если указан) и **без секретов**. Любое нарушение делает попытку `error`;
  файл не сохраняется и не переписывается. Сырой каталог программы не
  хранится.
- В логах, `reason` и `invocation.json` секреты заменяются: паттерны токенов
  и ключей (сканер `pkg/redact`) и дословные значения **всех** переменных из `env_allow`
  длиной от 4 символов, независимо от имени (короче — только паттернами).

## Повтор и идемпотентность

`Runner.Run` идемпотентен по `attempt_id`: если `attempt.json` уже записан,
возвращается сохранённая попытка без запуска программы; одновременные вызовы
с одним ID запускают её один раз. Тот же ID для другой задачи, этапа, посещения,
хеша или гейта — ошибка. Незавершённый каталог (контроллер умер на середине)
очищается и попытка выполняется заново.

Гарантия «один запуск на ID» держится на мьютексе внутри процесса: два
процесса контроллера на одном `EvidenceRoot` не координируются и могут оба
запустить программу (второй коммит упадёт, запись неизменяема). Держите один
контроллер на `EvidenceRoot`.

`attempt.json` защищён от подделки программой: она не знает каталога попытки
(`evidence_dir` лежит отдельно), всё, что она всё же записала в каталог
попытки, отбрасывается, а попытка становится `error`; при повторном чтении
запись принимается только с верной подписью HMAC (`attempt.sig`, ключ в
`<evidence_root>/.gaterun.key`, права 0400, создаётся атомарно при первом
`Run`, до запуска любой программы; ключ неверной длины — ошибка).
Несовпадение — ошибка целостности, не `pass`.

Граница этой защиты: хост-запуск идёт под тем же uid, поэтому программа
технически может прочитать ключ (путь вычисляется из `evidence_root` контроллера
и `AI_TEAM_GATE_ATTEMPT_ID` из окружения) или, если ключа ещё нет, подложить
свой. Подпись защищает от записи в каталог попытки во время запуска, от
случайной порчи и от процессов без доступа к ключу, но не от враждебной
программы. От недоверенной программы защищает только изоляция: Docker-адаптер
(`docker_program@1`, ниже) или отдельный uid.

## Ограничения

- На Windows остаток группы после самостоятельного выхода лидера не
  убивается (дерево уже нельзя адресовать); на Unix убивается.
- Isolation от хоста у `external_program` не обеспечивается: программа
  доверенная и выполняется с правами контроллера. Для изоляции —
  `docker_program`.
- Бинарные доказательства не поддерживаются: их нельзя проверить на секреты.

## Docker-адаптер: `docker_program@1`

Тот же протокол и та же классификация, но команда выполняется в контейнере из
образа, закреплённого digest. Код — `pkg/gaterun/docker.go` (`DockerLauncher`,
второй `Launcher`) поверх переиспользуемого пакета `pkg/dockerrun` (сборка argv
`docker run`, запуск без shell, удаление контейнера по имени); `executor` попытки
— `docker`. Запускается `docker` CLI контроллера; демон и образ — внешние
зависимости, их недоступность — `error`.

```yaml
exit_gate_groups:
  - - gate: docker_program
      version: 1
      name: license_scan
      params:
        image: ghcr.io/acme/license-scan@sha256:<64 hex>
        command: ["/usr/local/bin/license-gate", "--strict"]
        timeout_seconds: 120
        mounts: ["build:/out:rw"]     # исключение, попадёт в evidence
        env_allow: ["LICENSE_API_TOKEN"]
```

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `image` (обязателен) | — | `name@sha256:<64 hex>`; тег без digest отклоняется |
| `command` (обязателен) | — | argv внутри образа; заменяет entrypoint образа; без shell |
| `allow_unpinned_image` | `false` | явно разрешить образ без digest (исключение) |
| `pull` | `missing` | `missing` — тянуть, если образа нет локально; `never` — только локальный |
| `network` | `none` | `none` или `bridge` (исключение); `host` не поддерживается |
| `cpus` / `memory_mb` / `pids_limit` | `1` / 512 / 128 | лимиты; память без swap |
| `tmpfs_mb` | 64 | scratch `/tmp` в памяти, `noexec`; 0 — без `/tmp` |
| `user` | uid:gid контроллера | не root; при контроллере-root — `65534:65534`; `0` — исключение |
| `repo_access` | `ro` | `ro` или `rw` (исключение); и при `rw` `.git` остаётся read-only |
| `mounts` | пусто | `<путь в репозитории>:<абсолютный путь в контейнере>[:ro или :rw]`, по умолчанию `ro` |
| `timeout_seconds`, `cwd`, `env_allow`, `max_output_bytes` | как у `external_program` | таймаут включает pull образа |

Строгие значения по умолчанию (не параметры, их нельзя ослабить): `--rm`,
`--read-only` корень, `--cap-drop ALL`, `--security-opt no-new-privileges`,
явный `--user`, лимиты CPU/памяти/PID, `docker` без shell, уникальное имя
контейнера `ai-team-gate-<attempt_id>-<random>` и метка
`ai-team.gate-attempt` (плюс служебные метки `ai-team.dockerrun` и
`ai-team.started` со временем старта). Контейнеру **не** передаются: Docker-сокет, домашний
каталог, окружение и credentials контроллера, любые каталоги вне репозитория.

Что видит программа:

- `/gate/repo` — корень репозитория (по умолчанию только чтение; `cwd`
  становится рабочим каталогом внутри него). При `repo_access: rw` поверх
  записываемого репозитория отдельным read-only mount накладывается `.git`
  (каталог или gitfile linked worktree) и любой другой git-каталог внутри
  репозитория, чтобы контейнер не мог подложить хук или изменить
  `.git/config`, которые потом выполнит хост. Общий gitdir linked worktree
  (`git rev-parse --git-common-dir`) лежит вне репозитория и не монтируется
  вообще; symlink вместо `.git` отклоняется;
- `/gate/evidence` — приватный каталог доказательств (единственное место записи,
  кроме `/tmp` и явных `rw`-mounts);
- результат стадии: лежит в репозитории — через `/gate/repo`, иначе как один файл
  только для чтения `/gate/artifact/<имя>`;
- `paths.repo_root`, `paths.evidence_dir`, `artifact.path` во входном документе
  переписаны на эти пути, хостовых путей в документе нет;
- переменные: только `AI_TEAM_GATE_*` и `env_allow`. Значения не попадают в argv
  (`-e NAME`), а идут в окружении процесса `docker`; имена из окружения
  клиента Docker (`PATH`, `HOME`, `DOCKER_*`, `XDG_*`…) в `env_allow` отклоняются.

Источники extra-mounts — только подкаталоги/файлы репозитория: путь
относительный и чистый, symlink в любой компоненте отклоняется (демон Docker
раскрыл бы его на хосте), `.git` на запись монтировать нельзя, цели в
`/proc`, `/sys`, `/dev`, `/gate/evidence`, `/gate/artifact` и повтор цели
отклоняются при проверке конфигурации.

Исходы: содержательное заключение программы (код 0 и валидный документ) —
`succeeded` + `pass`/`fail`/`not_applicable`, как у хоста. Недоступный демон,
отсутствующий образ или ошибка pull (код `docker run` 125), невозможный запуск
команды (126/127), `137` (SIGKILL, в том числе OOM-kill по лимиту памяти),
отсутствующий бинарь `docker`, нарушение лимита вывода — `error` без вердикта;
причина содержит класс сбоя и хвост stderr. Таймаут — `timeout`, отмена —
`canceled`; в обоих случаях процесс `docker` убивается, а контейнер
принудительно удаляется по имени (`docker rm -f`); неудачное удаление явно
попадает в причину.

Evidence: набор файлов попытки тот же (`stdout.log`, `stderr.log`,
`invocation.json`, `evidence/…`, `attempt.json`). `invocation.json` получает
`"executor": "docker"` и блок `launcher.container`: образ и признак закрепления,
имя контейнера, сеть, пользователь, `workdir`, список mounts (источник как
`repository root`, `repository:<путь>`, `private evidence directory`, цель,
`read_only`), `tmpfs_mb`, **имена** переменных, лимиты, `docker_socket: false`,
`host_home: false`, полный argv `docker run` (без значений и без хостовых
путей) и список `exceptions` — всё, что шире умолчаний (`network=bridge`,
rw-репозиторий, каждый extra-mount, переданные переменные, root, образ без
digest, отсутствие `/tmp`). Значений секретов в записи нет.

Ограничения: на Docker Desktop (macOS/Windows) источники mount должны входить в
общие каталоги Docker; Windows-контроллер не определяет uid и запускает
контейнер как `65534:65534`; при контроллере-root `65534` не может писать в
приватный каталог `/gate/evidence` (задайте `user` явно). `--pull missing`
использует сеть демона вне зависимости от `network` программы; для
воспроизводимых окружений без сети используйте `pull: never` и предзагруженный
образ. Контейнер не защищает от уязвимостей ядра/демона Docker; `bridge`
открывает сеть целиком, и тогда программе доступны `.git/config` с URL
remote (в том числе с токенами в URL) и всё остальное, что читается из
репозитория, — это отдельно называется в `exceptions` вместе с
`network=bridge`. При удалённом демоне (`DOCKER_HOST`, `DOCKER_CONTEXT`)
источники bind-mount разрешаются на удалённой машине, а не на хосте
контроллера: репозиторий и приватный каталог доказательств там не окажутся,
поэтому Docker-гейт поддерживается только с локальным демоном.

Контейнер-сирота. Если контроллер убит (`kill -9`, потеря питания), он не
успевает удалить контейнер, и тот живёт до своего завершения. Гарантия
«контейнера не остаётся» поэтому best effort после аварии контроллера:
при первом Docker-гейте нового `Runner` выполняется свип
(`dockerrun.Runner.SweepOrphans`) — удаляются контейнеры с метками
`ai-team.dockerrun` и `ai-team.gate-attempt`, запущенные дольше
`gaterun.OrphanAge` (максимальный таймаут гейта плюс 15 минут, чтобы не
тронуть контейнеры другого живого контроллера на том же демоне). Контейнер,
убитый между `create` и `start`, тоже ловится свипом. Сбой свипа не блокирует
гейт. Свип сам не лечит работающий контроллер и не заменяет `--rm`.
