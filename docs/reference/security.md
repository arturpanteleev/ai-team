# Граница безопасности

Эта страница честно говорит, что ai-team гарантирует, а что нет. Коротко:
контроллер строго держит процесс и доказательства, но это не песочница.
Агент и проверки работают с правами процесса, который их запустил: вашего
пользователя ОС на своей машине или исполнителя на сервере.

> [!WARNING]
> Изоляцию даёт инфраструктура, а не ai-team. Контейнеризация сама по себе не
> является поддерживаемой границей изоляции для текущего `ai-team worker`:
> worker должен записывать approvals, lifecycle и run evidence в общее состояние,
> доступное для восстановления. Контейнер не мешает worker изменять это состояние.
> Не запускайте текущий worker как sandbox для недоверенного кода или пользователей.
> Архитектурный блокер и условия облачного пилота описаны в
> [руководстве по облачному пилоту](../guides/cloud-pilot.md).

## Чем ai-team защищает, а чем нет

| Гарантируется | Не гарантируется |
|---|---|
| переходы, проверки и delivery исполняет контроллер, а не модель | изоляция агента на уровне ОС |
| изменения вне разрешённых путей проваливают этап | защита от вредоносного кода в проекте или в проверках |
| delivery — только по подтверждённому SHA-256 плана | качество кода само по себе: только то, что покрыли проверки |
| доказательства нельзя незаметно изменить после записи | авторство доказательств без подписи |
| ключи провайдера не попадают к агенту без явного разрешения и не пишутся в доказательства | что агент не прочитает файлы, доступные вашему пользователю |
| Codex MCP получает только выбранные для этапа stdio-серверы из конфигурации проекта | изоляция MCP-процесса от других процессов того же OS-пользователя |

## Недоверенный код

Профиль по умолчанию — `trusted-local`. Для OpenCode контроллер запрещает на
уровне приложения shell, сеть и вложенные задачи, ограничивает правила чтения
и записи и выдаёт отдельный каталог настроек. Для Claude Code и Codex действуют
похожие запреты своими средствами (список запрещённых инструментов, режим
`workspace-write`). Но сам процесс агента и команды проверок работают с правами
текущего пользователя ОС.

Каждый прогон записывает в `containment.json` честный уровень изоляции по
четырём осям: файловая система, сеть, процессы, окружение
(`containment.json` хранит их):

- `trusted-local` → `PARTIAL`: ограничения приложения, не ОС;
- `strict` без бэкенда изоляции ОС → `UNAVAILABLE`: прогон недоверенного кода
  запрещён.

Строгий бэкенд изоляции ОС пока не реализован.

> [!WARNING]
> У проекта пока нет поддерживаемого изолированного cloud deployment. В
> текущем worker-контракте pipeline напрямую записывает approvals, lifecycle и
> run evidence в `.ai-team` target workspace. Общий writable volume нужен для
> recovery, но позволяет worker изменять эти файлы. Отдельный процесс или
> контейнер не доказывает защиту этих данных. До смены storage/API-границы не
> запускайте worker как sandbox для недоверенного кода или пользователей.
> Проверяемый блокер и минимальная целевая граница описаны в
> [статусе облачного пилота](../guides/cloud-pilot.md).

В опциональном Linux bubblewrap режиме текущий durable brief скрыт от worker
через namespace-local маску, а версии и текст передаются по run-scoped API.
Это защищает только конкретный каталог `.ai-team/runs/<run_id>/brief` в одной
invocation. Прочие run evidence, manifests, artifacts и файлы target по-прежнему
не изолированы; это не меняет статус cloud deployment и не закрывает MAJ-07.

## Ключи и секреты

Агент получает только базовые переменные окружения и те, что вы разрешили по
имени в `AI_TEAM_HARNESS_ENV_ALLOW`. Подробно — в
[Конфигурация](config.md#runtime-и-ключи).

В режиме disposable worker (`--worker-command` и scheduler-worker) контроллер
не передаёт дочернему процессу полное своё окружение. Worker получает
ограниченный набор переменных ОС и только имена, перечисленные в
`AI_TEAM_WORKER_ENV_ALLOW`; выбранные значения также разрешаются для runtime
через `AI_TEAM_HARNESS_ENV_ALLOW`. `HOME`, `TMPDIR` и XDG-каталоги worker
направлены в отдельный временный каталог и очищаются после задания. Для
примеров настройки см. [CLI](cli.md#ai-team-worker).

Эта фильтрация предотвращает случайное наследование переменных аутентификации,
подписи и базы данных control plane, если их имена не разрешены явно. Она не
защищает от процесса с тем же OS-пользователем, который может прочитать другие
доступные этому пользователю файлы или получить секреты из доступной файловой
системы. Это уменьшение наследуемого окружения, а не sandbox или граница
изоляции.

Секреты внешних интеграций (`tracker.jira.token_env`,
`cicd.teamcity.token_env`, адреса webhook и Slack, SMTP-URL уведомлений) задаются в шаблоне только именем переменной окружения
процесса `ai-team web` (адреса и SMTP-URL уведомлений — также процесса
`ai-team run` и `ai-team scheduler-worker`, которые отправляют уведомления сами). Ошибки доставки записываются в поток событий без URL,
тела ответа и учётных данных; webhook и Slack принимают только `https` и не
следуют редиректу на другой хост. Подробно — в
[Конфигурация](config.md#уведомления-webhook-slack-e-mail).

`tracker.jira.base_url` — это адрес, на который уходит секрет: каждый запрос
к Jira несёт Basic-авторизацию с `email` и токеном из `token_env`. Поэтому
`base_url` защищается так же, как сам токен: кто может менять
`.ai-team/config.yaml`, тот может направить токен на свой сервер. Указывайте
только `https`-адрес своего Jira Cloud и проверяйте изменения этого поля в
ревью. Ошибка трекера (в `integration_error` и в `tracker_deliveries.last_error`) записывается только классом
(«connection failed», «request timed out», «TLS verification failed»): ни URL,
ни заголовки запроса, ни текст ошибки транспорта туда не попадают.

**Адреса уведомлений задаёт оператор, а не модель или пользователь
дашборда.** Webhook, Slack и SMTP-адреса читаются только из переменных
окружения процесса; ai-team не ограничивает, куда они указывают, и намеренно
не фильтрует внутренние адреса: если оператор задал адрес во внутренней сети,
запрос туда уйдёт. Защита от SSRF здесь — в том, что ни агент, ни участник
команды не может подставить свой адрес. Сам запрос ограничен: только `https`
без логина в URL, редирект только на тот же хост и порт по `https` (смена
хоста, порта или переход на `http` отклоняются до отправки тела), 10 секунд на
доставку, тело ответа не читается в ошибки. Для SMTP при `smtp://` STARTTLS
обязателен для любого хоста, кроме loopback (`localhost`, `127.0.0.0/8`,
`::1`): если сервер не предлагает STARTTLS, письмо и учётные данные не
отправляются (fail-closed).

Выкладку через TeamCity инициирует только контроллер: модель не получает ни
токен, ни доступ к адаптеру. Токен читается из окружения процесса
контроллера (`ai-team run` или `ai-team web`) и не передаётся в disposable
worker; egress идёт только на `https`-хост `cicd.teamcity.base_url`, редиректы
на другой хост отклоняются. Сборка ставится только для вершины ветки
выкладки, которую сообщает GitHub API для репозитория, зафиксированного при
старте run, и в которую, по проверке самого контроллера через Git, вошёл merge
commit PR. Проверка идёт во временном отдельном bare-репозитории, поэтому
конфиг, атрибуты, credential helper'ы, replace refs и объекты рабочей копии на
неё не влияют. Учётные данные для приватного репозитория даёт только явно
заданный helper `gh auth git-credential`; `git` и `gh` запускаются без токена
TeamCity в окружении, `gh` — в отдельном пустом временном каталоге, `git` —
без шаблона каталога (`--template=`, без `GIT_TEMPLATE_DIR`). Подробно — в
[Конфигурация](config.md#выкладка-через-teamcity).

Что выкладка через TeamCity **не** гарантирует:

- **Человеческое решение о выкладке.** ai-team сам PR не мержит и выкладывает
  то, что смёржено в ветку. Шаблон не требует человеческого гейта перед
  выкладкой: `--approve-gates` и auto mode подтверждают гейты автоматически,
  а агент работает под тем же пользователем ОС и с тем же входом `gh`, что и
  контроллер, и технически может смёржить PR сам. Человеческое решение
  обеспечивает только защита ветки в GitHub с обязательным одобряющим ревью
  другого человека и без права обхода для этой учётной записи. Подробно — в
  [Кто подтверждает выкладку](config.md#кто-подтверждает-выкладку).
- **Любой способ мержа.** Merge commit и fast-forward доказываются предком,
  squash и rebase одного коммита — совпадением diff. Rebase merge нескольких
  коммитов и squash с изменённым при мерже содержимым отклоняются
  (fail-closed). Подробно — в
  [Ограничения squash и rebase merge](config.md#ограничения-squash-и-rebase-merge).
- **Автоматическое восстановление любого потерянного запуска.** Если ответ
  TeamCity на запуск потерян, повтор ищет сборку по уникальному
  `env.AI_TEAM_DEPLOY_ID` и принимает её, только если она одна, из
  настроенной build configuration и закреплена на том же SHA. Если сборка не
  найдена или найдено несколько, нужна ручная проверка: пустой поиск не
  доказывает, что запрос не дошёл.

### MCP-серверы агентов

Подключение MCP по умолчанию выключено. Для Codex контроллер строит новый
временный `CODEX_HOME` и помещает туда только серверы из allowlist, явно
выбранные на текущем этапе. Пользовательский/global Codex MCP config не
загружается и project `.codex/config.toml` по-прежнему блокируется. Доступны
только локальные stdio команды с абсолютным путём и фиксированным argv; URL,
remote transport и shell-команды не принимаются. Другие runtime с выбранным
MCP-сервером завершаются ошибкой.

Вызовы `env_vars` — отдельный opt-in: имя должно быть в `AI_TEAM_HARNESS_ENV_ALLOW`
и значение должно быть установлено. Upstream Codex очищает environment перед
запуском stdio MCP и передаёт свой базовый набор вместе с именами из
`env_vars` ([реализация Codex](https://github.com/openai/codex/blob/main/codex-rs/rmcp-client/src/utils.rs)).
Сам ai-team блокирует секретные имена (`*_API_KEY`, `*_TOKEN`, `*_SECRET`,
`*_PASSWORD`, `*_CREDENTIAL*`, `*_AUTH`, `*_PRIVATE_KEY`, `*_PAT`, в том числе
`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `CODEX_API_KEY`,
`CLAUDE_CODE_OAUTH_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`, `AI_TEAM_WEB_TOKEN`) и
runtime-переменные `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `HOME` и `AI_TEAM_*_ALLOW`.
Эти запреты действуют и для литерального `env`, и для `env_vars`; явный выбор
имени не открывает исключение для credentials. Отдельный механизм передачи
service credentials не реализован.

Subscription `~/.codex/auth.json`, если нужен для входа, остаётся в приватном
временном `CODEX_HOME` самого Codex CLI и не задаётся как env MCP-сервера.
Всем выбранным на этапе MCP-серверам задаётся один общий пустой временный
`HOME`, отдельный от `CODEX_HOME`, с правами `0700`.
Codex получает до двух секунд на остановку своих MCP процессов после timeout
или отмены этапа, затем контроллер принудительно завершает оставшиеся процессы.
Таймаут запуска MCP ограничен 60 секундами, таймаут одного tool call —
300 секундами; значения по умолчанию — 10 и 60 секунд.

Это уменьшает случайную передачу credentials через environment, но не создаёт
изоляцию ОС. MCP-команда и агент выполняются под тем же OS-пользователем; сервер
может читать другие доступные этому пользователю файлы и получает данные,
которые агент передаёт через инструменты. Определения команд и их аргументы в
`.ai-team/config.yaml` являются исполняемой доверенной конфигурацией: подключайте
только просмотренные серверы. Ограниченный `--readonly` аргумент — договорённость
с сервером, а не гарантия ai-team, что он не изменит внешнюю систему.

Перед экспортом доказательств и публикацией bundle `gate` контроллер ищет в
них секреты и при находках отказывает. Отдельно это делает
[`ai-team redact`](cli.md#ai-team-redact). Поиск секретов — дополнительная
страховка, а не гарантия найти всё.

## Целостность и подлинность

Это два разных вопроса: «не изменено ли» и «кто создал».

**Целостность (integrity) проверяется.** `ai-team verify <run_id>` сверяет
anchor с точными байтами `run.json`, event chain и attempt manifests; затем
проверяет размер и SHA-256 каждого сохранённого input/output artifact. Anchor
также связывает обычные файлы run-каталога: логи, reports, `candidate.json`,
`usage.json` и `containment.json`. Если присутствует terminal `delivery.json`,
его identity, self-digest и связь с `delivery_deferred` event тоже проверяются.
Изменённое доказательство приводит к ошибке проверки. `ai-team export` сначала
выполняет ту же live-проверку; bundle содержит attempt artifacts, а его
проверка не зависит от исходного каталога.

Bundle намеренно не включает raw logs и reports: экспорт проверяет их до
сборки, а переносит только whitelisted records. Поэтому получатель bundle
может проверить включённые records и attempt artifacts, но не получить
исключённые файлы обратно.

Workspace identity digest и mutation guard используют разные ignore-наборы.
Identity digest исключает `.git`, `.ai-team` и явно заданные
`tree_hash.ignore_dirs`; mutation guard исключает только `.git` и `.ai-team`,
поэтому изменения в `vendor`, `dist`, `node_modules` и `.venv` остаются
видимыми и проверкам, и attribution.

Anchors старой схемы без `run_manifest_sha256` и `supplemental_sha256` текущий
`verify` отклоняет: он не может заявить о проверке новых привязок.

**Подлинность (authenticity) — по подписи.** Bundle можно подписать своим
ключом ed25519 в формате DSSE (по спецификации in-toto):

```bash
ai-team export --sign-key ./signing.key <run_id>
ai-team gate --sign-key ./signing.key
ai-team verify --verify-key ./signing.pub /path/to/bundle
```

Подписывается детерминированный digest bundle, подпись лежит в `dsse.json`.
С `--verify-key` проверка строгая: подпись обязана быть и совпадать. Без ключа
проверяется только целостность, и успешный `verify` ничего не говорит об
авторе. Ключи передаются файлами и никогда не попадают в доказательства.

Как передать результат другому человеку — в
[Проверить и передать результат](../guides/evidence.md).

## Подлинность релизных бинарников

Та же пара гарантий действует для бинарников, которые выпускает проект.

- **Целостность:** к релизу приложен `sha256sums.txt` с digest каждого архива.
- **Подлинность:** каждый архив и сам `sha256sums.txt` подписаны cosign без
  хранимого ключа (keyless). Job сборки в `.github/workflows/release.yaml`
  получает короткоживущий OIDC-токен GitHub Actions, Fulcio выдаёт по нему
  сертификат, привязанный к
  `…/.github/workflows/release.yaml@refs/tags/<tag>`, а запись о подписи
  попадает в публичный журнал Rekor. Рядом с каждым архивом лежит
  `<asset>.cosign.bundle`: подпись, сертификат и доказательство из Rekor.

Подпись не заменяет digest, а дополняет его: digest отвечает «не изменено»,
подпись — «собрано этим релизным workflow на этом теге». Подпись **не**
доказывает, что бинарник безопасен или что тег поставил конкретный человек.

Перед сборкой тот же workflow прогоняет полный набор CI против коммита тега.
Подписанный артефакт всегда происходит от коммита, прошедшего те же проверки,
что и `master`.

> [!NOTE]
> `v0.2.0` и более ранние релизы не подписаны. Всё, что опубликовано позже,
> подписано обязательно. Как проверить подпись перед установкой — в учебнике
> [Установка](../tutorial/install.md).

## Веб-дашборд

Без аутентификации `ai-team web` слушает только loopback-адрес и защищает
пишущие запросы сессионной cookie и CSRF-токеном. Облачный режим с токенами и
ролями описан в [Команды CLI](cli.md#ai-team-auth-token). TLS должен
завершаться на внешнем прокси.

**Команды не принимаются из веба.** Программа, которую хост запускает сам
(гейты `external_program` и `docker_program` с их `command`, образом и
mounts, а также `executor_adapters`, `checks` и `mcp_servers`), задаётся
только в файловом конфиге репозитория `.ai-team/config.yaml`, который правят
как код. Проверка и публикация шаблона через REST, MCP и страницу «Шаблон»
(право `template.edit`) отклоняют такой шаблон: `400`, код `trusted_config_only`
(при проверке — `valid: false` с тем же кодом). Адаптеры, проверки и серверы
можно упоминать по имени, если их определения совпадают с определениями
активного шаблона, то есть команда не меняется. Чтение активного шаблона это
правило не затрагивает. Следствие: шаблон с командными гейтами правится в
файле; публикация через UI заменит его шаблоном без таких гейтов.

**Инфраструктура тоже не принимается из веба.** Не только команды: адрес и
имя переменной с токеном (`tracker.jira.base_url`/`token_env`,
`cicd.teamcity.base_url`/`token_env`), каналы `notifications` (`url_env`,
`smtp_url_env`, адресаты), `containment.profile`, `cli`/`model`/`effort`,
таймауты, `budget`, `auto_pickup`, `usage`, `tree_hash`, `redaction`,
`retention`, `tracker.adapter`, `tracker.web_base_url`, `tracker.inbound` и
политика `delivery` этапа позволили бы направить токен из окружения хоста на
чужой адрес или ослабить изоляцию. Правило устроено как явный allow-list полей
(`configFieldClasses` в `pkg/config/trusted_commands.go`) с четырьмя классами:

- **свободно из веба (процесс):** `template`, `title`, `schema_version`,
  `stall_after`; у этапа: `id`, `title`, `result`, `link_kind`,
  `required_sections`, `check`; карты статусов `tracker.on_enter`,
  `tracker.on_pass`, `tracker.jira.stage_statuses`; сами этапы можно добавлять и
  удалять;
- **только ужесточать:** `forbid_self_approval` (включённый в файле запрет
  нельзя выключить), `returns` (можно оставить только маршруты, которые есть в
  файле; новый маршрут отклоняется), `max_visits` и лимиты возвратов (эффективный
  лимит этапа не выше файлового); у существующего этапа `skippable` (нельзя
  сделать обязательный этап пропускаемым), `confirm` и `exit_gate_groups`: ни
  один гейт без команд из файла (подтверждение перехода `human_approval` тоже
  гейт) нельзя убрать или изменить, добавить новый гейт без команды можно;
- **совпадение с этапом файла:** `function`, `approver_function`, `executor`,
  `agent`, `adapter`, `mcp_servers` существующего этапа (поиск по `id`). Можно
  только снять адаптер (этап уйдёт на внутренний исполнитель) или сузить список
  MCP-серверов. Этап, которого нет в файле, может быть только `human` без
  `agent`, `adapter` и `mcp_servers`, а его роли должны уже встречаться в файле:
  веб не вводит ни нового исполнителя, ни новой роли подтверждающего;
- **равно файлу (инфраструктура):** всё остальное, включая `tracker.adapter`,
  `tracker.web_base_url`, `tracker.inbound`, `tracker.jira.*` (кроме карты
  статусов) и `delivery` этапа.

Сравниваются разобранные структуры; отсутствующая секция и пустая (`tracker: {}`,
`tracker.jira: {}`) считаются одной конфигурацией. Нарушение даёт `400`,
`trusted_config_only` с названием поля. Новая секция конфига по умолчанию
защищена: тест-сторож падает, пока поле не отнесено к классу. Консервативные
решения: `tracker.inbound` считается доверенным (внешний статус управляет
контроллером), `delivery` этапа можно только убрать (этап без delivery ничего не
доставляет), но не изменить или добавить.

Остаточный риск: право `template.edit` может удалять этапы целиком,
переименовывать этапы и менять `required_sections`/`check`. Убрать гейт без
команды у существующего этапа, сделать его пропускаемым, сменить роль, агента,
адаптер, лимиты и самоподтверждение из веба нельзя. Пустой `executor` файла
считается `human`.

**Запуск по сохранённым версиям отклоняется.** Шаблоны, опубликованные через веб
до этого правила, могли содержать командные гейты (`external_program`,
`docker_program`), новые `executor_adapters` и `checks`, изменённые адреса и токены
трекера или CI. Теперь шаблон, который собираются исполнять (закрепление за
задачей), проходит ту же проверку, что и присланный через веб: если он содержит
командные гейты или инфраструктурные секции, не совпадающие с файловым
`.ai-team/config.yaml`, запуск отклоняется с кодом `trusted_config_only`. Это
относится ко всем путям: `ai-team run --resume`, веб-запуск и resume, MCP
(`resume_task` — тот же REST-маршрут), пропуск этапа, повторную доставку и
процесс-воркер; у REST и MCP ответ `409` с кодом `trusted_config_only`.
Проверки `stageProblems` (роли, исполнитель, агент, адаптер, MCP-серверы этапа) и
`tightenProblems` (самоподтверждение, возвраты, лимиты посещений, пропуск, гейты
этапа) относятся только к присланному через веб документу; к уже закреплённому
шаблону они **не применяются**: приостановленная задача может законно жить с
процессом, который файл с тех пор изменил. При запуске проверяются только
команды и инфраструктура.

Различия в процессе (названия, мягкие гейты, карты статусов, роли, возвраты,
лимиты посещений) и в настройке `stage_timeout`, `gate_concurrency`,
`preflight_timeout`, `delivery_timeout`, `model`, `effort` запуску не мешают
(приостановленная задача сохраняет свои лимиты; из веба эти поля по-прежнему
менять нельзя);
командный гейт закреплённого шаблона допустим, если у файла в этапе с тем же `id`
есть тот же гейт (тот же `gate`, версия, имя, режим и параметры, то есть та же
команда); правка файла в другом месте законный `external_program` не блокирует.
Любое другое расхождение команд или инфраструктуры отклоняется, и текст отказа
называет выход: привести `.ai-team/config.yaml` к значениям закреплённого
шаблона через review либо начать новую задачу по активному шаблону. Побочный
эффект: если вы сами изменили инфраструктурную секцию файла (адрес, `cli`,
`containment`, `budget`, `tracker`) или саму команду, пока задача стояла на
паузе, её закреплённый шаблон перестанет совпадать, и resume потребует новой
задачи либо возврата файла.

**Якорь доверия вне веба.** «Активный шаблон» (`.ai-team/config.yaml`) сам по
себе не доверенный: его перезаписывает публикация из веба, и старая веб-версия
с командой осталась бы активной и «доверяла» самой себе. Поэтому при каждой
публикации контроллер (`TemplateStore.Publish`) пишет в `.ai-team/templates`,
вне содержимого шаблона: реестр `web-written/<sha256>` (хеши байт, которые веб
записал в `config.yaml`) и `trusted-baseline.yaml` (последний файловый конфиг,
который записал человек и который публикация заменила). Пока байты
`config.yaml` совпадают с записанным вебом хешем, файл считается
веб-записанным: командные гейты и инфраструктура сверх базового конфига
отклоняются (`trusted_config_only`, в тексте отказа сказано, что файл записан
через веб). Человек открыл файл, проверил и сохранил любую правку (хоть
комментарий): хеш изменился, файл снова доверенный код. Возврат побайтно той же
веб-версии из системы контроля версий снова делает её недоверенной. Без файла
`.ai-team/config.yaml` доверенная база пуста: закреплённый шаблон с командами
или инфраструктурой отклоняется, без них запускается. `ai-team template audit`
и предупреждение `ai-team web` теперь включают и активный шаблон, если его
записал веб. Ограничение: файл, который веб записал до появления реестра, в
нём не значится и считается файловым конфигом; такие версии показывает аудит.
Реестр и базовый конфиг лежат в локальном `.ai-team/` (он в `.gitignore`), как и
версии шаблонов. `ai-team web` при старте по-прежнему
печатает предупреждение со списком сохранённых версий, чьи команды или
инфраструктура не совпадают с активным шаблоном, и сообщает, что запуск по ним
отклоняется; если аудит не удалось выполнить, ошибка печатается. Просмотр
сохранённых версий и страниц задач правило не затрагивает.

Каталог моста фейкового трекера (`AI_TEAM_FAKE_TRACKER_DIR`) — локальный
доверенный канал для демо: тот, кто пишет в него, подаёт «внешний» статус,
который всё равно проходит через контроллер. Файлы моста открываются без
следования символьным ссылкам. В продакшене переменная не задаётся.

Сессии хранятся в базе дашборда: в ней лежит SHA-256 cookie, а не сама
cookie. Сессия ограничена 8 часами бездействия и 7 днями всего, отзывается при
выходе, при отзыве участника и при смене его функций. Каждая сессия хранит
отпечаток учётных данных (HMAC от секрета с фиксированной меткой, не сам
секрет; для SSO — с issuer и client ID). Если секрет `AI_TEAM_AUTH_SECRET` или
локальный токен утёк, смените его и перезапустите `ai-team web`: все сессии,
выпущенные под старым секретом, перестанут действовать. Cookie сессии —
`HttpOnly`, `SameSite=Strict`, `Secure` за TLS; пишущие запросы требуют
CSRF-токен сессии и проверку Origin, как и раньше.

Вход через SSO (OIDC) работает только в облачном режиме и fail-closed:
неверный или повторно использованный `state`, неверный `nonce`, подпись,
issuer, audience или истёкший `id_token` дают `401`; недоступность
провайдера или JWKS — `503`; ни в одном случае сессия не создаётся и вход не
понижается до другого способа. `id_token` принимается только из ответа token
endpoint, а не из запроса браузера. Функции пользователя берутся из
назначений участника на сервере, а не из claims. Участник находится по
подтверждённому ASCII e-mail, и при первом входе через SSO к нему
привязывается учётная запись провайдера (`iss` и `sub`). Дальше войти как этот
участник может только она же: если провайдер переназначит адрес другой
учётной записи, вход получит `403`. Одна учётная запись провайдера привязана
не больше чем к одному участнику. Отзыв участника снимает привязку; после
восстановления первый вход привяжет учётную запись заново (так переносят
участников на другого провайдера). Пока участник ни разу не входил через SSO,
защиты от переназначения адреса нет.

Незавершённых входов не больше 1000 одновременно, а с одного адреса клиента
(IPv4 или IPv6 /64) — не больше 20 за 10 минут; сверх лимита вход получает
`429` до записи в базу. Адрес берётся из TCP-соединения, заголовки прокси не
учитываются: за обратным прокси все клиенты делят один адрес прокси и этот
лимит становится общим. Новая сессия при входе отзывает ту, что была в этом
браузере, когда он начал вход: cookie `SameSite=Strict` приходит с запросом
входа на нашем сайте, а не с возвратом от провайдера, поэтому её отпечаток
сохраняется вместе с `state`. Брошенный вход прежнюю сессию не трогает.

Сетевой MCP (`POST /mcp`, [подробно](mcp.md)) не читает cookie и принимает только
`Authorization: Bearer`. Персональные токены `aitm_…` хранятся как SHA-256, выпускаются
и отзываются только владельцем через сессию с CSRF-токеном, имеют срок (до 365 дней)
и пишутся в журнал команды; роли берутся из реестра команды на каждый вызов, отзыв
участника действует сразу. Токен — долгоживущий секрет с правами владельца: храните его
как пароль. Проверка `Origin`: без заголовка допускается, с заголовком — только свой origin
или `--mcp-allowed-origins`. Ограничения скорости на подбор токена нет: токен — 256 бит
случайности; за публичным адресом ограничьте частоту на прокси.

MCP выполняет и **действия**, но не получает прав сверх личности токена: каждое действие — внутренний запрос
к тому же роутеру (те же обработчики, роли, функция этапа, запрет самоподтверждения, право администратора), а CSRF
браузера заменяет Bearer-токен (внутренний запрос несёт CSRF-токен той же личности). Инструменты не принимают
`actor_id`; решение по этапу требует точный `subject_hash`, обход гейта — право `admin` и причину, delivery — план по
`plan_hash`; каналом решения служит `mcp` (из контекста вызова, не из тела запроса). `/api/mcp/tokens` и
`/api/session` недоступны MCP: токен не выпускает токены (маршрут отвечает `403` на запрос из MCP), а cookie-сессии
у MCP нет. Каждое действие повторно доставляемо безопасно: `idempotency_key` (в SQLite, область — личность) не даёт
выполнить его дважды, а секрет, показываемый один раз (токен активации приглашения), в сохранённый для повторов ответ не
попадает. Успешное действие пишет `mcp_action` (канал, инструмент, токен, клиент, ключ; без аргументов) в журнал задачи
или команды. Полнота покрытия проверяется тестом: каждый маршрут роутера (`chi.Walk`) обязан иметь строку в матрице
паритета (инструмент или исключение с причиной).

Обход проваленного обязательного гейта — отдельное **системное право
администратора** (роль `admin`, permission `gate:override`), а не функция
процесса: `product_owner` его не подразумевает, ни шаблон (`function`,
`approver_function`), ни `roles` ребра approval не могут назвать `admin` (ошибка
конфигурации), проверка идёт на сервере для REST и MCP (обычный PO получает
`403`, обход без причины — ошибку валидации). Право выдаёт и снимает только
администратор, последнего активного администратора снять нельзя; отзыв
участника, чья роль не читается из реестра, отклоняется (fail-closed).
Создатель команды получает право вместе с `product_owner`, миграция схемы 17
выдаёт его только владельцу существующей команды (запись в журнал команды
`admin_granted_by_migration`); выдача смотрит на фактическое состояние (нет
активного администратора), а не на отметку версии, и повторяется при каждом
открытии базы, поэтому база, поднятая сборкой с более новой схемой без шага v17,
тоже получает администратора. В локальном режиме локальный владелец получает
право явно.

**Точка принуждения** — не HTTP-слой, а решение и пайплайн: (1) approval store
принимает `override` по `check_decision` только с `authority=system_admin` и
признаком аутентифицированного контроллера, `retry_gate` — только от
аутентифицированного контроллера; (2) `applyCheckOverride` в пайплайне
повторно требует `authority=system_admin` и (для доверенного store) решение
контроллера и отклоняет иное с понятной причиной, не применяя его; (3) CLI
`ai-team decision` отказывает для `override` и `retry_gate`, так что
`decision --action override … && run --resume` обход не проводит: authority
выставляет только контроллер после проверки права на сервере. Общий endpoint
решений по approval тоже не пропускает `override`. Использовать нужно
Web/REST (`POST /api/runs/{id}/stages/{stage}/override`) под администратором.
Записи `check_overridden` без `authority` (до S06) считаются legacy: они
показываются в истории окна как «legacy», ничего не разрешают и права не
расширяют.

Обход пишется неизменяемым `check_overridden` в hash-chained журнал (автор,
`authority`, время, причина, хеш результата, посещение, ID проваленных попыток)
и не меняет исход гейта; на другую версию результата он не действует. Повторы
технически упавших гейтов ограничены 10 раундами на попытку этапа
(версию результата): затем 409 с пояснением, остаются новая версия, возврат
или обход администратором. Устаревшее действие `override_approve` legacy-конфигурации с loopback
(ревьюер → кодер) — обычное решение человека на ребре графа: оно вне системы
гейтов, не требует права `gate:override`, не создаёт `check_overridden` и не
относится к проваленным гейтам шаблона.

Client secret задаётся только переменной окружения
(`--oidc-client-secret-env`). Он не входит в отпечаток сессии: смена только
client secret существующие сессии **не** отзывает. Если secret утёк, смените
его у провайдера и в `ai-team web`, а затем отзовите сессии сменой
`AI_TEAM_AUTH_SECRET` или отзывом участников.
