# Отчёт спринта октября 2026: гейты, исполнители, проекты и внешние интерфейсы

Спринт реализует ТЗ владельца от 2026-10-15 (задачи S01–S17). Базовый процесс —
девять этапов шаблона `idea-to-prod` из `pkg/config/load.go`; этапы графа остаются
последовательными, параллельны только гейты одного выходного перехода (fan-out/join
этапов — отдельная [задача #126](https://github.com/arturpanteleev/ai-team/issues/126)).
Каждый смёрженный PR получал patch-релиз (v0.2.1–v0.2.16).

## Как это устроено

- **Гейты.** Определения живут в Go-коде (`pkg/gatelib`) и меняются через PR; этап
  ссылается на `id@версия` и параметры. Шаблон и начатая задача закрепляют точные
  версии. Попытка хранит отдельно техническое исполнение
  (`pending/running/succeeded/error/timeout/canceled`) и вердикт
  (`pass/fail/not_applicable`). Контракт: [config.md](reference/config.md),
  [gate-protocol.md](reference/gate-protocol.md), спеки `gate-contract`,
  `pipeline-gates`, `external-gate`. Устройство планировщика — в
  [ARCHITECTURE.md](ARCHITECTURE.md).
- **Исполнители этапа.** Человек, внутренний агент или внешняя программа/контейнер по
  одному JSON-контракту (`stage-executor`); исполнитель только создаёт результат, тип,
  mutation scope и вердикт проверяет контроллер.
- **Статусы этапов** — чистая проекция durable-журнала, не редактируются вручную
  (`stage-status`, [TASK-FLOW-WEB-API.md](reference/TASK-FLOW-WEB-API.md)).
- **MCP.** Один реестр инструментов поверх того же роутера: те же роли, CSRF-границы,
  запрет самоподтверждения и аудит; каждый маршрут обязан иметь строку в матрице
  паритета ([mcp.md](reference/mcp.md), спека `mcp-server`).
- **Трекер.** Связь 1:1 хранится отдельным полем; входящий статус двигает граф только
  через штатный контроллер, конфликт показывается с причиной (`tracker-adapter`,
  [ARCHITECTURE.md](ARCHITECTURE.md#интеграция-с-трекером-задач)).
- **Права.** `product_owner`, `architect`, `developer`, `reviewer`, `qa`,
  `release_manager` и системное право `admin` (`gate:override`); `project:manage` и
  `tracker:link` — у владельца продукта и архитектора
  ([security.md](reference/security.md)).
- **Данные.** Версия схемы SQLite — 18 (v14 проекты, v15 токены MCP, v16 трекер,
  v17 администратор, v18 входящая синхронизация); версия схемы конфига — 6 (v5
  читается).

## Решения владельца (2026-10-15)

- До пяти параллельных исполнителей и до пяти ревьюеров; оркестратор мёржит PR после
  зелёного CI и `APPROVED`.
- Реальная Jira недоступна: S14/S15 сделаны под абстрактный интерфейс трекера (поле
  связи `tracker` + `issue_key`), Jira — один из адаптеров, приёмка на фейковом трекере.
- Дев/стейдж-среды нет: приёмка S17 и «выкладка» выполняются локально (запуск бинаря
  релиза) и релизом-тегом; версия поднимается patch'ем на каждый смёрженный PR.
- CoreKit (<https://github.com/propellerads/kit>) — необязательный пример внешнего
  агента; протокол работает с любым контейнерным агентом.

## Известные ограничения и остаточные проблемы

Накопленные замечания ревью, не блокирующие приёмку:

- файловый approval store работает без `TrustedDecisionAuthority`;
- системное право `admin` выдаётся владельцу команды при каждом открытии базы, если
  активного администратора нет;
- аудит отказанных MCP-вызовов пишется в журнал run по аргументам, без проверки
  существования run;
- нет индекса по `api_idempotency.created_at`;
- `ReturnStage` не проверяет самоподтверждение (возврат не подпадает под
  `forbid_self_approval`);
- Jira: читается только первая страница Changes, PAT/Bearer-аутентификация не
  поддержана;
- `gatephrases`: остаются краевые случаи;
- Docker: вложенные gitfile сабмодулей не поддержаны; Linux и Windows не проверялись
  (проверено на macOS);
- CoreKit не подключался: для него нужен флаг вывода результата в файл;
- реальные клиенты Claude и Codex проверены частично (см.
  [docs/demo/README.md](demo/README.md) после слияния PR демонстрации и раздел
  «Проверка на реальных клиентах» в [mcp.md](reference/mcp.md)).

Исправлено в S18: строка лога `web store (create missing stage): UNIQUE constraint
failed: stages.attempt_uid` на успешном демо-сценарии. Причина: `StageFinished` для
попытки этапа человека вызывается дважды (`pkg/pipeline/human_stage.go` и цикл этапов в
`pkg/pipeline/execute.go` после гейтов и delivery), а `StoreRecorder.StageFinished`
второй раз вставлял строку заново и терял итоговые проверки. Теперь строка обновляется
(`pkg/web/recorder.go`, тест `TestStoreRecorder_RepeatedStageFinishedUpdatesTheRowOnce`).

Исправлено в S20: повторная доставка той же ветки после возврата из ревью
(`pkg/delivery/planner.go`: новый план встаёт поверх коммита, который контроллер
записал при прошлой доставке; состояния подписаны HMAC с ключом вне рабочего дерева,
цепочка commits перепроверяется по сохранённым планам; push fast-forward, PR переиспользуется); этап
`executor: human` со встроенным агентом больше не падает на отсутствующем входе агента;
на PR-этапе ссылкой считается только URL PR, номер или поле `pr_url` (а не первый
не-Markdown выход); поведение без `human_approval` приведено в соответствие со справочником
(этап с возвратами по-прежнему ждёт решения `approve`/`return_to_*`, это описано явно).

Остаточное по S18: хранилище версий шаблонов не фиксирует происхождение версии (файл или
веб), поэтому запуск по сохранённой версии с чужими командами не блокируется, а
предупреждение печатается при старте `ai-team web`; право `template.edit` по-прежнему
меняет роли этапов, `forbid_self_approval` и выбор объявленного адаптера или MCP-сервера
для этапа (это процесс).

Расхождения справочных текстов `ai-team --help` с документацией (в справке нет
`--mcp-allowed-origins` и права `admin` в списке ролей `auth-token`) — в коде, не в
документации; код в этом PR не менялся.

## Как повторить демонстрацию

Пошаговый сценарий (проект → задача по девяти этапам → кодовый fail и новая версия →
LLM-гейт → решение человека → рекомендательный fail → админский обход → внешняя
программа и Docker-гейт → внутренний и внешний исполнитель → MCP → трекер в обе
стороны → delivery) и скрипты запуска — в [docs/demo/README.md](demo/README.md).
Он запускается локально на бинаре релиза, без дев/стейдж-среды и без ручных правок
базы.
