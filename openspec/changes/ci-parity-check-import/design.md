# Design — CI-parity check import (P1-8)

## Безопасная модель: никогда не исполняем YAML

Опасность: превратить workflow в источник произвольных команд — это
code-exec via YAML. Решение — **статическое ограниченное сопоставление**:

1. Из workflow читаются ТОЛЬКО `jobs[].steps[]` и в каждом шаге только
   `uses` и `run` (скалярные строки). Все остальные поля (env, shell, `with`,
   template-синтаксис, conditional) игнорируются — они не читаются и тем более
   не исполняются.
2. Каждый шаг проходит whitelist преобразование:
   - `run:` с префиксом известной команды → фиксированный `checks.Definition`,
     команда заимствуется из шага только при точном prefix-соответствии и
     отсутствии shell-операторов (`&&`, `;`, `|`, перенос строки).
   - `uses:<известный action>` → фиксированное определение (action-версия
     отбрасывается: на этапе импорта это только label, ничего не исполняется).
   - Всё остальное → `Skipped` с причиной; **не импортируется, не исполняется**.
3. Нет раскрытия переменных окружения/контекста GitHub — импорт детерминирован
   и не зависит от окружения, что и даёт стабильный fingerprint.

## Fingerprint до запуска

`SHA-256(json{checks[], sources[]})` — детерминированный. Adopter видит
сумму ДО запуска: можно зафиксировать её как ожидание и позже детектировать
дрейф суиты (кто-то поменял CI → fingerprint меняется → suite пересматривается).

## Формат и порядок

Jobs в YAML — mapping с непредсказуемым порядком; сортируем job-id (map keys)
и шаги сохраняем в порядке YAML. Definitions сортируются (class, name) и
дедуплицируются по имени — единый канонический набор вне зависимости от
порядка файлов/job'ов.

## Почему один формат

Начинаем только с GitHub Actions (формат по умолчанию). Расширение на другие
adopter-форматы (GitLab CI, CircleCI) — отдельные преобразователи за тем же
интерфейсом `Import(target, format)`, не трогая ядро. Это соответствует
"начать с одного adopter-формата".

## CLI

`ai-team ci-import` — импорт и показ только (checks НЕ запускаются командой).
Это отдельный read-only шаг: adopter видит suite до того, как смонтировать её
в pipeline. Вывод — через `logging.Emit` (OPS-6): JSON-стабильный record с
`data.fingerprint`, `data.checks`, `data.skipped`.
