# Coder не видит будущее ревью — contract test

## Why

Столп независимости оценки: «агент не может сам себе поставить зачёт». Это
только один из двух способов, которыми эта независимость может быть нарушена.
Второй, более коварный — **информационная утечка**: если artifacts
reviewer/tester/verifier (например, `review.md`, `test-report.md`,
`verification.md`) попадают во входы coder на прямом forward-проходе, то coder
уже на этапе написания кода «видит», что потом скажет ревьюер, и может
подстроить решение. Это молчаливая деградация честности оценки безо всякого
нарушения прав записи.

Сейчас код реализует это правильно (декларативные `inputs` + loopback через
`extraInputs`), но **нет ни одного теста**, который страхует именно *отрицательное*
свойство: что на прямом проходе во входы coder не попадает ничего из будущих
review/test-report/verification. Существующие тесты покрывают только *положительную*
сторону (loopback ДОБАВЛЯЕТ `review` во входы coder при retry). P1-9 закрывает
этот пробел дешёвым contract test'ом — вторым столпом независимости после V0-1
(mutation guard).

## What Changes

Контрактный тест в `pkg/pipeline/pipeline_test.go` (плюс runtime-уровень в
`pkg/runtime/runtime_test.go`), который фиксирует, что:

- На прямом forward-проходе набор входов coder — ровно его декларированные
  `inputs`, и никогда не включает `review`, `test-report`/`report`,
  `verification`.
- Reviewer/tester/verifier artifacts достигают coder ТОЛЬКО через явное
  loopback-ребро (`rejected` edge + человеческое решение) — это уже покрыто
  положительными тестами, но контракт дополнительно удостоверяет отсутствие
  утечки на первом проходе.
- Runtime-уровень: opencode read-правила deny `.ai-team/**`, и только явно
  переданные inputs разрешаются к чтению (уже есть
  `TestOpenCodeIsolationDeniesEffectsAndNarrowsEdits`, контракт его закрепляет
  как часть гарантии).

No production code changes — только тесты. Если тест упадёт (например, кто-то
добавит `review` в `inputs` coder или случайно начнёт авто-подмешивать artifacts
в `collectInputs`), это сигнализирует о нарушении независимости оценки.

## Success Criteria

- [green] Contract test проходит на текущем коде.
- [negative] Тест гарантированно ломается, если в `inputs` coder добавить
  `review` (проверено размышлением: декларативный вход стал бы видимым → тест
  красный).
- [coverage] Покрыты и прямые forward-проходы, и (для полноты) подтверждение,
  что coder получает `review` только после loopback.
- `make specs` зелёный; `go test ./pkg/pipeline/ ./pkg/runtime/` зелёный.
