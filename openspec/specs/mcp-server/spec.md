## Purpose

Сетевой MCP-сервер `ai-team`: один endpoint на веб-сервере, через который Claude и
Codex читают те же данные, что Web UI и REST, под личностью и ролями владельца токена.
Версия протокола — MCP 2026-07-28 (stateless Streamable HTTP). Действия и OAuth
в эту версию контракта не входят.

## Requirements

### Requirement: Stateless Streamable HTTP endpoint

Сервер MUST обслуживать `POST /mcp` по MCP 2026-07-28 без сессий: без заголовка
`Mcp-Session-Id`, с ответом `application/json`. Клиенты 2025-11-25 MUST иметь возможность
выполнить `initialize` без сессии. `GET` и `DELETE` MUST давать 405, уведомление — 202,
неподдерживаемая `MCP-Protocol-Version` — 400, тело запроса больше лимита — отказ без
выполнения.

#### Scenario: Современный и прежний клиент

- **КОГДА** клиент вызывает `server/discover` или `initialize` и затем `tools/list`
- **ТОГДА** сервер MUST ответить списком инструментов без выдачи сессии

#### Scenario: Неподдерживаемые методы

- **КОГДА** клиент шлёт `GET /mcp` или `DELETE /mcp`
- **ТОГДА** сервер MUST вернуть 405

### Requirement: Авторизация только Bearer-токеном

Каждый запрос `/mcp` MUST нести `Authorization: Bearer`. Cookie браузерной сессии MUST NOT
использоваться. Допустимы персональный MCP-токен и токен, принимаемый `IdentityVerifier`
веб-сервера. Принятый токен MUST быть сопоставлен с участником команды тем же правилом, что вход
в UI (`resolveTeamPrincipal`): участник активен, роли берутся из реестра команды на каждый вызов.
Неизвестный, просроченный, отозванный и повреждённый токен MUST давать один и тот же ответ 401
без различий в теле. Сервер без аутентификации MUST отказывать в обслуживании MCP.

#### Scenario: Недействительный токен

- **КОГДА** токен отсутствует, неизвестен, отозван или просрочен
- **ТОГДА** сервер MUST вернуть 401 с `WWW-Authenticate: Bearer` и одинаковым телом

#### Scenario: Только cookie

- **КОГДА** запрос несёт валидную cookie-сессию, но не Bearer
- **ТОГДА** сервер MUST вернуть 401

#### Scenario: Роли меняются

- **КОГДА** роли участника изменены или участник отозван
- **ТОГДА** следующий вызов с тем же токеном MUST видеть новые роли, а для отозванного — 401

### Requirement: Персональные MCP-токены

Авторизованный пользователь MUST мочь выпустить, перечислить и отозвать токены только для себя
через сессию браузера с CSRF-токеном. Секрет MUST показываться один раз; в базе MUST храниться
только SHA-256. Токен MUST иметь срок (по умолчанию 90 дней, максимум 365), метку, отметку
последнего использования и отзыва; живых токенов на человека MUST быть не больше 20. Выпуск и
отзыв MUST попадать в журнал команды. Токен MUST NOT быть учётными данными REST, MUST NOT
создавать браузерную сессию и MUST NOT управлять токенами. Чужой токен MUST выглядеть как
несуществующий.

#### Scenario: Только для себя

- **КОГДА** пользователь вызывает `POST /api/mcp/tokens` с чужим `actor_id` в теле или `DELETE` чужого токена
- **ТОГДА** поле MUST быть отвергнуто (400), а удаление чужого токена MUST вернуть 404

### Requirement: Проверка Origin

Запрос без `Origin` MUST допускаться. Запрос с `Origin` MUST допускаться только при совпадении с
собственным origin сервера или с настроенным allow-list; иначе MUST вернуться 403 до проверки токена.
В локальном режиме `Host` MUST быть loopback. Некорректный allow-list MUST останавливать запуск.

#### Scenario: Чужой Origin

- **КОГДА** запрос несёт `Origin`, которого нет в allow-list
- **ТОГДА** сервер MUST вернуть 403, даже при верном токене

### Requirement: Чтение через сервисный слой Web API

Инструменты и ресурсы чтения MUST выполняться теми же обработчиками, middleware и проверками ролей,
что REST-маршруты, под личностью токена, и MUST возвращать то же содержимое: проекты, backlog,
задачи с фильтрами, снимок задачи, результаты этапов, события, логи, артефакты и ревизии, шаблоны
и версии, каталог гейтов, метрики, команда, preflight. Все инструменты MUST быть помечены read-only;
действия MUST NOT регистрироваться. Параметры пути MUST проверяться до маршрутизации и MUST NOT выбирать
другой маршрут. Отказ роли, несуществующий ресурс и неверные аргументы MUST возвращаться как ошибка
инструмента `{error, code, status}` без данных, которых REST бы не вернул.

#### Scenario: Паритет с REST

- **КОГДА** пользователь вызывает `get_task` и `GET /api/runs/{id}` под своей личностью
- **ТОГДА** содержимое MUST совпасть

#### Scenario: Недостаточно прав

- **КОГДА** участник без права управления командой вызывает `list_team_members`
- **ТОГДА** результат MUST быть ошибкой 403 без списка участников

#### Scenario: Несуществующая задача

- **КОГДА** запрошен неизвестный `run_id`
- **ТОГДА** результат MUST быть ошибкой `not_found`

### Requirement: Ограничение и пагинация ответов

Списки без пагинации в REST MUST принимать `limit` и `offset` и сообщать `total`, `has_more`,
`next_offset`. Результат больше 256 КиБ MUST резаться по границе UTF-8 и возвращаться конвертом с
`next_byte_offset`; повторный вызов с `byte_offset` MUST продолжать с этого места, а склейка частей MUST
давать исходное содержимое. Нетекстовое содержимое MUST NOT отдаваться.

#### Scenario: Большой артефакт

- **КОГДА** артефакт больше лимита читается последовательно по `next_byte_offset`
- **ТОГДА** склеенные части MUST совпасть с файлом байт в байт
