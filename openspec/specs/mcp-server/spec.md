## Purpose

Сетевой MCP-сервер `ai-team`: один endpoint на веб-сервере, через который Claude и
Codex читают те же данные и выполняют те же действия, что Web UI и REST, под личностью и
ролями владельца токена. Версия протокола — MCP 2026-07-28 (stateless Streamable HTTP).
OAuth в эту версию контракта не входит.

## Requirements

### Requirement: Stateless Streamable HTTP endpoint

Сервер MUST обслуживать `POST /mcp` по MCP 2026-07-28 без сессий: без заголовка
`Mcp-Session-Id`, с ответом `application/json`. Клиенты 2025-11-25 MUST иметь возможность
выполнить `initialize` без сессии. `GET` и `DELETE` MUST давать 405, уведомление — 202,
неподдерживаемая `MCP-Protocol-Version` — 400, тело запроса больше лимита — отказ без
выполнения.

#### Scenario: Современный и прежний клиент

- **КОГДА** клиент вызывает `server/discover` или `initialize` и затем `tools/list`
- **ТОГДА** сервер MUST ответить списком инструментов без выдачи сессии

#### Scenario: Неподдерживаемые методы

- **КОГДА** клиент шлёт `GET /mcp` или `DELETE /mcp`
- **ТОГДА** сервер MUST вернуть 405

### Requirement: Авторизация только Bearer-токеном

Каждый запрос `/mcp` MUST нести `Authorization: Bearer`. Cookie браузерной сессии MUST NOT
использоваться. Допустимы персональный MCP-токен и токен, принимаемый `IdentityVerifier`
веб-сервера. Принятый токен MUST быть сопоставлен с участником команды тем же правилом, что вход
в UI (`resolveTeamPrincipal`): участник активен, роли берутся из реестра команды на каждый вызов.
Неизвестный, просроченный, отозванный и повреждённый токен MUST давать один и тот же ответ 401
без различий в теле. Сервер без аутентификации MUST отказывать в обслуживании MCP.

#### Scenario: Недействительный токен

- **КОГДА** токен отсутствует, неизвестен, отозван или просрочен
- **ТОГДА** сервер MUST вернуть 401 с `WWW-Authenticate: Bearer` и одинаковым телом

#### Scenario: Только cookie

- **КОГДА** запрос несёт валидную cookie-сессию, но не Bearer
- **ТОГДА** сервер MUST вернуть 401

#### Scenario: Роли меняются

- **КОГДА** роли участника изменены или участник отозван
- **ТОГДА** следующий вызов с тем же токеном MUST видеть новые роли, а для отозванного — 401

### Requirement: Персональные MCP-токены

Авторизованный пользователь MUST мочь выпустить, перечислить и отозвать токены только для себя
через сессию браузера с CSRF-токеном. Секрет MUST показываться один раз; в базе MUST храниться
только SHA-256. Токен MUST иметь срок (по умолчанию 90 дней, максимум 365), метку, отметку
последнего использования и отзыва; живых токенов на человека MUST быть не больше 20. Выпуск и
отзыв MUST попадать в журнал команды. Токен MUST NOT быть учётными данными REST, MUST NOT
создавать браузерную сессию и MUST NOT управлять токенами. Чужой токен MUST выглядеть как
несуществующий.

#### Scenario: Только для себя

- **КОГДА** пользователь вызывает `POST /api/mcp/tokens` с чужим `actor_id` в теле или `DELETE` чужого токена
- **ТОГДА** поле MUST быть отвергнуто (400), а удаление чужого токена MUST вернуть 404

### Requirement: Проверка Origin

Запрос без `Origin` MUST допускаться. Запрос с `Origin` MUST допускаться только при совпадении с
собственным origin сервера или с настроенным allow-list; иначе MUST вернуться 403 до проверки токена.
В локальном режиме `Host` MUST быть loopback. Некорректный allow-list MUST останавливать запуск.

#### Scenario: Чужой Origin

- **КОГДА** запрос несёт `Origin`, которого нет в allow-list
- **ТОГДА** сервер MUST вернуть 403, даже при верном токене

### Requirement: Чтение через сервисный слой Web API

Инструменты и ресурсы чтения MUST выполняться теми же обработчиками, middleware и проверками ролей,
что REST-маршруты, под личностью токена, и MUST возвращать то же содержимое: проекты, backlog,
задачи с фильтрами, снимок задачи, результаты этапов, события, логи, артефакты и ревизии, шаблоны
и версии, каталог гейтов, вычисляемые статусы этапов (`get_task_stage_statuses`, тот же JSON, что
`stage_statuses` в `get_task`; см. capability stage-status), метрики, команда, preflight, состояние трекера.
Инструменты чтения MUST быть помечены read-only. Параметры пути MUST проверяться до маршрутизации и MUST NOT выбирать
другой маршрут. Отказ роли, несуществующий ресурс и неверные аргументы MUST возвращаться как ошибка
инструмента `{error, code, status}` без данных, которых REST бы не вернул.

#### Scenario: Паритет с REST

- **КОГДА** пользователь вызывает `get_task` и `GET /api/runs/{id}` под своей личностью
- **ТОГДА** содержимое MUST совпасть

#### Scenario: Недостаточно прав

- **КОГДА** участник без права управления командой вызывает `list_team_members`
- **ТОГДА** результат MUST быть ошибкой 403 без списка участников

#### Scenario: Несуществующая задача

- **КОГДА** запрошен неизвестный `run_id`
- **ТОГДА** результат MUST быть ошибкой `not_found`

### Requirement: Ограничение и пагинация ответов

Списки без пагинации в REST MUST принимать `limit` и `offset` и сообщать `total`, `has_more`,
`next_offset`. Результат больше 256 КиБ MUST резаться по границе UTF-8 и возвращаться конвертом с
`next_byte_offset`; повторный вызов с `byte_offset` MUST продолжать с этого места, а склейка частей MUST
давать исходное содержимое. Нетекстовое содержимое MUST NOT отдаваться.

#### Scenario: Большой артефакт

- **КОГДА** артефакт больше лимита читается последовательно по `next_byte_offset`
- **ТОГДА** склеенные части MUST совпасть с файлом байт в байт

### Requirement: Действия через сервисный слой Web API

Каждое продуктовое действие Web/REST MUST иметь MCP-инструмент: проекты, backlog, создание, запуск,
возобновление и отмена задачи, выбор исполнителя, сдача результата, запуск агента, повтор гейта, решения,
возвраты, пропуски, обход гейта, delivery-план и delivery, шаблон, команда и роли, связь с трекером.
Инструмент MUST выполняться внутренним запросом через тот же роутер, обработчики и проверки, что REST,
под личностью токена; бизнес-переходы MUST NOT реализовываться в слое MCP. Инструмент MUST NOT принимать `actor_id` или иным образом позволять
действовать от имени другого человека. Роль, функция этапа, запрет самоподтверждения, право
администратора, причина и точный хеш MUST проверяться теми же серверными правилами, что для
Web UI: клиент без права получает тот же отказ, и действие MUST NOT дойти до контроллера. CSRF
браузера для MCP-вызова заменяется Bearer-токеном: внутренний запрос MUST нести CSRF-токен той же
личности; cookie-сессия на `/mcp` MUST NOT использоваться. MCP MUST NOT выпускать, перечислять и
отзывать токены, создавать или завершать браузерную сессию. Длинное действие MUST возвращать
идентификатор задачи сразу, а состояние и результат MUST читаться отдельными инструментами.

#### Scenario: Неправомочный клиент

- **КОГДА** участник без функции этапа подтверждает чужой этап, а не администратор обходит провал гейта
- **ТОГДА** результат MUST быть ошибкой 403 и контроллер MUST NOT быть вызван

#### Scenario: Личность из токена

- **КОГДА** инструмент вызван с аргументом `actor_id`
- **ТОГДА** вызов MUST быть отвергнут как неверный аргумент, а действие MUST записываться на владельца токена

#### Scenario: Токены недоступны

- **КОГДА** внутренний запрос с личностью MCP обращается к `/api/mcp/tokens`
- **ТОГДА** ответ MUST быть 403

### Requirement: Подтверждения с точным хешем

`confirm_stage` и `decide_approval` MUST требовать `subject_hash` (SHA-256) и MUST NOT подставлять
хеш за клиента; устаревший хеш MUST давать отказ `subject_hash_mismatch`. Утверждение delivery-плана
MUST требовать `plan_hash`, обход гейта и пропуск этапа — непустую причину. Событие решения
человека MUST нести канал `mcp`, определённый транспортом, а не телом запроса. `confirm_stage` и
`return_stage` при ожидающем подтверждении перехода MUST принимать `stage_id` подтверждаемого этапа
(`from_stage` согласования; допустим и следующий этап, как у прежних клиентов) и MUST проверять право по
функции подтверждаемого этапа и роли согласования: точный хеш, роли согласования и запрет самоподтверждения
сохраняются.

#### Scenario: Решение без хеша

- **КОГДА** клиент вызывает `confirm_stage` без `subject_hash`
- **ТОГДА** вызов MUST быть отвергнут до обращения к контроллеру

#### Scenario: Самоподтверждение

- **КОГДА** автор результата подтверждает его по MCP при `forbid_self_approval`
- **ТОГДА** результат MUST быть ошибкой `self_approval_forbidden`

### Requirement: Ключ запроса и повторная доставка

Каждый POST-инструмент MUST требовать `idempotency_key` (1-128 видимых символов); PUT, PATCH и DELETE
MAY его принимать. Первая доставка MUST занять ключ в области личности, выполнить действие и сохранить
ответ; повтор с тем же ключом и теми же аргументами MUST вернуть сохранённый ответ (с пометкой
`idempotent_replay`) без повторного выполнения; тот же ключ с другими аргументами MUST давать
`idempotency_conflict`. Ответ MUST сохраняться при любом коде, включая 5xx (действие могло уже иметь побочные эффекты, как в REST); ключ освобождается только при сбое до диспетча. Ключ и ответ MUST храниться 7 суток, просроченные ключи MUST удаляться при выдаче нового ключа. Секреты, показываемые один раз, MUST NOT
сохраняться для повторов. Решение человека дополнительно MUST распознаваться сервисом решений по
(актор, действие, хеш, роль) независимо от ключа.

#### Scenario: Повтор не удваивает действие

- **КОГДА** клиент дважды доставляет `start_task` или `confirm_stage` с одним ключом
- **ТОГДА** MUST существовать одна задача и одно решение

### Requirement: Аудит канала MCP

Каждое успешное изменяющее действие, а также отказ 401/403 по нему MUST оставлять запись `mcp_action` с каналом `mcp`, инструментом,
владельцем токена, идентификатором токена, клиентом и ключом запроса, без аргументов (запись отказа помечена `denied`; сбой записи MUST NOT ломать вызов): в журнале
задачи для успешного действия над задачей, иначе в журнале команды. Отказ 401/403 MUST писаться только в журнал команды (заявленный `run_id` — как данные записи), потому что отказанный вызов не подтверждает ни существование задачи, ни права на неё.

#### Scenario: Действие видно как MCP

- **КОГДА** администратор обходит гейт через MCP
- **ТОГДА** журнал задачи MUST содержать запись обхода и запись `mcp_action` с его личностью и каналом `mcp`

### Requirement: Матрица паритета маршрутов

Для каждого маршрута, который обслуживает роутер, MUST существовать строка матрицы: MCP-инструмент,
вызывающий именно этот метод и путь, либо исключение с причиной (транспортная авторизация MCP выполняет
функцию маршрута или маршрут запрещён для MCP: сессия, SSO, токены, активация приглашения, WebSocket,
статика). Тест MUST обходить реальный роутер и падать при маршруте без строки, строке без маршрута и
инструмента без строки.

#### Scenario: Новый маршрут

- **КОГДА** в роутер добавлен маршрут без строки матрицы
- **ТОГДА** тест паритета MUST упасть и назвать маршрут
