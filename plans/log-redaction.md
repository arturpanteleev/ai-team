# Log redaction (гигиена логов)

Статус: идея
Источник: AUDIT M-07

## Задача

Политика классификации и редакции того, что попадает в evidence logs, отчёты
и экспорты: stdout/stderr агентов, вывод проверок, диагностические бандлы
могут содержать секреты и персональные данные.

## Ценность для продукта

Логи — единственное место, где продукт сам копирует потенциально секретное
содержимое на диск надолго. Одна утечка через расшаренный отчёт или
приложенный к issue лог перечёркивает всю историю «строгости». Редакция даёт
право делиться: приложить отчёт в PR, отправить диагностику коллеге,
включить экспорт телеметрии — без ручного вычитывания. Для команд это
условие комплаенса, для соло-пользователя — страховка от собственной ошибки.

## Рекомендации по реализации

- классификация источников: agent stdout/stderr (рискованный), check output
  (ограниченный), controller events (чистые);
- редакция по паттернам: ключи/токены (AWS, GH, OpenAI форматы), .env-
  присваивания, абсолютные пути хоста; redaction receipt — что замазано,
  без оригинала;
- сырые логи хранятся только внутри immutable run root с укороченным
  retention (связано с plans/retention-gc.md); отчёты/экспорты — только
  редактированные версии;
- ориентир: ALK neutrality/redaction подход.

## Как проверить

1. Hostile fixture печатает фейковые секреты в stdout — в reports/экспортах
   они замаскированы, в evidence есть redaction receipt.
2. Абсолютные пути хоста отсутствуют в HTML-отчёте.
3. Легитимный вывод (код, диффы) не повреждается ложными срабатываниями.
