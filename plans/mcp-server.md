# MCP server (только чтение)

Статус: идея

## Задача

MCP-сервер только на чтение: внешний агент (Claude Desktop, другая сессия
кодинг-агента, любой MCP-клиент) может узнать, что происходит в ai-team —
какие раны, на каком этапе, что ждёт решения, что показали проверки.
Управляющих операций нет вообще.

## Ценность для продукта

Знания о прогонах сегодня заперты в наших интерфейсах: сторонний агент либо
не видит ничего, либо должен разбирать файлы .ai-team на свой страх и риск.
MCP делает состояние продукта потребляемым экосистемой агентов напрямую:
«что происходило в прогоне по задаче X?» — и агент отвечает из timeline, не
имея доступа к коду проекта. Вторая параллельная сессия получает контекст
чужого прогона без пересечения с ним; руководитель спрашивает у своего
ассистента статус всех задач, не открывая дашборд. Для продукта это канал
распространения: любой MCP-клиент становится окном в ai-team без нашего UI,
а жёсткая граница «read-only» сохраняет инвариант безопасности — управлять
конвейером может только человек через веб/CLI.

## Рекомендации по реализации

- инструменты (черновик): `list_runs`, `get_run`, `get_timeline`,
  `list_pending_approvals`, `get_artifact` / `get_report` (ограниченный по
  объему (bounded), без секретов);
- транспорт: stdio первым (стандарт для локальных MCP), HTTP позже;
- данные переиспользуют read-API слоя web и каталог событий
  (plans/context-checkpoints.md) — новый сервер это другой транспорт к тем же
  данным, не новая логика;
- явно задокументировать границу: мутаций нет и не будет в этом контракте.

## Как проверить

1. MCP-клиент (Claude Desktop) видит список ранов (runs) и статус живого
   прогона.
2. Инструмент подтверждения (approval) отсутствует как инструмент — попытка
   мутации невозможна на уровне контракта.
3. Чтение артефакта ограничено по объему и не отдаёт файлы вне разрешённых
   корней (та же политика путей, что в web).
