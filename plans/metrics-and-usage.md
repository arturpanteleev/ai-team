# Metrics & usage accounting (метрики всего)

Статус: idea
Источник: ALK parity — `docs/reference/usage-export.md`, `lifecycle-cost.md`,
`host-local-token-accounting.md`

## Задача

Автоматически измерять всё, что возможно, на каждом этапе и run в целом.
Никакой ручной отчётности: токены, время, попытки, исходы — фиксируются
контроллером как побочный продукт исполнения.

## Ценность для продукта

Сейчас о прогоне известно только «прошёл/не прошёл» — ни стоимость, ни
узкие места. С метриками появляются ответы на вопросы владельца: сколько
токенов съела фича, какой этап самый дорогой, растут ли loopback-циклы после
изменения промптов. Это превращает продукт из чёрного ящика в управляемый:
можно сравнивать хосты и модели по цене/качеству, ловить деградацию между
версиями, показывать пользователям объективную картину вместо ощущений.
Метрики — обязательный фундамент для model-routing и evals; без них оба
направления слепы.

## Рекомендации по реализации

- мерить: токены (prompt/completion/total) на attempt и этап; длительность
  этапа/попытки/run; число попыток и loopback-циклов по стадиям; размер
  контекста; счётчики исходов (passed/rejected/blocked/warning); cost_usd
  опционально, если хост отдаёт;
- хранение: в attempt manifest / events evidence (hash-chain уже есть);
  агрегаты — в SQLite projection для дашборда;
- экспорт: единый JSON envelope за run;
- смотреть реализацию у ALK (usage export envelope).

## Как проверить

1. После любого run существует машиночитаемый файл/envelope с метриками,
   значения сходятся с evidence events.
2. Дашборд показывает токены/длительность по этапам без ручных действий.
3. Два одинаковых прогона дают сопоставимые метрики (детерминированность
   измерения), а прогон с изменённым числом ретраев — корректно отличимые.
