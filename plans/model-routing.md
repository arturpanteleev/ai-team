# Model routing (выбор модели по этапам)

Статус: idea
Источник: ALK parity — `profiles/model-routing-profile.v1.json`,
`docs/reference/model-routing.md`

## Задача

Выбор модели для каждого этапа workflow через конфигурируемый профиль:
тяжёлые reasoning/thinking-модели на архитектуру и ревью, дешёвые быстрые —
на механические этапы. Классы моделей (fast / reasoning / thinking) поверх
конкретных ID, чтобы профили были переносимы между провайдерами.

## Ценность для продукта

Одинаковая дорогая модель на всех этапах — это переплата за механическую
работу и узкое место в доступности. Роутинг даёт управление ценой/качеством
как настройкой, а не переписыванием: аналитик может быть дешёвым и быстрым,
архитектор — thinking-моделью, ревью — независимой моделью другого
провайдера (заодно снижая «одноглазость» само-ревью). Для пользователей это
снижение стоимости фичи в разы при сохранении качества там, где оно нужно;
для продукта — применимость к разным экосистемам моделей без хардкода.
Позже метрики + роутинг дают автоматический выбор «самый лёгкий безопасный
режим» (quality-cost learning у ALK).

## Рекомендации по реализации

- профиль: этап → класс модели (+effort), с дефолтами; переопределение на
  уровне run;
- классы fast/reasoning/thinking мапятся на конкретные ID в слое адаптера
  хоста (зависимость от adapters-layer);
- сравнение маршрутов опирается на metrics-and-usage;
- посмотреть: model-routing-profile.v1.json в ALK; подходы китайских
  провайдеров (показать отдельно).

## Как проверить

1. Конфиг задаёт разные модели двум этапам — run использует их по evidence
   (в attempt manifest виден факт).
2. Один профиль переносится между двумя хостами без правки этапов.
3. Прогон с «дешёвым» профилем дешевле полного при том же конечном исходе —
   измеряется метриками.
