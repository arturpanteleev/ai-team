# Multi-repo (задачи на несколько репозиториев)

Статус: идея

## Задача

Одна задача может затрагивать несколько репозиториев: candidate worktree,
checks, delivery plan и PR создаются на каждый репозиторий, отчёт агрегирует
все изменения под одним run_id.

## Ценность для продукта

Реальные фичи часто пересекают границы репозиториев (клиент + API + общая
библиотека), а сегодня такой запуск невозможен в принципе — только N ручных
прогонов с ручной синхронизацией требований между ними. Мультирепо закрывает
класс «интеграционных» задач целиком: один proposal, одна трасса AC на все
репо, согласованный delivery, один итоговый отчёт со всеми PR. Для команд это
разница между «инструмент для одного сервиса» и «инструмент для платформы».

## Рекомендации по реализации

- RunConfig: список targets вместо одного; lifecycle/evidence остаются
  per-run, candidate manager создаётся per-target;
- delivery plan получает секцию по каждому репозиторию (forge-adapters
  переиспользуются);
- approval-политики: единое решение на весь run или per-repo — решить при
  проектировании;
- большой кусок: начинать с design doc, не сразу код.

## Как проверить

1. Fixture из двух репозиториев: фича доходит до двух PR, evidence покрывает
   оба.
2. Сбой во втором репо не оставляет первый в рассинхронизированном состоянии
   (компенсация/явный blocked).
