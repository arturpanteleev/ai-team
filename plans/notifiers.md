# Notifiers (подписка на события)

Статус: идея

## Задача

Push-уведомления о событиях запусков (run) во внешние каналы. Пользователь
подписывается на классы событий (см. каталог в
plans/context-checkpoints.md) и получает сообщения в мессенджер/почту — не
держа веб открытым. Первая итерация: Slack и email; Telegram и другие — тем
же адаптерным контрактом позже.

## Ценность для продукта

Сегодня о том, что прогон остановился и ждёт решения, узнаёшь, только когда
снова открываешь дашборд — автономный режим на этом ломается: агент стоит,
человек не в курсе. Уведомители (notifiers) замыкают цикл: «запуск (run)
ждет подтверждения плана доставки (delivery plan)» прилетает в Slack, решил
с телефона через CLI/веб — конвейер поехал дальше. Это прямой рост пропускной
способности автономной работы: время простоя между «агент остановился» и
«человек заметил» сокращается с минут/часов до секунд. Для команд — общий
канал прозрачности: блокировки (blocked), нарушения политик (guard violations) и завершения видны всем, а не только автору задачи. Email покрывает
нестрожащие дайджесты (итоги дня/результаты запусков (run)), Slack — события,
требующие реакции.

## Рекомендации по реализации

- подписка = конфиг в слое project/user: `event class → channel`; классы уже
  определены: NEEDS_HUMAN (приоритет), TERMINAL, INVALIDATING; INFO по
  умолчанию не рассылается;
- **Slack**: входящий webhook (incoming webhook); подход переиспользовать из
  рабочих адаптеров;
- **Email**: SMTP-отправитель + шаблон письма;
- доставка асинхронная из контроллера: сбой канала НЕ влияет на pipeline
  (лог + повторные попытки (retry) с экспоненциальной задержкой (backoff),
  максимум N попыток);
- шаблоны сообщений: читаемый заголовок из каталога типов + минимум полей
  (run_id, этап, действие); без секретов и сырых логов;
- дедупликация: не спамить повторными NEEDS_HUMAN на тот же approval.

## Как проверить

1. Запуск (Run) встал в ожидание подтверждения (waiting_for_approval) → сообщение приходит в канал ≤ N секунд, повторного сообщения нет.
2. Падение webhook не проваливает запуск (run) — сбой виден в логах, pipeline зелёный.
3. Фильтры подписки соблюдаются: INFO-события не доставляются, если не включены явно.
4. Секреты/пути хоста отсутствуют в сообщениях.
