# Pipeline refactoring (остаточная декомпозиция)

Статус: идея

## Задача

Второй этап декомпозиции pkg/pipeline после разделения на 8 файлов:
`runStage` (~300 строк) и `RunWithResult` (bootstrap-монстр) остаются
слишком большими; швы размечены.

## Ценность для продукта

Прямой пользовательской ценности нет — это инвестиция в скорость и
безопасность всех будущих изменений ядра. Огромные функции = каждое
изменение approvals/delivery требует чтения сотен строк контекста, высокий
риск регрессий, медленное онбординг-ревью. Меньшие единицы = точечные диффы,
точечные тесты, возможность параллельной работы над подсистемами. После
этого задача рефакторинг перестаёт быть аргументом против новых фич.

## Рекомендации по реализации

- `runStage` → подготовка (baseline, guard setup) / исполнение / вердикт-
  конвейер — три функции-компоновщика;
- `RunWithResult` → bootstrap.go: resumeState / setupCandidate /
  replayEvidence / initReports (куски уже почти самостоятельные);
- только механические перемещения внутри пакета, без изменения поведения;
- гонять полный сьют + e2e после каждого шага; коммиты по одному шву.

## Как проверить

1. Ни одна функция не превышает ~150 строк; ни один файл ~400.
2. Полный тест-сьют зелёный без правок самих тестов.
3. Покрытие пакета не упало.
