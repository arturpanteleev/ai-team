# Tree hashing performance (перформанс хеширования)

Статус: идея
Источник: AUDIT M-05; SCOPE_REVIEW корзина 3

## Задача

Две параллельные реализации полного обхода дерева (`checks.workspaceDigest`
и `captureFilesystemSnapshot`) дают ~17 полных проходов по репозиторию за
прогон, включая игнорируемые файлы и node_modules. Заменить на git-tree
дайджесты + одну кеширующую реализацию.

## Ценность для продукта

Каждый лишний проход — это секунды на среднем репо и десятки секунд на
монорепо, умноженные на каждый этап/чек. Пользователь платит латентностью за
реализационную случайность, а нестабильность из-за caches даёт ложные
срабатывания guard'а. Одна быстрая реализация = заметно более резвые прогоны
на больших проектах (расширение применимости с «маленьких пет-проектов») и
меньше ложных блокировок. Candidate worktree уже делает большую часть работы
ненужной — задача фиксирует этот выигрыш.

## Рекомендации по реализации

- одна функция digest'а: для git-проектов — `git write-tree`/tree hash от
  candidate worktree (O(changes), не O(tree)); fallback полный walk только
  вне git;
- исключать ignored/node_modules через git check-ignore;
- удалить вторую реализацию; все вызовы (checks before/after, delivery,
  snapshots) идут через неё;
- бенчмарк до/после на fixture-репо ~10k файлов.

## Как проверить

1. Число полных walk'ей за прогон падает с ~17 до ≤3 (замер инструментально).
2. На монорепо-фикстуре время стадии сокращается измеримо.
3. Guard по-прежнему ловит мутацию файла вне scope (тесты существующие).
